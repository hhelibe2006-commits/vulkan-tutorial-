= 内存模型与一致性：简介

== 概述

上一章我们看了如何通过高占用率和紧凑的数据布局让 GPU 保持忙碌。但当你把计算派发从简单、独立的任务扩展到复杂、协作的算法时，很快会遇到一个更棘手的问题：**内存一致性**（确保 GPU 的所有部分在同一时刻看到相同的数据）。

你如何知道一个调用写入的值对另一个调用可见？如果两个调用同时写同一位置会怎样？如何在数千个线程之间高效共享数据，又不撞进竞态条件？

=== Vulkan 的显式特性

在 CPU 上，缓存一致性硬件确保一旦线程 A 完成一次存储，其他 CPU 核心最终会观察到新值。然而 CPU 多线程编程仍然需要显式同步——没有 `std::atomic`、互斥锁或内存栅栏，编译器和乱序执行的 CPU 核心可以自由重排或延迟操作，从而产生数据竞争。

在 GPU 上却**不是**这样。数千个线程在多个计算单元上并发执行，每个计算单元都有自己的分层缓存（**L1**——一级缓存、**L2**——二级缓存等），让所有线程对内存的视图保持同步是一件极其昂贵的事。Vulkan 的哲学很简单：**同步从不自动发生**。如果你希望一次写入对某次读取可见，你必须显式说明。

== 内存管理的三大支柱

本章我们将深入 Vulkan 为管理这种复杂性提供的机制：

1.  **Vulkan 内存模型**：掌握可用性、可见性与域操作，在线程之间建立正式的**「先于发生」**（Happens-Before）关系（一种严格的操作顺序）。
2.  **共享内存（LDS）**：利用一小块极快的工作组本地内存，做高速数据交换与手动缓存。
3.  **内存一致性**：使用 Slang 的 `GroupMemoryBarrierWithGroupSync` 与 Vulkan 1.4 的细粒度屏障，尽量减少管线停顿、最大化吞吐量。

== 为什么这很重要

高效的内存同步，是高性能模拟与一团破碎、不确定的乱麻之间的区别。

*   **同步过度**：内核会变慢，因为每个线程都在不停等别的线程。
*   **同步不足**：你会得到闪烁的结果、「幽灵」数据，以及只在某些硬件上才出现的难调崩溃。

我们先从理论基础讲起：**Vulkan 内存模型**。它乍看可能很抽象，但它是写出可移植、健壮、能在从智能手机到高端工作站的各种 GPU 上运行的计算代码的关键。
