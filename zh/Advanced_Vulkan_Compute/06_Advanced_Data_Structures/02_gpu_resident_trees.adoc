= 驻留 GPU 的树结构：BVH 与八叉树

== 为什么要用树？

树是空间划分的基本结构。无论你是在查找某条光线命中了哪些三角形，还是在查找某个粒子附近的物体，对每个对象做线性搜索都太慢了。

虽然在 CPU 上递归地构建树很容易，但在 GPU 上构建却出了名的困难，原因是 SIMD 执行模型以及缺少共享堆。不过，只要方法得当，GPU 构建一棵树的速度可以远超 CPU。

== 包围体层次结构（BVH）

BVH 是一棵树，其中每个节点代表一个包围盒，该包围盒包含它的所有子节点。这是每个光线追踪引擎的核心。

传统上，BVH 会被「拍平」成线性数组，子节点的链接用数组下标表示。在现代硬件上，我们可以用**基数树**（一种空间优化的树）或 **Morton 码**来构建这些树。

=== BVH 节点的构成

BVH 中典型的**内部节点**必须存储自己的空间边界以及指向子节点的指针。**叶节点**则存储边界以及它所包含的图元（例如三角形）列表。

为了节省空间并改善缓存局部性，这些内容通常被打包进一个结构体：

[source,slang]
----
struct BVHNode {
    float3 min;           // AABB Min: The minimum corner of the bounding box
    uint   childOrLeaf;   // Index to children OR first triangle in leaf
    float3 max;           // AABB Max: The maximum corner of the bounding box
    uint   count;         // Number of children (if inner) OR triangles (if leaf)
};
----

在这个布局中：

*   **AABB（轴对齐包围盒）**：由两个点（`min` 和 `max`）表示。这是最常见的体积类型，因为在 GPU 上判断光线是否命中一个盒子极快。
*   **childOrLeaf**：一个 32 位整数，指向树的下一层。如果 `count > 0`，它就是叶节点。如果 `count == 0`，它就是内部节点，而 `childOrLeaf` 是 `nodePool` 缓冲区中第一个子节点的下标。

=== 构建层次结构：Morton 码

1.  **Morton 编码**：我们把三维位置映射到一维的**空间填充曲线**（即 **Z 曲线**）上。具体做法是**交错排列** X、Y、Z 坐标的各个比特位。例如，若 X 为 `010`、Y 为 `101`，则 Morton 码为 `011001`（X[0] 贡献 0，Y[0] 贡献 1，X[1] 贡献 1，Y[1] 贡献 0，依此类推）。这种映射有一个神奇的性质：在三维空间中接近的点，在一维空间中也会接近，从而有效地把三维层次结构「拍平」成一个有序列表。
2.  **基数排序**：拿到 Morton 码之后，我们使用高性能的 GPU **基数排序**。基数排序是一种非比较排序算法，逐位地对数字排序。由于不需要复杂的比较，它在 SIMD 硬件上极其高效。对 Morton 码排序，正是从空间上把物体「分组」的步骤。
3.  **构建层次结构**：排序之后，计算派发中的每个线程负责构建树的一部分。通过观察两个相邻 Morton 码第一个不同的比特位，线程就能确定树中某个节点该在哪里分裂。这被称为**线性 BVH**（LBVH），它让整棵树可以在没有任何全局锁的情况下并行构建。

这个过程是「令人尴尬的并行」，能在短短几毫秒内为数百万个三角形构建出一棵 BVH。

== 八叉树

八叉树是一棵树，其中每个节点恰好有八个子节点，把空间划分成**卦限**（三维空间的八种自然划分，就像立方体的八个角）。对于流体模拟或**基于体素的渲染**这类需要快速找出空间哪部分被占据的场景，这是完美的结构。

=== 八叉树节点的构成

与子节点数量可变的 BVH 节点不同，纯粹的八叉树节点永远代表一个可以分成八个更小立方体的完美立方体。

[source,slang]
----
struct OctreeNode {
    uint childIndices[8]; // Indices to the eight octants
    float3 center;        // Center of the node's cube
    float  extent;        // Half-width of the node's cube
    uint   payload;       // User data (e.g., color, density, or material)
};
----

然而，每个节点存八个 32 位下标（32 字节）会非常占内存。实践中，开发者常用**基于指针的八叉树**：只存一个 `firstChildIndex`，并保证八个子节点在 `nodePool` 中连续存放。这样节点就缩减为一个下标加上几位元数据。

=== 构建策略：自顶向下与自底向上

*   **自底向上**：先把每个对象都当作叶节点，再用 `SubgroupMatch`（来自第 4 章）找出应当属于同一个父节点的对象。这很快，但需要复杂的排序。
*   **自顶向下**：从一个根节点开始，用全局原子操作按需「细分」节点。这更直观，但可能导致严重的内存竞争。

== 遍历树：栈与位域

树建好之后，怎么用它？在 C{pp} 里，你会写一个递归函数。而在 GPU 上，递归通常被禁止或性能很差，因为每个线程的调用栈只有有限的**私有内存**（寄存器）。

因此，我们改用**基于栈的遍历**或**无栈遍历**：

1.  **基于栈**：每个线程在寄存器或本地内存中维护自己的一个小数组，记录「待访问的节点」。这很快，但会消耗宝贵的寄存器，可能降低**占用率**（硬件能同时运行的活跃线程数）。
2.  **无栈（线索化树）**：每个节点存一个「跳过指针」，指向**深度优先搜索（DFS）**顺序中的下一个节点。如果光线错过了某个节点，只需沿着跳过指针前进，就能绕过该节点的所有子节点。这不需要任何栈空间，但会让树的构建过程更复杂。

== 实现挑战：内存瓶颈

在 GPU 上建树时最大的挑战是**内存管理**。在传统的 C{pp} 应用里，你会用 `malloc` 或 `new` 在需要时创建节点。而在计算着色器中，这些东西并不存在。

为什么？因为传统 CPU 的 `malloc` 使用**集中式堆管理器**，它依赖一把全局锁来防止不同线程抢占同一块内存。如果 10,000 个 GPU 线程同时试图调用 `malloc`，硬件就会把所有时间花在等锁上，导致性能大幅崩塌。

因此，我们必须预先分配一个**「节点池」**（一个大缓冲区），并用单个原子计数器从这个池中「分配」节点。每个需要节点的线程只需把计数器加一，再把结果当作自己在池中的唯一索引。

[source,slang]
----
// Simple node allocation using atomics
struct Node { ... };
RWStructuredBuffer<Node> nodePool;
RWStructuredBuffer<uint> nodeCounter;

uint allocateNode() {
    uint index;
    InterlockedAdd(nodeCounter[0], 1, index);
    return index;
}
----

这样做虽然可行，但如果成千上万个线程同时争抢同一个计数器，就会变慢。下一节我们会看到，**64 位原子操作**与**全局原子管理**如何针对超大规模优化这一过程。
