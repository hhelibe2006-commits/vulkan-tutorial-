= 占用率与延迟隐藏：让 GPU 保持忙碌

== 简介

上一节我们了解了工作组如何映射到 GPU 的工厂车间（计算单元或 SM）。但仅仅把一个工作组放进 CU 只是战斗的一半。如果这个工作组设计得不好，它可能只用到硬件潜力的一小部分，让昂贵的硅片闲在那里。

要理解这为什么会发生，我们必须谈**延迟**与**占用率**。

== 延迟鸿沟

GPU 是受内存带宽限制的。现代 GPU 每秒能执行数万亿次浮点运算（**TFLOPS**），但从 **VRAM**（显存）取一次数据却可能要几百甚至几千个时钟周期。

如果一批调用（一个 warp 或波前）需要读内存，它就必须等。如果那个 CU 只有一批可运行，整个 CU 就会静默下来，直到数据到达。这对性能是灾难，称为**内存延迟**。

GPU 的解决办法是**并发**。CU 不会干等一批，而是切换到另一批已就绪的调用。单个 CU 上「在飞」的批越多，你就越能掩盖访存的延迟。

== 定义占用率

**占用率**衡量的是一个 CU 上活跃的批数量相对理论最大值的比例，通常用百分比表示。

*   **100% 占用率**：CU 被批完全填满。每当一批在等内存，几乎肯定有另一批可以接上。
*   **低占用率**：只有少数批活跃。如果它们同时撞上访存，CU 就会停顿。

=== 资源限制与占用率压力

你可能想问：「为什么不干脆总是派发几千个线程？」问题在于每个计算单元都有固定的物理资源池。你加的每个线程都要消耗这个池的一部分。

限制占用率的三个主要因素：

1.  **寄存器**：每个线程都需要一组寄存器来存变量。如果你的着色器用了 128 个寄存器，能容纳的线程数就比只用 32 个时少。
2.  **共享内存（LDS）**：这块内存由整个工作组共享。如果你的工作组用了 32KB LDS 而 CU 只有 64KB，那不管工作组有多少线程，这个 CU 上最多只能放下两个工作组。
3.  **线程/warp 槽位**：硬件调度器同时能跟踪的线程数有硬上限（例如每个 CU 2048 个线程）。

|===
| 资源用量 | 对占用率的影响 | 结果

| 高寄存器用量
| **负面**
| 每个 CU 的批更少；更难掩盖延迟。

| 高 LDS 用量
| **负面**
| 每个 CU 的工作组更少；并发受限。

| 工作组尺寸偏小
| **中性/负面**
| 可能填不满所有 warp 槽位；还有调度开销。
|===

== 计算理论占用率

多数 GPU 厂商都提供工具（如 NVIDIA 的 Nsight 或 AMD 的 RGP）替你计算占用率。不过你也可以看着色器的资源用量自己估算。

如果一个 CU 有 64KB 共享内存，而你的工作组用了 32KB，那么这个 CU 任何时候最多只能容纳两个工作组。如果你的工作组很小（比如 64 个线程），每个 CU 就只有 128 个线程。若该硬件能跟踪 2048 个线程，你的占用率只有约 6%。

这就是为什么「胖」着色器（用大量寄存器或共享内存的着色器）往往性能不佳，除非经过细致的调优。

== 监控利用率

在真实引擎里，你不会只想靠猜。现代 Vulkan 引擎使用性能计数器（通过 `VK_KHR_performance_query` 扩展）实时监控硬件利用率。

通过跟踪 **ValuUtilization**（AMD）或 **SM Active**（NVIDIA）这类指标，你能看出内核是否真的让硬件保持忙碌。如果你看到内存延迟高、占用率却低，就说明需要优化寄存器用量或共享内存占用。
