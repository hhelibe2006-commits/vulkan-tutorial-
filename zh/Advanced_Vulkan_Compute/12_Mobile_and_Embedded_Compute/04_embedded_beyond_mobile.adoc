= 超越移动：嵌入式与无头计算

== Vulkan 设备的长尾

手机占据了头条，但 Vulkan 计算运行的**嵌入式**硬件世界要广阔得多。这些设备继承了移动端的约束——有限的功耗、共享内存、基于瓦片的 GPU、严苛的散热边界——同时又加上了自己的特点：没有显示器、实时截止时间、安全认证，以及以年甚至十年计的产品生命周期。本节梳理这片图景、它的工具链，以及你为高效面向它开发所需的环境。

== 嵌入式 Vulkan 计算的应用领域

*   **单板计算机（SBC）。** Raspberry Pi 4/5 在 VideoCore GPU 上提供了符合规范的 Vulkan 1.2+ 驱动（`v3dv`），还有无数 Arm 单板机搭载 Mali 或 Adreno 部件。它们在爱好者和边缘计算实验中很受欢迎。
*   **边缘 AI 模块。** NVIDIA Jetson、Qualcomm 机器人平台以及类似模块把一块性能不错的 GPU 与嵌入式 CPU 搭配在一起，专门用来在设备端运行推理和计算机视觉。
*   **汽车。** 信息娱乐系统、数字仪表盘和驾驶辅助系统越来越多地统一到 Vulkan 上，通常经由**安全关键** profile **Vulkan SC**（面向可认证系统的派生 API）。
*   **工业与机器人。** 机器视觉相机、激光雷达处理单元和机器人控制器使用 Vulkan 计算，在靠近传感器的地方做低延迟的传感器处理。
*   **数字标牌与机顶盒。** 长寿命、无风扇的设备，持续运行视频和图像处理管线。

== 为嵌入式目标搭建开发环境

移动端开发与通用嵌入式开发之间最大的差别是工具链：你通常要在性能强劲的 x86 主机上*交叉编译*，然后把生成的 ARM 二进制部署到目标设备。选对 IDE 和交叉编译方案，决定了你的迭代循环是以分钟计还是以天计。

=== 面向嵌入式与跨平台开发的 CLion

JetBrains 的 link:https://www.jetbrains.com/clion/[**CLion**]（https://www.jetbrains.com/clion/）是面向嵌入式与跨平台 Vulkan 工作最强大的 C{pp} IDE。它是商业软件，但提供 30 天试用，学生还能在 link:https://www.jetbrains.com/community/education/[jetbrains.com/community/education] 获取免费的教育许可证。

有两个 CLion 特性让它在嵌入式开发中格外有价值：

==== 远程开发（SSH）

CLion 的**远程开发**模式（CLion 2022.3 引入）让你通过 SSH *在目标设备上*（Raspberry Pi、Jetson 等）打开项目，而完整的 IDE 界面在本地运行。所有编辑、代码补全和调试都使用*设备上*的原生编译器和库，因此交叉编译工具链不匹配的问题就不存在了。启用方式：

1.  在 CLion 中选择 **File → Remote Development → SSH**。
2.  添加一条连接条目，填入目标设备的 IP 地址、SSH 端口（默认 22）和你的用户名。
3.  CLion 首次连接时会向设备上传一个小的服务器后端，然后在完整编辑器中打开远程项目。

设备至少要有几百兆字节的可用存储空间，并运行 64 位 ARM Linux。Raspberry Pi 5 和 Jetson 模块跑起来很轻松；装了完整 Raspberry Pi OS（64 位）的 Raspberry Pi 4 也可以。

==== 通过 CMake 工具链文件交叉编译

如果目标设备资源太紧张，跑不了远程开发——或者你要为裸机嵌入式操作系统构建——CLion 也支持带工具链文件的 **CMake 交叉编译**。你在主机上安装交叉编译器，然后让 CLion 指向一个 `CMakeToolchain-arm64.cmake` 文件：

[source,cmake]
----
# CMakeToolchain-aarch64-linux.cmake
# Install the toolchain on Ubuntu/Debian:  sudo apt install gcc-aarch64-linux-gnu g++-aarch64-linux-gnu

set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

set(CMAKE_C_COMPILER   aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)

# Point at sysroot if you have one from Raspberry Pi OS or the Jetson L4T rootfs.
# Leave these unset if you are relying solely on the cross-toolchain's default sysroot.
# set(CMAKE_SYSROOT /opt/sysroots/aarch64-rpi)

set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
----

在 CLion 中新增一个 **CMake 配置（profile）**（**Settings → Build, Execution, Deployment → CMake → +**），把 **CMake options** 设为 `-DCMAKE_TOOLCHAIN_FILE=/path/to/CMakeToolchain-aarch64-linux.cmake`，并在为目标构建时选中该配置。你可以另留一个配置用于本机 x86 构建，好在主机上迭代。

对于 32 位 ARM 目标（较老的 SBC、部分汽车 SoC），把 `aarch64-linux-gnu` 换成 `arm-linux-gnueabihf`。

== Raspberry Pi：Vulkan 计算环境配置

Raspberry Pi 4 和 5 运行 **v3dv** Vulkan 驱动，它是 Mesa 开源图形栈的一部分。从 Raspberry Pi OS（Bookworm，64 位）起，默认安装的 Mesa 版本已经足够新。先确认驱动是否存在：

[source,bash]
----
# On the Raspberry Pi (64-bit RPi OS Bookworm or later):
sudo apt update && sudo apt install -y mesa-vulkan-drivers vulkan-tools

# Confirm v3dv is recognized:
vulkaninfo --summary | grep driverName
# Expected output:  driverName = V3DV (Broadcom)
----

安装 Vulkan 开发头文件和验证层：

[source,bash]
----
sudo apt install -y \
    libvulkan-dev \
    vulkan-validationlayers \
    spirv-tools \
    glslang-tools      # provides glslangValidator
----

至于 `slangc`，从 link:https://github.com/shader-slang/slang/releases[github.com/shader-slang/slang/releases] 下载预编译的 Linux AArch64 发行版，放到你的 `PATH` 上。

=== Raspberry Pi 上的 Vulkan 限制

VideoCore VI GPU（Pi 4，Mesa 23.3+）支持 Vulkan 1.2；VideoCore VII（Pi 5，Mesa 24.0+）可达到 Vulkan 1.3。两者都有基于瓦片的硬件典型的紧约束：

*   `maxComputeWorkGroupInvocations`：**256**（Pi 4）/ **256**（Pi 5）
*   `maxComputeSharedMemorySize`：**16 384 字节**（16 KB）
*   子组大小：**16**（Pi 4——要查询，别写死）
*   Pi 4 上没有 `shaderInt64`；Pi 5 可能因固件版本而异

把 Android 那一节里所有防御性查询和工作组钳制的做法都用上。它们在这里同样重要。

=== 为 Raspberry Pi 构建计算应用（远程开发）

用 CLion 的远程开发连上 Pi 之后，工作流就是平常的 CMake 开发：

[source,bash]
----
# On the Raspberry Pi, in the project directory CLion opened remotely:
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
make -j4           # Pi 4 has 4 cores; -j4 saturates them
./my_headless_compute
----

CLion 的原生调试器（LLDB 或 GDB，取决于 Pi 上装了哪个）通过同一条 SSH 隧道工作——设置断点、查看 `VkResult` 值、单步调试命令缓冲区录制代码，和桌面上一模一样。

== NVIDIA Jetson：Vulkan 计算环境配置

NVIDIA Jetson 模块（Jetson Orin、Jetson AGX Xavier、Jetson Nano）随 **JetPack SDK** 一起运行 NVIDIA 专有的 Vulkan 驱动——它与 NVIDIA 移动端部件使用相同的底层 GPU IP，只是通过完整的 Vulkan 实现暴露出来。

=== 安装 JetPack SDK

从 link:https://developer.nvidia.com/embedded/jetpack[developer.nvidia.com/embedded/jetpack] 下载 **JetPack**。JetPack 是一个综合 SDK，包含：

*   **L4T（Linux for Tegra）**——Jetson 专用的、基于 Ubuntu 的操作系统镜像。
*   **CUDA**——NVIDIA 的 GPGPU 计算 API（在同一套硬件上与 Vulkan 并存运行）。
*   **cuDNN**——深度学习原语。
*   **TensorRT**——推理优化器。
*   **Vulkan 头文件与加载器**——从 JetPack 5.x 起包含在 L4T 中。

用 SDK Manager 工具（Windows/Linux 主机）为目标模块刷机，或者按 JetPack 文档中 Jetson 专用的刷机说明操作。刷机完成后确认 Vulkan：

[source,bash]
----
# On the Jetson:
vulkaninfo --summary | grep -E "driverName|apiVersion"
# Expected:  driverName = NVIDIA (or similar), apiVersion = 1.x
----

安装开发头文件：

[source,bash]
----
sudo apt install -y libvulkan-dev vulkan-validationlayers
----

=== 从 x86 主机为 Jetson 交叉编译

Jetson 是 64 位 ARM（aarch64）。你可以沿用 Raspberry Pi 那一节的 `CMakeToolchain-aarch64-linux.cmake`，只是把 sysroot 换成 Jetson 的 L4T sysroot，而不是 Raspberry Pi OS 的 sysroot。NVIDIA 提供了一个基于 Docker 的交叉编译环境，名为 **Jetson Linux Developer Guide**，它把完整的 L4T rootfs 和工具链打包在一起——请查阅 link:https://docs.nvidia.com/jetson/archives/l4t-archived/[docs.nvidia.com/jetson]，找到与你 JetPack 版本匹配的那一份。

另一种做法是：CLion 基于 SSH 的远程开发在 Jetson 上效果极好，因为这些模块足够快（Orin 上是 Cortex-A78AE），能轻松跑起 CLion 的服务端后端。

=== Jetson 上的 CUDA 与 Vulkan 互操作

Jetson 是少数几个**CUDA–Vulkan 互操作**（`VK_KHR_external_memory`、`VK_KHR_external_semaphore`）真正有用的嵌入式目标之一：你可以通过把 `VkDeviceMemory` 与 CUDA 的 `cudaExternalMemory_t` 共享，在同一个硬件引擎里对同一份数据运行 CUDA 内核和 Vulkan 计算内核。这支持渐进式迁移：把某一个阶段改写成 Vulkan 计算，管线其余部分仍留在 CUDA 里。NVIDIA 在 link:https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#interoperability-with-vulkan[CUDA 互操作指南] 中记录了这一点。

*   link:https://developer.nvidia.com/embedded/community/jetson-projects[Jetson AI 项目]——社区示例，其中许多在 TensorRT 之外还使用 Vulkan 计算。

== 无头计算：没有窗口，也没有表面

许多嵌入式系统的一个决定性特征就是**完全没有显示器**。好消息是 Vulkan 计算并不需要它。本教程系列里的一切——管线、描述符、派发——都可以在不创建 `VkSurfaceKHR` 或交换链的情况下工作。

要以无头方式运行，只需*省略*表面和呈现机制：

*   **不要**启用 `VK_KHR_surface`、`VK_KHR_swapchain`，或任何平台的 `*_surface` 扩展。
*   选择一个报告了 `VK_QUEUE_COMPUTE_BIT` 的队列族；你不需要呈现支持，所以完全跳过 `vkGetPhysicalDeviceSurfaceSupportKHR` 检查。
*   提交派发，并通过缓冲区回读结果，和前面 Android 回读示例里完全一样。

[source,cpp]
----
// Headless device: request a compute-capable queue, no surface/presentation needed.
uint32_t computeFamily = findQueueFamily(physicalDevice, VK_QUEUE_COMPUTE_BIT);

float priority = 1.0f;
VkDeviceQueueCreateInfo queueInfo{
    .sType            = VK_STRUCTURE_TYPE_DEVICE_QUEUE_CREATE_INFO,
    .queueFamilyIndex = computeFamily,
    .queueCount       = 1,
    .pQueuePriorities = &priority,
};
// No VK_KHR_swapchain in the enabled device extensions — pure compute.
----

上面这个 `findQueueFamily` 辅助函数值得展开写清楚，因为在嵌入式部件上，你常常想要一个*专用*的计算队列（不额外声明图形能力的那个），好让你的派发不和任何显示工作争抢：

[source,cpp]
----
uint32_t findQueueFamily(VkPhysicalDevice dev, VkQueueFlags required) {
    uint32_t count = 0;
    vkGetPhysicalDeviceQueueFamilyProperties(dev, &count, nullptr);
    std::vector<VkQueueFamilyProperties> families(count);
    vkGetPhysicalDeviceQueueFamilyProperties(dev, &count, families.data());

    // First pass: prefer a compute-only family (no graphics) to avoid contention.
    for (uint32_t i = 0; i < count; ++i) {
        const bool hasCompute  = families[i].queueFlags & VK_QUEUE_COMPUTE_BIT;
        const bool hasGraphics = families[i].queueFlags & VK_QUEUE_GRAPHICS_BIT;
        if (hasCompute && !hasGraphics) return i;
    }
    // Fallback: any family that satisfies the requirement.
    for (uint32_t i = 0; i < count; ++i)
        if ((families[i].queueFlags & required) == required) return i;

    throw std::runtime_error("no suitable compute queue family");
}
----

同一条无头路径，也适用于服务端计算节点、验证内核的 CI 运行器，或者没有屏幕的机器人控制器。

== 驱动与一致性：差异比桌面端更大

在嵌入式部件上，你不能假定最新的 Vulkan 版本，也不能假定可选项全都齐备：

*   始终把可选特性放在特性查询之后。几乎所有在售的嵌入式硬件（Raspberry Pi 4/5、NVIDIA Jetson JetPack ≥ 5.1、Android API 33+）都支持 Vulkan 1.3。你可能会在较老或高度专用的工业设备上遇到 Vulkan 1.1 或 1.2，但对任何新项目来说 1.3 都是合理的基线。
*   一些嵌入式驱动缺少你曾视为理所当然的可选能力，比如 `shaderInt64`、某些子组操作，或者**缓冲区设备地址（Buffer Device Address）**。提供回退路径，或者给出清晰信息优雅失败。
*   这里常见 Mesa 驱动（`v3dv`，以及用于软件回退的 `lavapipe`）；`lavapipe` 尤其是一个有用的、基于 CPU 的合规 Vulkan 实现，可在完全没有 GPU 的机器上测试计算。

由于 `lavapipe` 完全在 CPU 上运行，它非常适合作为 CI 关卡：即便构建机上没有 GPU，也能验证你的内核。你可以在启动无头应用之前，把 `VK_ICD_FILENAMES` 指向 Mesa 的软件 ICD，通过标准 Vulkan 加载器选中它：

[source,bash]
----
# Run the headless compute app against the CPU-based lavapipe driver.
export VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.x86_64.json
./my_headless_compute --validate
----

这样就能在 CI 里对*同一个二进制文件*做冒烟测试，而这个二进制正是要发到嵌入式设备上的——在真机稀缺时，这一点极其宝贵。

== 通过 clvk 与 OpenCL 实现可移植性

嵌入式厂商经常直接提供 OpenCL 栈，而不是手写一条 Vulkan 计算路径，在视觉和 ML 工具链里尤其如此。`clvk` 在 Vulkan 之上提供了符合规范的 OpenCL 3.0 运行时。这对嵌入式来说是一个强有力的可移植性方案：

*   一套按 OpenCL 编写的机器人或视觉代码库，只要链接 `clvk`，就能在任何只有 Vulkan 驱动的嵌入式设备上运行——不需要重写内核或主机代码。
*   反过来，如果你直接面向 Vulkan，`clspv` 让你可以把现有的 OpenCL C 内核当作 SPIR-V 在这些同样的设备上复用。

对嵌入式团队而言，这往往决定了某套现成算法库究竟能不能部署到只有 Vulkan 的 SoC 上。

=== 为嵌入式 Linux 构建 clvk

用上面交叉编译那一节的同一套 aarch64 工具链，在 x86 主机上交叉编译 `clvk`，然后把生成的库部署到设备：

[source,bash]
----
git clone --recursive https://github.com/kpet/clvk.git
cd clvk && mkdir build-arm64 && cd build-arm64

cmake .. \
    -G Ninja \
    -DCMAKE_BUILD_TYPE=Release \
    -DCMAKE_TOOLCHAIN_FILE=/path/to/CMakeToolchain-aarch64-linux.cmake \
    -DCLVK_COMPILER_AVAILABLE=OFF   # use pre-compiled SPIR-V; no clspv on device

ninja OpenCL

# Deploy to the target.
scp libOpenCL.so pi@raspberrypi.local:/usr/local/lib/
ssh pi@raspberrypi.local "sudo ldconfig"
----

如果要在设备上*本地*构建（在 Jetson 上很实际，在 Pi 上慢但可行），就去掉 `-DCMAKE_TOOLCHAIN_FILE` 参数：

[source,bash]
----
# On the Pi or Jetson directly:
git clone --recursive https://github.com/kpet/clvk.git
cd clvk && mkdir build && cd build
cmake .. -G Ninja -DCMAKE_BUILD_TYPE=Release -DCLVK_COMPILER_AVAILABLE=OFF
ninja OpenCL
sudo cp libOpenCL.so /usr/local/lib/ && sudo ldconfig
----

=== 用 clinfo 验证 clvk

`clinfo` 工具会列出系统上可见的每一个 OpenCL 平台和设备。部署 `libOpenCL.so` 之后，测试一下：

[source,bash]
----
# On the target device.
sudo apt install -y clinfo    # or build from source on older distros

LD_PRELOAD=/usr/local/lib/libOpenCL.so clinfo
----

成功的输出会显示一个名为 `clvk` 或 `Vulkan-backed OpenCL` 之类的平台，并带有一条 GPU 设备条目。如果看到「No platforms found」，请再确认 `libOpenCL.so` 位于链接器搜索路径上（`ldconfig -p | grep OpenCL`），并且已安装支持 Vulkan 的驱动（`vulkaninfo --summary` 必须先能成功运行）。

=== 在嵌入式 Linux 的 CMake 项目中集成 clvk

`libOpenCL.so` 部署好之后，在 CMake 项目里使用它很直接：

[source,cmake]
----
# In your project's CMakeLists.txt:
find_package(OpenCL REQUIRED)   # finds libOpenCL.so via pkg-config or find_library
target_link_libraries(my_vision_app OpenCL::OpenCL)
----

运行时要让 `LD_LIBRARY_PATH` 或 `ldconfig` 把 `libOpenCL.so` 解析到 `clvk` 库，而不是系统上可能同时存在的、厂商提供的 OpenCL 运行时。在 Jetson 上，NVIDIA 自带一套由 CUDA 支撑的 OpenCL，此时要有意识地选择加载哪个库：

[source,bash]
----
# Force clvk instead of the NVIDIA OpenCL runtime.
LD_PRELOAD=/usr/local/lib/clvk/libOpenCL.so ./my_vision_app
----

=== 在 Raspberry Pi 上通过 clvk 运行 OpenCL 内核——完整示例

下面这个端到端示例在 Raspberry Pi 5 上，通过由 `v3dv` Vulkan 驱动支撑的 `clvk`，运行一个 OpenCL 向量缩放内核。内核就是第 5 章里的那一个，没有任何 Pi 专属的内容。

*第 1 步：在主机上用 `clspv` 编译内核。*

[source,bash]
----
# On the x86 host (clspv is available for Linux x86-64):
clspv scale.cl -o scale.spv --spv-version=1.3
scp scale.spv pi@raspberrypi.local:~/my_app/
----

*第 2 步：在 Pi 上运行主机应用。*

[source,bash]
----
# Compile and run on the Pi (or cross-compile and scp the binary).
g++ -std=c++20 scale_host.cpp -o scale_app -lOpenCL
./scale_app scale.spv
----

*第 3 步：确认实际干活的是 Vulkan。*

在运行前启用 Vulkan 验证层，确认 `clvk` 是通过 `v3dv` 驱动转发调用的：

[source,bash]
----
VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation ./scale_app scale.spv 2>&1 | head -20
# If you see "VUID" messages, clvk is talking to Vulkan — no messages means all is clean.
----

== 实时性与安全性考量

许多嵌入式工作负载有硬性截止时间（激光雷达的一帧必须在下一帧到来前处理完），或者有安全义务（仪表盘绝不能卡死）：

*   优先使用**可预测**的派发规模，避免内核中出现迭代次数无上限、依赖数据的循环。
*   使用**时间线信号量**（第 8 章）构建确定性的、能感知截止时间的管线，而不是依赖 `vkQueueWaitIdle`。
*   在需要认证的场合，面向 **Vulkan SC**——它去掉了非确定性行为和运行时错误报告，改用经离线验证的确定性执行模型。Vulkan SC 规范发布在 link:https://www.khronos.org/vulkansc/[khronos.org/vulkansc]。
*   考虑设备的长生命周期：固定到某个已知驱动版本，并持续用它重新验证内核，因为现场更新可能很少甚至不可能。

== 小结

嵌入式 Vulkan 计算把移动端的思维方式延伸到一个没有屏幕的世界：单板计算机、边缘 AI 模块、汽车仪表盘和机器人控制器。对 Android 来说，完整的开发环境以 **Android Studio** 加 NDK 和 CMake 为中心，`clvk` 作为 `jniLibs` 共享库，`clspv` 离线编译内核。对 Raspberry Pi 和 Jetson 这类嵌入式 Linux 目标，用基于 SSH 的 **CLion 远程开发**获得接近原生的 IDE 迭代体验，或者为资源受限设备搭建 aarch64 交叉编译工具链。构建并部署 `clvk`，就能把任何 OpenCL 代码库移植到只有 Vulkan 驱动的环境，无需重写内核。只要省略表面和交换链就能**无头**运行；由于驱动覆盖面参差不齐，要以防御性方式查询能力；并用确定性的、能感知截止时间的管线来满足实时性和安全约束。本系列其余部分的计算技术在这里原样适用——只是它们必须生存在一个更紧、更长寿的边界之内。
