= 诊断与 AI 辅助计算优化：简介

== 概览

在这最后一章里，我们将探讨 Vulkan 计算开发的现代图景。随着内核越来越复杂、编排越来越精细，传统的调试与优化方法有时会显得力不从心。如果你写过一段时间计算着色器，就一定熟悉那种挫败感：代码编译通过，派发返回成功，但输出缓冲区里全是 0——更糟的是，整个系统卡死并报出 "Device Lost" 错误。

GPU 常被描述为一个"**黑盒**"——一个强大的处理器，能并行执行数百万次运算，却几乎不让你看见内部发生了什么。与 CPU 上的 C{pp} 代码不同，你无法轻易设置断点、逐行跟踪逻辑，也无法检查每个寄存器的状态。要构建健壮、高效的计算管线，我们需要一套新工具，以及看待开发流程的新方式。

== 诊断的两大支柱

为了揭开 GPU 的幕布，我们将重点介绍两种现代运行时验证技术：

*   **GPU 辅助验证（GAV）**：这是 Vulkan 验证层的一项强大功能。GAV 不只是检查你的 API 调用是否合法，它会在运行时把少量诊断代码直接注入你的着色器。这个过程称为**插桩**，让验证层能够发现那些原本完全不会被注意到的错误——从 **越界（OOB）** 缓冲区访问，到使用**缓冲区设备地址（BDA）** 时的非法指针解引用。
*   **着色器 printf**：我们将探讨如何在着色器里使用标准的 `printf` 逻辑，在成千上万个并行调用中"看"到变量的值。它看起来也许很原始，但在大规模并行环境里，这往往是追查细微逻辑错误的唯一办法。

== AI 辅助开发

最后，我们会看看**AI 辅助优化**这一新兴角色。**大语言模型（LLM）**——在海量代码上训练出来的 AI 模型——在理解着色器代码并给出对并行友好的重构建议方面，正变得越来越擅长。

无论你是在为向量化一个朴素的循环而发愁，还是在寻找更高效的**子组**模式（使用我们在第 4 章学过的 **Wave** 操作），AI 助手都可以成为开发过程中的有力伙伴。不过我们也会看到，有效使用 AI 的关键在于用本系列中掌握的**专业术语**与它"对话"——比如 **LDS（本地数据共享）**、**屏障**和**占用率**。

== 本章路线图

1.  **计算验证**：配置并使用 GPU 辅助验证来捕捉内存错误，以及用 `printf` 调试着色器。
2.  **助手主导的优化**：借助 AI 把朴素的计算内核重构成波感知的高性能模式。
