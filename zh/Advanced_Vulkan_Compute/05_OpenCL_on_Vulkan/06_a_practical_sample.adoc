= 实战示例：由 OpenCL 驱动的 Vulkan 渲染

前面几节介绍了 Vulkan 上 OpenCL 工具链中的两件工具：`clspv`（提前编译）和 `clvk`（运行时分层）。本节用一个实时、可交互的示例把它们串起来。

把框架设定讲清楚很重要。这**并不是**「一个恰好跑在 Vulkan 上的 OpenCL 程序」，恰恰相反：它是一个正常的 **Vulkan 应用**——窗口、交换链、呈现循环、自由飞行相机——只是**用 OpenCL 内核来绘制场景**。在默认模式下，内核由 `clspv` 编译，并作为 Vulkan 引擎自身的计算着色器运行，直接把结果写入用于呈现的缓冲区，没有任何拷贝。这正是分层生态的真正价值所在：Vulkan 引擎可以接入海量现有 OpenCL 内核，并把它们当作一等的着色器来运行。

完整源码位于 `attachments/compute`：

- `05_opencl_on_vulkan.cl` —— OpenCL C 内核（一个光线步进的*实例化森林*）
- `05_opencl_on_vulkan.cpp` —— 带窗口的 Vulkan 主机应用
- `CMakeLists.txt` —— 配置可选的 `clspv` 与 OpenCL 检测

这个场景是一堂关于实例化的小课：*单个*树的距离场在无限网格上重复（`round(p.xz / cell)`），而每个格子的哈希值赋予每个实例各自的高度、树冠大小、颜色，偶尔还留出一片空地。你用 `WASD`/`EQ` 和鼠标拖拽在其中实时穿行、环顾四周。

== 两种后端

应用可以通过任一后端驱动内核，后端在启动时选择（可用 `--backend=aot` 或 `--backend=clvk` 覆盖）：

[cols="1,3"]
|===
|后端 |OpenCL 内核如何到达屏幕

|**clspv AOT**（默认，零拷贝）
|OpenCL C 内核在构建时由 `clspv` 编译成 `forest.spv`，并作为 Vulkan 引擎*自己*的计算着色器运行。它直接写入用于呈现的 Vulkan 存储缓冲区——OpenCL 内核在 Vulkan 管线中就是字面意义上的「又一个着色器」，运行时没有拷贝，也没有第二个 API。

|**clvk 运行时**（`--backend=clvk`）
|同一个 `.cl` 文件在运行时由 `clvk` 编译并执行（分层在 Vulkan 之上的 OpenCL 3.0）。`clvk` 没有实现 `cl_khr_external_memory`，因此其结果需要通过每帧一次 `clEnqueueReadBuffer` 桥接进 Vulkan 缓冲区。它展示了运行时分层工具的价值，代价是每帧一次拷贝。
|===

== 内核作为 Vulkan 着色器（零拷贝）

默认路径是「Vulkan 使用 OpenCL」最干净的演示。因为 `clspv` 把 OpenCL C 内核变成了普通的 Vulkan SPIR-V，Vulkan 应用可以像加载任何计算着色器一样加载它，并把它指向即将呈现的缓冲区——内核把最终像素直接写入 Vulkan 拥有的内存：

[source,cpp]
----
// forest.spv was produced from 05_opencl_on_vulkan.cl by clspv at build time.
vk::PipelineShaderStageCreateInfo stage{
    .stage  = vk::ShaderStageFlagBits::eCompute,
    .module = *shaderModule,
    .pName  = "render"};               // clspv names the entry point after the kernel
// binding 0 = Params, binding 1 = the storage buffer that present() copies to screen
cb.dispatch((W + 15) / 16, (H + 15) / 16, 1);
----

这里没有互操作层，没有 FD 导出，也没有第二个设备：OpenCL 内核与引擎的其余部分运行在同一套 Vulkan 命令缓冲区流程中。

== clvk 运行时路径

为什么不用 `clvk` 也做零拷贝的缓冲区共享呢？因为主线 `clvk` 没有暴露 `cl_khr_external_memory`，所以无法把 `VkBuffer` 导入它的 OpenCL 上下文。于是运行时路径先计算到普通的 OpenCL 缓冲区，再每帧把它回读到 Vulkan 可见的内存中：

[source,cpp]
----
clEnqueueNDRangeKernel(queue, kernel, 2, nullptr, global, local, 0, nullptr, nullptr);
clEnqueueReadBuffer(queue, outMem, CL_TRUE, 0, bytes, hostMappedVkBuffer, 0, nullptr, nullptr);
// ... vkCmdCopyBufferToImage(vkBuffer -> intermediate) ; blit -> swapchain ; present
----

这就是当前工具链的现状：`clspv` 给你真正的零拷贝集成，而 `clvk` 让你无需改动 OpenCL 主机代码就能在运行时编译，代价是一次桥接拷贝。

== 可移植的内核

这个内核仍然遵循前面几节的可移植性规则，因此它的描述符映射是确定的，并且在两种后端上都能不加修改地运行：

[source,c]
----
typedef struct {
    int   width, height;
    float camX, camY, camZ;     // free-fly camera position
    float camYaw, camPitch, fog;
} Params;

#define MAX_STEPS 128           // compile-time constant — see the note below

__attribute__((reqd_work_group_size(16, 16, 1)))
__kernel void render(__global const Params* P, __global uint* outRGBA) {
    const int x = get_global_id(0), y = get_global_id(1);
    if (x >= P->width || y >= P->height) return;     // guard the rounded-up global size
    for (int i = 0; i < MAX_STEPS; ++i) { /* raymarch the instanced-forest SDF */ }
    // ... shade, then:
    outRGBA[y * P->width + x] = r | (g << 8) | (b << 16) | (0xFFu << 24);
}
----

[NOTE]
====
光线步进的步数是**编译期常量**，而不是内核参数。`clspv` 会把循环边界从存储缓冲区加载的光线步进循环编译错——它的结构化控制流处理过程无法证明循环会终止，生成的着色器会让 GPU 挂起。原生 OpenCL 驱动能正常编译同样的动态边界，所以这是一个值得了解的可移植性陷阱：打算通过 `clspv`/`clvk` 运行的内核，请让循环边界保持常量。
====

*   **只用缓冲区参数** → `clspv` 把两个 `__global` 指针映射到可预测的布局（`set=0,binding=0` 是 Params，`set=0,binding=1` 是输出），AOT 路径手工构建的 `VkDescriptorSetLayout` 与之完全匹配。
*   **`uint` 输出**（打包的 RGBA8）让所有访问都保持在 32 位存储访问之内，因此不需要特殊的 8 位存储 Vulkan 特性。
*   **固定工作组大小**，再加上主机端的向上取整，可以让 NDRange 保持均匀。
*   **没有跨调用的状态**——每个调用只对一个像素做光线步进——因此同一个内核在两种后端上都能不加修改地运行（两者之间的任何差异只是两块不同 GPU 之间的浮点舍入差异）。

用 `WASD`（移动）、`E`/`Q`（上升/下降）、鼠标拖拽（环顾）、`Shift`（加速）、`R`（重置）、`ESC`（退出）在森林中穿行。使用默认后端时，你看到的每个像素都由以 Vulkan 引擎自身计算着色器运行的 OpenCL 内核生成——没有拷贝，没有第二个 API。
