= 交叉编译：为 Arm 生态构建
:pp: {plus}{plus}
:stem: latexmath

你在一台性能强劲的 x86_64 工作站上开发，它有 128GB 内存和一块水冷 GPU。而你的目标是一台 **Raspberry Pi 5** 或 **NVIDIA Jetson**——ARM64 处理器，资源只有工作站的零头。你当然可以试着把 Vulkan C{pp} 代码直接放在设备上编译，但你很快会发现：在微型计算机上构建 ONNX Runtime 这样的大项目，或者一套复杂的 Vulkan 引擎，等于自找灾难。

如果你尝试本地构建，就会撞上**内存抖动**——系统花在把内存页换到慢速 SD 卡上的时间，比真正编译代码的时间还多。最终 Linux 的**内存耗尽（OOM）杀手**会醒来，杀掉你的编译器以免系统卡死。就算侥幸成功，你也要等上 8 小时，而工作站 2 分钟就能搞定。

**交叉编译**才是专业的解法。它让你用工作站的「蛮力」为一种完全不同的架构生成二进制代码。

本章我们要揭开交叉编译过程的神秘面纱：学会搭好 **Sysroot**、配置 link:https://cmake.org/cmake/help/latest/manual/cmake-toolchains.7.html[**CMake 工具链**]，并构建一条用起来和本地开发一样顺滑的远程部署流水线。

有一点很重要：大多数 OEM 都会提供下面讲到的这些内容，如果可能，你应当使用它们预构建的工具链和 sysroot，以免自己搭建的复杂性。不过，如果你面对的是定制或非标准的 ARM 设备，你可能需要自建工具链与 sysroot；弄懂它如何运作，你才能明白一套开发环境该给你什么。

为了避免把事情弄得更复杂，我们不深入具体 IDE 的配置——可用的 IDE 很多，各有各的怪癖和配置陷阱。下面描述的核心路径在某种程度上对它们都是通用的。

== 两个世界的问题：主机与目标

在交叉编译中，你同时生活在两个世界里：
1.  **构建主机**：你的 x86_64 Linux/Windows 机器，编译器（`gcc` 或 `clang`）真正运行的地方。
2.  **目标主机**：生成的二进制代码将要执行的 ARM64 设备。

.交叉编译生态
image::images/ML_Inference/Embedded_Applications/cross_compilation_architecture.svg[示意图：构建主机、目标主机与 sysroot 镜像之间的关系, 800]

初学者最常犯的错误，是拿构建主机的库去链接。如果你的 ARM 代码链接了 x86 的 `libvulkan.so`，链接器要么一头雾水地报错（「File format not recognized」），要么产出一个二进制文件，在第一次调用 Vulkan 时就以「Invalid Instruction」错误崩溃。

你必须在**工具**（运行在 x86 上）与**库**（必须是 ARM）之间保持严格分离。编译器是工具；`.so` 文件是库。

== 支柱 1：Sysroot（目标系统的倒影）

**Sysroot** 是构建主机上的一个文件夹，里面是目标主机文件系统的完整副本，包含 ARM 设备用到的每一个头文件（`.h`）与库（`.so`）。

=== 用 `rsync` 创建 Sysroot
不要从网上下载来路不明的库。最好的 sysroot 直接来自你的硬件。我们用 `rsync` 把目标操作系统的「五脏六腑」克隆过来。

[source,bash]
----
# On your development machine
mkdir -p ~/target_sysroot

# Pull the vital organs of the target OS
# -a: Archive mode (preserves permissions and timestamps)
# -v: Verbose output so you can see the progress
# -z: Compress data during transfer to save network bandwidth
# -L: CRITICAL - Transforms absolute symlinks into relative ones.
# On Linux, /usr/lib/libvulkan.so often points to /lib/aarch64-linux-gnu/libvulkan.so.1
# Without -L, that link would point to your workstation's root, not the sysroot!
rsync -avzL --rsync-path="sudo rsync" \
    pi@raspberrypi.local:/lib/aarch64-linux-gnu ~/target_sysroot/
rsync -avzL --rsync-path="sudo rsync" \
    pi@raspberrypi.local:/usr/include ~/target_sysroot/usr/
rsync -avzL --rsync-path="sudo rsync" \
    pi@raspberrypi.local:/usr/lib/aarch64-linux-gnu ~/target_sysroot/usr/lib/
----

=== 深入：链接器的搜索路径
在 Linux 上，许多 `.so` 文件其实是文本脚本（链接器脚本），或者包含绝对路径。例如 `/usr/lib/aarch64-linux-gnu/libpthread.so` 常常就是一个文本文件，内容为：
`GROUP ( /lib/aarch64-linux-gnu/libpthread.so.0  /usr/lib/aarch64-linux-gnu/libpthread_nonshared.a )`

交叉编译时，那个 `/lib/...` 路径指向的是**主机**的根目录，而不是 **sysroot** 的根目录。这会导致链接失败，因为你工作站上的 `libpthread.so.0` 是 x86 二进制。

**解决办法**：在编译器里用 `--sysroot` 参数告诉链接器：「每当你在链接器脚本或库搜索中看到绝对路径，先给它加上 `~/target_sysroot` 前缀。」

=== 符号链接的疑难排查
基于 `rsync` 的 sysroot 有一个常见故障点：断裂的符号链接。在目标设备上，`/usr/lib/libvulkan.so` 可能指向 `../../lib/aarch64-linux-gnu/libvulkan.so.1.2.3`。如果 `rsync` 不带 `-L` 参数，你复制到的就是一个「悬空」链接，指向你工作站上并不存在的路径。

即便加了 `-L`，仍可能有绝对符号链接混进来。你可以用 `symlinks` 这类工具修掉它们：
[source,bash]
----
sudo apt install symlinks
# Convert all absolute symlinks to relative ones within the sysroot
symlinks -cr ~/target_sysroot
----

== 支柱 2：Docker 的优势（可复现的熔炉）

在本地机器上搭 sysroot 确实能用，但很脆弱。一旦你更新了工作站的系统，交叉编译器可能跟着换版本，破坏与目标 GLIBC 的兼容性。

**Docker** 让你能造一座「冻结的熔炉」，对团队里每个开发者都一模一样。它还通过提供一致的环境，简化了 link:https://docs.docker.com/build/building/multi-platform/[多架构构建] 的管理。

=== 多架构 Dockerfile
我们可以创建一个 Docker 镜像，把交叉编译器和预配置好的 sysroot 都装进去。

[source,dockerfile]
----
# Dockerfile.cross
FROM ubuntu:22.04

# 1. Install the cross-compilation tools
RUN apt-get update && apt-get install -y \
    build-essential \
    cmake \
    git \
    pkg-config \
    g++-aarch64-linux-gnu \
    rsync \
    && rm -rf /var/lib/apt/lists/*

# 2. Define the sysroot location
ENV SYSROOT=/opt/sysroot
RUN mkdir -p ${SYSROOT}

# (Optional) You can copy a pre-built sysroot into the image
# COPY ./target_sysroot ${SYSROOT}

# 3. Set up environment for CMake
ENV ARCH=aarch64
ENV CROSS_COMPILE=aarch64-linux-gnu-
----

=== 在 Docker 里构建
你可以把源码挂载进容器里构建，而不「污染」你的工作站。

[source,bash]
----
docker build -t vulkan-cross-builder -f Dockerfile.cross .
docker run --rm -v $(pwd):/src -w /src vulkan-cross-builder \
    cmake -B build-arm64 -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-toolchain.cmake .
----

== 支柱 3：CMake 工具链文件

除非你告诉 CMake，否则它并不「知道」你在交叉编译。我们用一个**工具链文件**把 CMake 从工作站的系统目录引向你的 Sysroot。

[source,cmake]
----
# cmake/aarch64-toolchain.cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)

# 1. Point to the ARM cross-compiler
# You can install this on Ubuntu via: sudo apt install g++-aarch64-linux-gnu
set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)

# 2. Point to our local Sysroot mirror
# We use an environment variable so the path can be different in Docker vs Local
if(NOT DEFINED ENV{SYSROOT})
    set(CMAKE_SYSROOT $ENV{HOME}/target_sysroot)
else()
    set(CMAKE_SYSROOT $ENV{SYSROOT})
endif()

# 3. CRITICAL: Don't look for libraries on the workstation host!
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER) # Use workstation's 'make', 'ls', 'cmake'
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)  # ONLY look in sysroot for libraries
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)  # ONLY look in sysroot for headers
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)  # ONLY look in sysroot for cmake-packages

# 4. Handle Pkg-Config for ARM
# Pkg-config is the most common cause of "Header not found" errors.
# We must prevent it from returning paths like /usr/include (which is your x86 host).
set(ENV{PKG_CONFIG_DIR} "")
set(ENV{PKG_CONFIG_LIBDIR} "${CMAKE_SYSROOT}/usr/lib/aarch64-linux-gnu/pkgconfig:${CMAKE_SYSROOT}/usr/share/pkgconfig")
set(ENV{PKG_CONFIG_SYSROOT_DIR} "${CMAKE_SYSROOT}")

# 5. Staging: Where do we 'install' our ARM binaries?
set(CMAKE_STAGING_PREFIX $ENV{HOME}/arm64_build_output)
----

== 支柱 4：处理 Vulkan SDK

为 Vulkan 交叉编译时，你需要两样东西：
1.  **Vulkan 头文件**：它们与架构无关，可以直接用主机上的。
2.  **Vulkan 加载器（`libvulkan.so`）**：它必须是从 sysroot 里来的 ARM 版本。

=== 正确地找到 Vulkan
在你的 `CMakeLists.txt` 里别写死路径，用 `find_package(Vulkan REQUIRED)`。由于我们在工具链里设置了 `CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY`，CMake 会自动跳过主机的 Vulkan，找到 sysroot 里的那一份。

[source,cmake]
----
find_package(Vulkan REQUIRED)
add_executable(vulkan_ml_app main.cpp)
target_link_libraries(vulkan_ml_app PRIVATE Vulkan::Vulkan)
----

=== 验证
构建完成后，用 `readelf` 确认你的二进制确实是 ARM64 而不是 x86：
[source,bash]
----
readelf -h build-arm64/vulkan_ml_app | grep Machine
# Should output: Machine: AArch64
----

== 支柱 5：针对 CPU 的优化

ARM 是一个庞大的处理器家族。为通用「ARM64」编译的二进制能在 Raspberry Pi 5 上运行，但会很慢，因为它没有用到让 Pi 5 变快的那些专用硬件指令。

=== 调校编译参数
要拿到生产级性能，你应该在 CMake 构建中加入针对具体架构的参数。这些参数会启用 NEON SIMD 或点积指令之类的芯片特性。可用参数的完整列表见 link:https://gcc.gnu.org/onlinedocs/gcc/AArch64-Options.html[GCC AArch64 选项] 文档。

[cols="1,2,2"]
|===
| 目标 SoC | `-march`（架构） | `-mtune`（调优）

| Raspberry Pi 4 | `armv8-a+crc` | `cortex-a72`
| Raspberry Pi 5 | `armv8.2-a+fp16+rcpc+dotprod` | `cortex-a76`
| NVIDIA Jetson Orin | `armv8.2-a+fp16` | `cortex-a78ae`
| Apple Silicon（M1/M2） | `armv8.5-a+fp16+sha3` | `apple-m1`
|===

*   **`+fp16`**：启用对半精度浮点的硬件支持。这是 Vulkan ML 最重要的单个参数，它让着色器吞吐量翻倍，并降低寄存器压力。
*   **`+dotprod`**：启用整数点积的专用指令（UDOT/SDOT），这对 INT8 量化模型至关重要。

[source,cmake]
----
if(CMAKE_SYSTEM_PROCESSOR STREQUAL "aarch64")
    # Tell the compiler exactly which silicon we are targeting
    # Note: Using -mcpu is often a shorthand for -march + -mtune
    add_compile_options(-march=armv8.2-a+fp16+dotprod -mtune=cortex-a76)
endif()
----

== 支柱 6：管理 GLIBC 兼容性

嵌入式 Linux 上最常见、也最令人抓狂的运行时错误是：
`./app: /lib/aarch64-linux-gnu/libc.so.6: version 'GLIBC_2.34' not found`

*   **成因**：你编译时所用的 Sysroot 里的 C 库（GLIBC）版本，比实际硬件上运行的版本更新。GLIBC 向后兼容，但不向前兼容。
*   **规则**：针对**较旧** GLIBC 编译的二进制永远可以在**较新**的系统上运行，反之绝不行。
*   **专家提示**：如果你在为较老的 Debian/Ubuntu 发行版（比如 JetPack 4.x）开发，就用基于较老 Ubuntu 版本（比如 18.04）的 Docker 镜像，确保你的交叉编译器链接到较旧的 GLIBC。

== 支柱 7：远程部署与调试

专业的嵌入式工作流是：**编码 latexmath:[\to] 构建 latexmath:[\to] 部署 latexmath:[\to] 运行**，全部在 IDE 里一键完成。

=== 用 SSH 密钥实现自动化部署
别每次构建都手打密码，那会打断你的创作心流。在工作站上生成 SSH 密钥并复制到目标设备：

[source,bash]
----
ssh-keygen -t ed25519
ssh-copy-id pi@raspberrypi.local
----

现在你可以用部署脚本在毫秒内同步二进制文件。部署时用 `rsync` 比 `scp` 更好，因为它只传输真正发生变化的字节。

[source,bash]
----
#!/bin/bash
# deploy.sh
set -e

TARGET="pi@192.168.1.50"
DEPLOY_DIR="~/edge_ai"

# 1. Build the project locally
cmake -B build-arm64 -DCMAKE_TOOLCHAIN_FILE=cmake/aarch64-toolchain.cmake .
cmake --build build-arm64 -j$(nproc)

# 2. Sync to the target (Only transfers changed files)
rsync -avz build-arm64/vulkan_ml_app $TARGET:$DEPLOY_DIR/

# 3. Remote Execution
ssh $TARGET "$DEPLOY_DIR/vulkan_ml_app --model $DEPLOY_DIR/resnet.onnx"
----

=== 深入：用 GDB 远程调试
你可以用工作站的高分辨率显示器与 IDE 逐行调试 ARM 代码，而代码实际跑在那颗小小的处理器上。

1.  **在目标设备（ARM 机器）上**：
    启动 **GDB Server**。它相当于处理器的「遥控器」。
    [source,bash]
    ----
    # Listen on port 1234
    gdbserver :1234 ./vulkan_ml_app --model resnet.onnx
    ----

2.  **在主机（你的工作站）上**：
    启动 `gdb-multiarch`。你必须把它指向二进制的**本地副本**（带调试符号）和 **sysroot**。
    [source,bash]
    ----
    gdb-multiarch ./build-arm64/vulkan_ml_app
    (gdb) set sysroot ~/target_sysroot
    (gdb) target remote 192.168.1.50:1234
    (gdb) continue
    ----

== 支柱 8：运行时搜索路径（RPATH）

当你在 Sysroot 里链接 `libonnxruntime.so` 这样的库时，链接器会记录路径 `~/target_sysroot/usr/lib/...`。但在 Pi 上，这个库位于 `/usr/lib/...`。

*   **问题**：应用可能按构建主机的路径去找库，结果以「找不到共享库」错误启动失败。
*   **解决办法**：使用 `CMAKE_INSTALL_RPATH`。它会把一条搜索路径嵌进二进制的头部。

[source,cmake]
----
# Tell the app to look in its own folder ($ORIGIN)
# and the standard system folders on the target.
set(CMAKE_INSTALL_RPATH "$ORIGIN;/usr/lib/aarch64-linux-gnu")

# Ensure RPATH is not cleared during installation
set(CMAKE_INSTALL_RPATH_USE_LINK_PATH TRUE)
----

== 小结：交叉编译检查清单

1.  **熔炉**：在主机上或 Docker 容器里装好 `g++-aarch64-linux-gnu` 交叉编译器。
2.  **镜像**：用 `rsync` 新鲜拉取目标的 `/usr/include` 与 `/usr/lib`，并把绝对符号链接解析掉。
3.  **指南**：一份设置 `CMAKE_SYSROOT`、重定向 `pkg-config`、配置 `CMAKE_FIND_ROOT_PATH_MODE_*` 的工具链文件。
4.  **优化**：针对具体芯片代际的架构相关 `-march` 与 `-mtune` 参数（例如 `+fp16`）。
5.  **握手**：配置好 ed25519 SSH 密钥，实现免密、快速的部署。
6.  **显微镜**：目标上跑 `gdbserver`，工作站上跑 `gdb-multiarch`。

交叉编译是专业嵌入式开发的「入场费」。付过这笔钱，你就能把一台水冷工作站的全部力量，聚焦到一小片高效能的芯片上。
