= 嵌入式应用：边缘侧的 AI
:pp: {plus}{plus}
:stem: latexmath

你已经构建出一台高性能推理引擎。你掌握了量化、厂商专用的矩阵硬件，以及内存别名分配器。在你的开发工作站上，模型跑到 500 FPS，GPU 风扇几乎都不转。但现在，任务变了：你要把同一个模型部署到**无人机**、**VR 头显**，或者用螺栓固定在工厂天花板上的**工业智能相机**上。

欢迎来到**嵌入式系统**的世界。

在这一节，我们从「资源无限」的世界走进**有限约束**的世界。在桌面世界，着色器慢了，用户会买更好的 GPU，或者调低设置。在嵌入式的世界里，没有「更好的 GPU」——只有已经焊在板子上的那块芯片。代码效率不达标，设备就会过热、电池会耗尽，或者机器人会真的撞上去。

这是 Vulkan ML 之旅的最后一片疆域。我们要学会做到「精简、强悍、可确定」。

== 边缘侧毫不留情的现实

嵌入式开发不只是「给更小的电脑写代码」，而是工程优先级的根本转变。在服务器环境里，你优化的是**吞吐量**（每秒多少请求）。在移动环境里，你优化的是**延迟**（用户多快看到响应）。在关键任务的嵌入式环境里，你优化的是**韧性**与**资源效率**。

作为一名专业人士，你必须在四大相互交织的支柱之间游走，它们决定了一个边缘产品的成败。

=== 1. 功耗：能量预算

在桌面上，我们用**每秒帧数（FPS）**衡量成败。在电池供电的无人机或可穿戴医疗设备上，我们用**每次推理的焦耳数**衡量成败。每一次晶体管翻转都要消耗能量。相机与 GPU 之间每一次多余的拷贝，都是白白损失的毫秒飞行时间。

[latexmath]
++++
\text{Intelligence Density} = \frac{\text{Successful Inferences}}{\text{Total Energy Consumed (Joules)}}
++++

*（注：智能密度并不是标准 SI 单位，但对边缘 AI 工程师来说，它是一个至关重要的概念指标，用来比较不同模型与硬件路径的效率。）*

如果你的 Vulkan ML 引擎功耗是 15W，你的无人机十分钟就会从天上掉下来。如果你用本节的技术把它优化到 3W，你就有了一个小时的续航任务。功耗优化不只是「省钱」——它让**不可能的任务**成为可能。

我们必须考虑：
* **静态功耗（漏电）**：仅仅是设备开机这一状态就要消耗的能量。
* **动态功耗**：计算过程中翻转晶体管所消耗的能量。Vulkan 允许我们通过减少多余的状态切换、优化着色器指令来把它降到最低。
* **「跑完就睡」策略**：尽快把活干完，好让 GPU 进入低功耗状态，而不是慢慢磨、让供电轨一直「热」着。

=== 2. 散热：硅的天花板

嵌入式设备常常被封在无风扇的 IP67 防水外壳里，只能依靠被动散热。如果你的 ML 模型让 GPU 以 100% 占空比运行，SoC 温度就会一路升到**热跳变点**（通常在 85°C 到 105°C 之间，取决于 SoC）。到了那一刻，硬件会「硬降频」——毫无预警地把时钟频率砍掉 50% 甚至更多。

对实时 VR 应用来说，这种降频就像从 90 FPS 突然掉到 15 FPS，令人不适，还会立刻引发晕动症。你必须学会实现**散热感知推理**。这包括：
* **动态分辨率缩放（DRS）**：设备发热时缩小 ML 模型的输入尺寸。
* **模型切换**：散热余量不足时，把笨重的高精度模型换成「轻量」版本。
* **占空比管理**：在推理之间刻意插入「休息」时段，让热量散出去。

=== 3. 确定性：99.9 分位

在自动驾驶汽车或机器人平台上，「平均延迟」是一个危险的指标。如果你的模型平均耗时 10ms，但每分钟有一次因为操作系统决定去索引文件系统、或者驱动做了一次「世界暂停」式垃圾回收而耗时 200ms，那这个系统从根本上就是不安全的。

我们优化的是**尾部延迟**（99.9 分位）。在 Vulkan 中，这意味着掌握**显式同步**。我们不指望驱动「做对的事」，而是使用：
* **栅栏与信号量**：精确控制 GPU 相对于 CPU 何时开始、何时结束工作。
* **时间线信号量**：用于复杂的多队列同步，避免管线中出现「气泡」。
* **实时调度**：与 Linux 的 link:https://man7.org/linux/man-pages/man7/sched.7.html[`SCHED_FIFO` 或 `SCHED_RR`] 打交道，确保 ML 线程不会被后台任务抢占。

=== 4. 统一内存：UMA 的优势

与通过低速 PCIe 总线连接独立显存的桌面不同，大多数嵌入式 SoC（ARM Mali、Qualcomm Adreno、Apple Silicon、NVIDIA Jetson）采用**统一内存架构（Unified Memory Architecture，UMA）**。CPU 与 GPU 共享同一块物理内存。

这是你最大的竞争优势。如果你用 `dmabuf` 正确管理内存，就能把数据从相机传感器搬到 ML 引擎，做到**零拷贝**。大多数开发者在多余的传输上浪费了 30% 的性能；你将学会如何彻底绕开这些传输。

[cols="1,1"]
|===
| 独立 GPU（桌面） | 统一内存（嵌入式）

| CPU 内存 latexmath:[\to] PCIe latexmath:[\to] GPU 显存 | 共享内存（CPU 与 GPU 访问同一批物理页）
| 高延迟传输 | 零延迟（传递指针）
| 高功耗的 PCIe 总线 | 高能效的内部互连
| 各自独立的内存池 | 共享内存池（需要小心管理）
|===

== 嵌入式软件生态

为嵌入式构建，需要理解的不只是 Vulkan。你面对的是一个「垂直堆栈」式的软件体系。

1.  **芯片（硬件）**：物理的 ARM 核心、GPU 集群，以及专用的 NPU（神经网络处理单元）。
2.  **内核（Linux/Android/QNX）**：管理内存、调度与设备驱动。link:https://docs.kernel.org/driver-api/dma-buf.html[`dmabuf`] 与 link:https://docs.kernel.org/userspace-api/media/v4l/v4l2.html[V4L2] 就住在这里。
3.  **驱动（Vulkan 实现）**：由 SoC 厂商（ARM、Qualcomm、NVIDIA、Broadcom）提供。它们常常是闭源的，并且有各自的怪癖。
4.  **加载器（`libvulkan.so`）**：你的应用与驱动之间的桥梁。
5.  **你的应用**：我们在本书中一路构建的 ML 引擎。

在这一节，我们会花很多时间待在这套堆栈的「地下室」——与内核和驱动打交道，把硬件的每一滴性能都榨出来。

== 硬件典型形态

并非所有嵌入式系统都生而平等。我们通常按性能把它们分为三个「层级」：

*   **第 1 层：单板计算机（SBC）**：比如 **Raspberry Pi 5**。它们是通用 Linux 机器，GPU 尚可，但缺少专用的 AI 加速器。在这类设备上，Vulkan 是获得高性能 ML 的*唯一*途径。
*   **第 2 层：边缘 AI 模块**：比如 **NVIDIA Jetson Orin**。它们拥有强大的 GPU 算力和专用的 Tensor Core。在这里，Vulkan 要与 CUDA 竞争，但 Vulkan 在不同厂商之间的可移植性更好。OpenCL 和 SYCL 对这些设备也是可行选项；但它们没有开箱即用的图形能力，而这往往是 Jetson 项目所需要的。
*   **第 3 层：移动/可穿戴 SoC**：比如 **Qualcomm Snapdragon** 或 **MediaTek Dimensity**。它们把功耗优化放在一切之上，通常有严格的热限制，Vulkan 驱动也非常复杂，扩展众多。

== 为什么 Vulkan 是边缘的秘密武器

像 TensorFlow Lite 或 ONNX Runtime 这样的高层框架非常适合快速原型开发，但它们往往把 GPU 当成一个「黑盒」。直接使用 Vulkan，你就能获得高层用户甚至不知道存在的「硬件超能力」：

*   **直接 DMA 访问**：你可以借助特殊的 Linux 内核句柄，把原始相机传感器直接喂给计算着色器。
*   **显式工作组调优**：你可以把着色器工作组调到与特定芯片上**执行单元（EU）**或**计算单元（CU）**的数量完全匹配。
*   **异步流水线**：你可以把 ML 的「思考」时间藏进图形管线的「显示」时间里，让 AI 实际上不占一毫秒的帧预算。
*   **多队列执行**：让 ML 跑在专用的「计算队列」上，同时由「图形队列」处理 UI，避免繁重推理期间 UI 卡顿。
