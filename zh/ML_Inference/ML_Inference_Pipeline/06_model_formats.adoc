= 模型格式

在学习机器学习的过程中，你会不断遇到这样的场景：你用 PyTorch 训练出了一个漂亮的模型。它运行得很好。现在你需要把它部署到 Android 手机上，集成进一个基于 Vulkan 的游戏引擎，也许还要在服务器上跑一份。每种环境都有各自的约束、各自的硬件、各自的优化需求。

你打算为每个平台单独维护一套实现吗？还是用不同的框架重写你的模型？你又如何确保它们都产生相同的结果？

这正是模型格式要解决的问题。它们是训练与部署之间的桥梁，是框架与硬件之间的桥梁，是研究与生产之间的桥梁。理解模型格式，是做好实际 ML 推理工作的必备前提。

== 巴别塔问题

在深度学习的早期（说来令人惊讶，那不过是大约十年前的事），每个框架都有自己表示模型的方式。这种碎片化引发了一场危机，几乎拖慢了整个领域的前进步伐。

=== 框架大爆发

大约在 2015 至 2017 年，深度学习的人气急剧上升。转眼之间涌现出几十个框架，每个都有自己的理念与做法：

*TensorFlow*（Google，2015）：围绕静态计算图构建。你先定义模型结构，然后执行它。非常适合生产部署与优化，但静态图让调试和实验变得更难。

*PyTorch*（Facebook，2016）：围绕动态计算图（边运行边定义，define-by-run）构建。你在执行的同时构建图，调试直观，实验也快。研究人员很喜欢它，但最初的部署颇具挑战。

*Caffe*（Berkeley，2014）：最早流行的框架之一，专注于计算机视觉。用 prototxt 文件定义模型——人类可读，但相当冗长。很适合 CNN，对其它架构则不够灵活。

*MXNet*（Apache，2015）：为效率与可扩展性而设计，支持多种语言。用自己的基于 JSON 的格式做模型序列化。

*Theano*（Montreal，2007）：现代框架的鼻祖，开创了自动微分。用 Python pickle 做序列化，这种方式既脆弱又只适用于 Python。

每个框架都有长处，研究人员自然会针对不同任务选用不同工具。但这给部署带来了巨大的麻烦。

=== 锁定问题

设想下面这个场景——它已经在全世界的公司里上演过成千上万次：

你的研究团队用 PyTorch 训练出一个最先进的模型。在你们的任务上达到 95% 的准确率——比以往任何结果都好。他们满怀期待，准备部署。

但你们的生产基础设施是建立在 TensorFlow 上的。你的部署流水线、监控工具、优化工作流，全都假定输入是 TensorFlow 模型。你的移动应用用的是 TensorFlow Lite。你的边缘设备运行的是 TensorFlow Lite for Microcontrollers。

你该怎么办？

*方案 1：用 TensorFlow 重新实现*。这意味着把 PyTorch 里的每一层、每一个运算、每一个细节手动搬到 TensorFlow。这要花上几周。你引入 bug。TensorFlow 版本只达到 92% 的准确率，而不是 95%——转换过程中有东西丢了，但丢的是什么呢？你又花几周调试。等你做完，研究团队已经转向更好的模型，你只好从头再来。

*方案 2：在生产环境中部署 PyTorch*。这意味着重建整个部署基础设施。PyTorch 的移动端支持在 2017–2018 年还很稚嫩。你的边缘设备根本无法运行 PyTorch。这个方案甚至不可行。

*方案 3：放弃*。模型永远上不了生产。所有研究投入都白费了。

这不是假想的难题——而是大多数试图部署深度学习模型的组织面对的现实。你为训练选择的框架，把你在部署上也锁进了那个框架的生态。

=== 互操作性危机

问题不止影响单个公司。整个领域都在受损：

*研究的可复现性*：用 Caffe 模型发表的论文，很难在 TensorFlow 中复现。研究人员不得不从头重新实现，结果往往还不一样。差异是来自实现细节，还是原论文本身有错？

*模型共享*：预训练模型是框架专属的。一个出色的 PyTorch ResNet 实现，TensorFlow 用户却用不了。社区的知识被割裂了。

*硬件优化*：硬件厂商（NVIDIA、Intel、ARM 等）不得不分别支持每个框架。为 TensorFlow 做的优化帮不到 PyTorch 用户。这拖慢了硬件创新。

*工具开发*：每种工具——性能分析器、可视化工具、优化器——都得为每个框架单独开发。生态碎片化，效率低下。

=== 解决方案：交换格式

业界需要一种通用语言——一种独立于训练框架、专为部署优化的神经网络表示方式。这促成了若干交换格式的诞生，它们各自解决略有不同的问题。

关键洞见在于关注点分离：训练与推理是两项不同的任务，需求也不同。训练需要灵活性、自动微分和优化算法。推理需要效率、小体积和广泛的硬件支持。

交换格式位于这两个世界之间。你用自己喜欢的框架训练，导出为交换格式，然后用最适合目标平台的运行时来部署。格式打破了锁定。

为解决这个问题，涌现出两种主要格式，各有侧重：

*TensorFlow Lite*（2017）：Google 针对移动部署的方案。专注于小体积、快执行和激进优化。

*ONNX*（2017）：Microsoft、Facebook 等公司的合作成果。专注于跨框架兼容性和广泛的生态支持。

下面我们逐一细看。

== TensorFlow Lite：移动优先的优化

Google 面临一个具体难题：他们有 TensorFlow 这个强大的训练框架，但它对移动设备来说太大、太复杂了。完整的 TensorFlow 运行时可能有数百 MB。而移动应用需要小、快、省电。

TensorFlow Lite 正是在这一约束下诞生的。它不只是一个文件格式——而是为移动与嵌入式部署设计的完整生态。

=== 设计哲学

关键洞见是：推理不需要训练的全部机制。你不需要自动微分，不需要优化器实现，也不需要定义任意新运算的灵活性。

你需要的是：

- 模型的紧凑表示
- 一个能高效执行它的小型运行时
- 针对体积和速度优化模型的工具

TFLite 三者齐备，并且把全部注意力都放在移动端的约束上。

=== 格式：为效率而生的 FlatBuffers

格式本身基于 FlatBuffers，这是 Google 专为效率开发的序列化库。与 JSON 或 Protocol Buffers 不同，FlatBuffers 不需要解析——你可以直接从序列化后的格式中访问数据。

这对移动设备很重要。解析一个 50MB 的模型文件要花时间和内存。用 FlatBuffers，你把文件内存映射后直接访问。加载几乎是瞬间完成的，也不需要额外内存来存放解析后的表示。

模型以紧凑的二进制格式存储（`.tflite` 文件）。一个典型的 ResNet-50 模型在 TensorFlow 的 SavedModel 格式下约 100MB，经优化后 TFLite 格式只有 25MB。这 4 倍的缩减来自量化，我们接下来就会讨论。

=== 量化：杀手级特性

TFLite 真正的威力来自它的优化工具，其中*量化*是最亮眼的特性。

神经网络通常用 32 位浮点数表示权重和激活值。每个权重占 4 字节。一个有 2500 万参数的模型就是 100MB。

量化把它们转成 8 位整数。每个权重变成 1 字节。同样的 2500 万参数模型现在只有 25MB——缩减到四分之一。

但这不会损害精度吗？出乎意料的是，损失并不大。对许多模型来说，量化造成的精度损失不到 1%。有些模型甚至略有提升（降低的精度起到了正则化的作用）。

好处不止于体积：

*更快的推理*：在大多数移动处理器上，整数运算比浮点运算更快。量化模型运行速度快 2–4 倍。

*更低的功耗*：整数运算消耗的功耗更少。这延长了电池续航——对移动设备至关重要。

*硬件加速*：许多移动处理器带有专用的整数运算单元。量化模型可以利用它们获得更多加速。

TFLite 支持多种量化方案：

*训练后量化*：最简单的做法。拿一个训练好的 float32 模型，转成 int8。无需重新训练。对许多模型都有效。

*量化感知训练*：在训练时就考虑量化。训练过程中模拟量化的影响，让模型学会对量化保持鲁棒。精度优于训练后量化，但需要重新训练。

*动态范围量化*：把权重量化为 int8，但激活值保持 float32。这是一种折中方案，比完整量化更容易应用。

=== 运行时：小巧且优化

TFLite 运行时是为资源受限设备设计的：

*体积*：核心运行时约 300KB。即使包含所有算子，也不到 1MB。相比之下，TensorFlow 是数百 MB。

*依赖*：依赖极少。运行时几乎是自包含的，很容易集成进移动应用。

*ARM 优化*：使用 NEON SIMD 指令，针对 ARM 处理器做了大量优化。移动设备几乎都基于 ARM，所以这项优化很关键。

*委托支持*：TFLite 支持「委托」（delegate），把计算卸载到专用硬件上。GPU 委托使用 OpenGL ES 或 Vulkan。NPU 委托使用神经网络处理单元。这样就能利用设备所提供的任何加速能力。

=== 生态：工具与模型

TFLite 有成熟的生态：

*TFLite Converter*：把 TensorFlow 模型（SavedModel、Keras、具体函数）转换成 TFLite 格式。处理量化、优化和验证。

*TFLite Model Maker*：用于训练与转换模型的高层 API。用极少的代码完成常见任务（图像分类、目标检测、文本分类）。

*TFLite Support Library*：处理预处理与后处理。提供图像缩放、归一化和结果解释的工具。

*Model Zoo*：数百个可直接使用的预训练模型。图像分类、目标检测、姿态估计、分割等等。

*基准测试工具*：在真实设备上测量推理时间和内存占用。对优化至关重要。

=== 权衡

TFLite 并不完美：

*TensorFlow 锁定*：虽然可以从其它框架转换（PyTorch → ONNX → TensorFlow → TFLite），但过程并不总是顺畅。TFLite 是为 TensorFlow 模型设计的。

*算子覆盖*：TFLite 只支持 TensorFlow 运算的一个子集。大多数常见模型都没问题，但前沿架构可能用到不受支持的运算。

*量化限制*：并非所有模型都适合量化。循环网络和注意力机制对量化可能比较敏感。你可能需要量化感知训练。

*移动端导向*：TFLite 针对移动与嵌入式优化。若是桌面或服务器部署，其它格式可能更合适。

=== 何时适合用 TFLite

以下情况 TFLite 是理想选择：

*移动端部署*：Android 与 iOS 应用。TFLite 在两个平台上都有一流支持。

*体积敏感*：你的应用体积预算很紧。TFLite 的激进优化能让模型保持小巧。

*看重续航*：靠电池运行的移动设备。TFLite 的高效能延长电池续航。

*TensorFlow 生态*：你已经在用 TensorFlow 训练。转换路径顺畅且文档完善。

*预训练模型*：你想用 TensorFlow Hub 上的预训练模型。许多已经以 TFLite 格式提供。

对于面向移动平台的游戏开发，TFLite 通常是最佳选择。工具成熟，文档出色，性能也很难被超越。

== ONNX：通用翻译器

当 Google 用 TFLite 解决移动端问题时，更广泛的业界面临另一个挑战：互操作性。研究人员可能用 PyTorch 训练，但生产系统用的是 TensorFlow。反之亦然。公司可能在不同项目上使用多个框架。每次框架切换都意味着重新实现与验证。

Open Neural Network Exchange（ONNX）格式正是 Microsoft、Facebook 等公司为解此问题而合作推出的。目标很有野心：创建一种任何框架都能导出、任何运行时都能执行的格式。

=== 设计：一种通用语言

ONNX 不只是一个文件格式——它是一套表示神经网络运算的规范。把它想象成神经网络的编程语言，有明确定义的语法与语义。

核心思想是*算子集*：一份全面的运算清单（卷积、矩阵乘法、激活函数、池化、归一化等），每项都有精确定义。每个算子都规定了：

- 接受什么输入（什么形状、什么类型的张量）
- 产生什么输出
- 有哪些参数（步长、填充等）
- 具体如何从输入计算出输出

当 PyTorch 导出到 ONNX 时，它是在把自己的内部运算翻译成这种通用语言。一个 PyTorch 的 `Conv2d` 变成一个带特定参数的 ONNX `Conv` 算子。当 ONNX 运行时加载模型时，它确切知道每个运算的含义以及如何执行。

=== 格式：Protocol Buffers

ONNX 用 Protocol Buffers（protobuf）做序列化。Protobuf 是 Google 开发的二进制格式，在业界被广泛用于高效的数据序列化。

该格式存储：

- *图结构*：节点（运算）与边（运算之间的数据流）
- *算子类型*：每个节点用的是哪个 ONNX 算子
- *属性*：每个算子的参数（卷积核大小、步长等）
- *初始化器*：学习得到的权重与偏置
- *元数据*：模型版本、生产者信息等

ONNX 模型通常比 TFLite 模型大，因为默认不做激进的量化。ResNet-50 的 ONNX 格式约 100MB（与 TensorFlow SavedModel 相同），而量化后的 TFLite 只有 25MB。

=== 可扩展性：随领域一同成长

ONNX 的关键优势之一是可扩展性。深度学习领域演进极快——新的层类型、新的架构、新的运算不断出现。

ONNX 通过*算子版本化*来应对。算子集随时间演进：

- ONNX 1.0（2017）：约 60 个算子
- ONNX 1.6（2020）：约 150 个算子
- ONNX 1.13（2023）：约 180 个算子

当某个新运算变得普及时，它就会被加入标准。模型会声明自己使用的 ONNX 版本，以保证兼容性。

ONNX 还支持*自定义算子*。如果你需要的运算不在标准集中，可以自己定义。这对新运算层出不穷的前沿研究至关重要。

=== 生态：工具与运行时

ONNX 有丰富的生态：

*转换器*：

- PyTorch → ONNX：内建于 PyTorch，支持出色
- TensorFlow → ONNX：通过 tf2onnx，对大多数模型都工作良好
- Keras → ONNX：通过 keras2onnx 或 tf2onnx
- Scikit-learn → ONNX：通过 sklearn-onnx，用于传统 ML 模型

*优化器*：

- ONNX Runtime 的优化 pass：融合运算、消除冗余节点、常量折叠
- ONNX Simplifier：简化复杂图，使其更易部署
- ONNX Optimizer：图级优化

*运行时*：

- ONNX Runtime（Microsoft）：高性能，支持 CPU、WebGPU、DirectML、CUDA
- TensorRT（NVIDIA）：针对 NVIDIA GPU 优化
- OpenVINO（Intel）：针对 Intel 硬件优化
- ONNX.js：在网页浏览器中运行 ONNX 模型
- 自定义运行时：许多公司自建

*验证工具*：

- ONNX Checker：验证模型正确性
- ONNX Shape Inference：推断整个图中的张量形状
- Netron：可视化 ONNX 模型，调试必备

=== 实际影响

ONNX 打破了框架锁定。下面是一个真实的工作流：

1. 研究团队用 PyTorch（他们偏好的框架）训练模型
2. 用一行代码导出为 ONNX：`torch.onnx.export(model, ...)`
3. 验证导出结果：分别在 PyTorch 和 ONNX Runtime 中运行推理，确认输出一致
4. 在服务器上用 ONNX Runtime 部署（为生产优化）
5. 把 ONNX 转成 TFLite，用于移动端部署
6. 把 ONNX 转成 TensorRT，用于 NVIDIA GPU 部署

一个模型，多个部署目标，无需手工重新实现。

=== 权衡

ONNX 并不完美：

*体积*：ONNX 模型比 TFLite 模型大。默认不做激进量化。用于移动部署时，你可能需要把 ONNX 转成 TFLite。

*转换问题*：并非所有运算都能完美转换。动态形状、控制流和自定义运算可能出问题。你可能需要修改模型以使其兼容 ONNX。

*运行时性能参差不齐*：ONNX Runtime 很快，但性能取决于你用的执行提供者（WebGPU、DirectML、CPU 等）。有些运行时优化得更好。

*算子覆盖*：虽然 ONNX 支持很多算子，但前沿研究可能用到尚未进入标准的运算。那就需要自定义算子，而可移植性会因此下降。

=== 何时适合用 ONNX

以下情况 ONNX 是理想选择：

*跨框架兼容*：你在一个框架里训练，在另一个框架里部署。ONNX 就是桥梁。

*多个部署目标*：你需要部署到服务器、边缘设备和移动端。ONNX 可以转换成各目标专属的格式。

*桌面与服务器部署*：体积不像移动端那么关键。ONNX 较大的模型是可以接受的。

*灵活性*：你想切换框架而不必重写一切。ONNX 提供了这种灵活性。

*生态*：你想要丰富的工具、优化器和运行时生态。

对于基于 Vulkan 的推理引擎，ONNX 通常是最好的选择。它不绑定框架，文档完善，工具链出色。本教程要讲的原理适用于 ONNX 模型，不过对其它格式同样有效。

== 格式间转换：现实情况

实践中，你很少只用一个格式。典型工作流会涉及转换，而且往往要经过多个步骤。理解常见的转换路径及其陷阱，能帮你在这一领域顺利穿行。

=== 常见转换工作流

*PyTorch → ONNX → TFLite（移动端部署）*：

1. 用 PyTorch 训练（对研究者友好、灵活）
2. 导出为 ONNX：`torch.onnx.export(model, dummy_input, "model.onnx")`
3. 把 ONNX 转成 TensorFlow：使用 `onnx-tf` 转换器
4. 把 TensorFlow 转成 TFLite：使用带量化的 TFLite 转换器
5. 在 Android/iOS 上部署

这条路径很常见，因为 PyTorch 在研究界很流行，而 TFLite 最适合移动部署。

*TensorFlow → TFLite + ONNX（多平台）*：

1. 用 TensorFlow 训练（对生产友好、成熟）
2. 为移动端转换成 TFLite：用 TFLite 转换器直接转换
3. 为其它平台转换成 ONNX：使用 `tf2onnx`
4. 移动端部署 TFLite，其余地方部署 ONNX

这条路径利用了 TensorFlow 的广泛支持，同时保持灵活。

*以 ONNX 作为通用枢纽*：

1. 用任意框架训练（PyTorch、TensorFlow 等）
2. 导出为 ONNX（大多数框架都支持）
3. 按需把 ONNX 转换成目标格式：
   - ONNX → TFLite，用于移动端
   - ONNX → TensorRT，用于 NVIDIA GPU
   - ONNX → OpenVINO，用于 Intel 硬件

ONNX 成为你的通用中间表示，带来最大的灵活性。

=== 验证：关键一步

每次转换都可能引入 bug。验证不是可选项——它是必须的。

*数值验证*：

把相同的输入分别送入原始模型和转换后的模型，比较输出：

[source,python]
----
# Original PyTorch model
pytorch_output = model(input_tensor)

# Converted ONNX model
onnx_session = onnxruntime.InferenceSession("model.onnx")
onnx_output = onnx_session.run(None, {"input": input_numpy})

# Compare
difference = np.abs(pytorch_output.numpy() - onnx_output)
max_diff = np.max(difference)
print(f"Maximum difference: {max_diff}")
----

什么算可接受？浮点运算并不精确，所以出现小差异是正常的。最大差异在 1e-5 到 1e-6 量级是典型的，也是可接受的。大于 1e-3 的差异则说明有问题。

*统计验证*：

在一个验证集（数百或数千个样本）上运行推理，比较：

- 准确率：转换后的模型是否达到相同的准确率？
- Top-5 准确率：对分类任务，前几个预测是否一致？
- 平均绝对误差：对回归任务，平均误差是否相同？

如果准确率下降超过 1%，就要查一查。转换很可能有问题。

*视觉验证*：

对视觉模型，把输出可视化：

- 分类：预测是否一致？
- 目标检测：边界框是否对齐？
- 分割：掩码看起来是否完全相同？

目视检查常常能发现数值比较漏掉的问题。

=== 常见转换陷阱

*动态形状*：

有些框架支持动态输入形状（批大小可变），另一些则要求固定形状。从动态转成固定，需要指定具体形状，而这些形状可能不合你的部署需求。

解决办法：按你在生产中将使用的形状导出。如果需要多种形状，就导出多个模型。

*自定义运算*：

如果你的模型用了自定义运算（你自己定义的运算），它们可能无法转换。标准格式只支持标准运算。

解决办法：用标准运算重新实现自定义运算，或者为你目标格式增加自定义算子支持（进阶做法）。

*控制流*：

带 if 语句或循环的模型（动态控制流）很难转换。并非所有格式都支持控制流。

解决办法：尽量避开控制流，改用固定尺寸的运算。如果无法避免，就选择支持控制流的格式（ONNX 支持，TFLite 支持有限）。

*量化不匹配*：

转换到 TFLite 时若做量化而处理不慎，会造成精度损失。量化方案很重要。

解决办法：如果精度下降太多，就用量化感知训练。量化之后要彻底验证。

*算子版本不匹配*：

ONNX 算子会随时间演进。用 ONNX 1.10 导出的模型，可能用到 ONNX 1.6 不支持的算子。

解决办法：检查算子版本。需要时升级运行时，或者用较旧的 ONNX 版本导出。

=== 调试转换问题

当转换失败或结果不对时：

*检查算子支持*：

目标格式是否支持你模型中的全部运算？用各格式专用的工具检查：

- ONNX：`onnx.checker.check_model(model)`
- TFLite：检查 TFLite 的算子兼容性

*可视化图*：

用 Netron（netron.app）把原始模型和转换后的模型都可视化看一看。留意：

- 缺失的运算
- 错误的连接
- 形状不匹配

*简化模型*：

如果复杂模型转换失败，试试转换一个更简单的版本：

- 去掉自定义运算
- 用固定形状替代动态形状
- 简化控制流

简单版本跑通之后，再逐步把复杂度加回来，直到找出有问题的部件。

*检查框架版本*：

转换工具对框架版本很敏感。确保你用的版本相互兼容：

- PyTorch 1.10 及以上，ONNX 导出效果好
- TensorFlow 2.x，用于 tf2onnx
- 最新的 onnx-tf，用于 ONNX → TensorFlow

=== 最佳实践

*尽早导出，经常导出*：

不要等模型完全训练好才去测试转换。在开发早期就导出，以便在转换问题变成阻塞项之前发现它们。

*记录预处理*：

准确记录你的模型期望什么样的预处理。这些信息必须随模型一起传递，否则推理会出错。

*一切都要版本化*：

记录框架版本、转换器版本和模型版本。要保证可复现，就必须确切知道用过哪些工具。

*自动化验证*：

编写自动化测试来验证转换后的模型。在 CI/CD 中运行这些测试，以便发现回归。

*保留原始模型*：

始终以原生格式保留原始模型。转换后的模型用于部署，而原始模型是你重新训练或重新转换的事实来源。

== 为 Vulkan 推理选择格式

对于我们基于 Vulkan 的推理实现，该用哪种格式呢？

诚实的答案是：取决于你的来源和你的优先级。

*如果你从 TensorFlow 模型出发、目标是移动端*，TFLite 是阻力最小的路径。格式文档完善，模型已经优化好，你也能找到大量示例。

*如果你需要灵活性和跨框架支持*，ONNX 是最佳选择。它是最通用的格式，生态也最丰富。你可以处理任何框架的模型，也有良好的优化工具。

在本教程系列中，我们主要使用 ONNX。它让我们能灵活使用任何框架的模型，工具链好，模型库也大。但我们要讲的原理适用于任何格式——它们表示的都是同样的底层概念（层、权重、运算），只是序列化方式不同。

== 这些格式究竟包含什么

无论你选择哪种格式，它们都包含相同的基本信息：

*网络架构*：模型的结构——有哪些层、它们如何连接、每层执行什么运算。这是推理的蓝图。

*权重与偏置*：学习得到的参数——数百万个浮点数，编码了模型在训练中学到的东西。这占了文件体积的大部分。

*元数据*：关于输入输出形状、数据类型、预处理要求以及正确使用模型所需其它细节的信息。

*算子定义*：每个运算做什么的规范——卷积如何工作、激活函数做什么等等。这可以是隐式的（引用标准算子集），也可以是显式的（包含自定义运算定义）。

当我们实现 Vulkan 推理时，我们会解析这些格式以提取上述信息，把权重加载进 GPU 内存，并把运算实现为计算着色器。格式只是包装——真正的工作在执行环节。

== 小结

模型格式解决了把训练好的模型从研究框架搬到生产部署的问题。两种主要格式占据主导：TFLite（面向移动端优化）与 ONNX（不绑定框架）。

TFLite 借助激进的优化工具（尤其是量化）在移动部署上表现出色。ONNX 提供跨框架的通用兼容性和丰富的生态。

实践中，格式转换很常见，典型工作流包含多个步骤（移动端用 PyTorch→ONNX→TFLite，或者把 ONNX 当作通用中间格式）。每种格式都包含相同的基本信息：网络架构、学习到的权重、元数据和算子定义。

对于 Vulkan 推理，ONNX 在灵活性与生态支持之间提供了最佳平衡，不过这些原理对任何格式都适用。理解这些格式，为我们加载模型并将其映射到 GPU 执行做好了准备。

有了对模型如何打包与传递的理解，我们就可以进一步探索这些模型如何映射到 Vulkan 的 GPU 执行的心智模型了。
