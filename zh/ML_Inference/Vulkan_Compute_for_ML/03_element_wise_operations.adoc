= 逐元素运算

== 引言

逐元素运算是 ML 中最简单的运算，也是在 Vulkan 计算着色器中实现神经网络层的绝佳起点。这类运算对张量中的每个元素独立地施加同一个函数——元素之间没有依赖关系，并行度完美，实现也直截了当。

想一想「逐元素」意味着什么：你有一个张量（一个多维的数字数组），对每个元素独立地施加同一个函数。如果张量有一百万个元素，你就执行一百万次独立的函数求值。元素之间不通信，没有共享状态，没有复杂的依赖关系。这让逐元素运算具有极强的并行性——简直是为 GPU 量身定做。

激活函数是神经网络中最常见的逐元素运算。正如我们在「ML 推理管线」一章中学到的，激活函数引入非线性，让神经网络能够学习复杂的模式。在推理过程中，激活函数被施加在大多数层之后：卷积 → 激活，全连接 → 激活，归一化 → 激活。它们无处不在，而且必须够快。

本章讲解如何把最常见的几种激活函数实现为 Vulkan 计算着色器：ReLU（现代网络的顶梁柱）、sigmoid（在特定场景中仍在使用）和 tanh（常见于循环网络）。我们会讨论并行化策略、数值稳定性考量，以及适用于所有逐元素运算的性能优化技巧。

== 为什么逐元素运算很重要

在深入实现之前，先弄清楚这些运算为什么重要，以及它们看似简单却难在哪里。

=== 计算强度

逐元素运算的计算量很小——每个元素只需几次算术运算。ReLU 字面上就是 `max(0, x)`，一次比较加一次选择。Sigmoid 需要一次指数运算，代价更高，但也不过是寥寥几次运算。

真正的挑战不在计算本身，而在内存带宽。对于一个有一百万个 float32 元素的张量，你要读入 4MB 输入数据、写出 4MB 输出数据。在内存带宽为 500 GB/s 的 GPU 上，仅内存传输就是 8MB / 500 GB/s ≈ 16 微秒。而实际计算可能只要几微秒。

这意味着逐元素运算是*内存受限*的，而不是计算受限。你的优化重点应该放在内存访问模式上，而不是算术效率。合并访存、缓存利用率、减少冗余传输，比从计算里抠掉几条指令重要得多。

=== 融合机会

因为逐元素运算如此廉价，把它们作为独立的计算派发来运行是一种浪费。每次派发都有开销：绑定管线、更新描述符集、发出命令、同步。对于执行只需几微秒的简单 ReLU，开销可能比实际工作还大。

解决办法是*算子融合*：把多个运算合并进单个计算着色器。与其这样：

[source]
----
Convolution → Write to memory → Read from memory → ReLU → Write to memory
----

不如这样做：

[source]
----
Convolution + ReLU → Write to memory
----

中间结果从不接触内存——它一直留在寄存器里。这消除了内存带宽开销，降低了延迟，提高了吞吐量。本章稍后我们会讨论融合策略。

=== 数值稳定性

某些激活函数涉及指数或除法，可能引发数值问题。Sigmoid 计算 `1 / (1 + exp(-x))`。当 x 为很大的负数时，`exp(-x)` 会上溢到无穷大。当 x 为很大的正数时，`exp(-x)` 下溢为零，于是你算的是 `1 / 1 = 1`，结果是对的，但中间的溢出仍是隐患。

数值稳定性不只是学术问题——它会带来真实的 bug。你的网络在测试时用小输入跑得好好的，到了生产环境遇到边界情况就崩了。我们会为每个激活函数给出数值稳定的实现。

== ReLU：最简单的激活函数

ReLU（Rectified Linear Unit，修正线性单元）是现代神经网络中最常见的激活函数。它的定义是：

[source]
----
ReLU(x) = max(0, x)
----

输入为正就原样输出，输入为负就输出零。就这样。没有指数，没有除法，只有一次比较和一次选择。

=== 为什么 ReLU 占据主导

ReLU 成为深度网络的默认激活函数，是因为它解决了困扰 sigmoid 和 tanh 的梯度消失问题。训练时，梯度在网络中反向流动。使用 sigmoid 时，梯度会被乘以很小的数（sigmoid 的导数最大只有 0.25），经过很多层之后，梯度衰减到几乎为零，前面的层就不再学习了。

ReLU 的梯度很简单：输入为正时为 1，输入为负时为 0。没有乘以小数，没有梯度消失。这让训练深得多的网络成为可能——几百层，而不是区区几十层。

对于推理（我们的关注点），ReLU 的优势在于速度。它是计算代价最低的激活函数，非常适合实时应用。

=== Slang 实现

下面是 ReLU 的完整 Slang 计算着色器：

[source,slang]
----
#version 450

layout(local_size_x = 256) in;

layout(set = 0, binding = 0) readonly buffer InputBuffer {
    float input_data[];
};

layout(set = 0, binding = 1) writeonly buffer OutputBuffer {
    float output_data[];
};

layout(push_constant) uniform PushConstants {
    uint num_elements;
} pc;

void main() {
    uint global_id = gl_GlobalInvocationID.x;

    if (global_id >= pc.num_elements) {
        return;
    }

    float value = input_data[global_id];
    output_data[global_id] = max(0.0, value);
}
----

我们来逐项拆解：

*工作组大小*：我们使用 `local_size_x = 256`，也就是每个工作组有 256 个线程。对大多数 GPU 来说这是个不错的默认值——大到足以隐藏延迟，小到不会耗尽资源。你可能需要针对自己的硬件做调整。

*内存布局*：输入和输出都是简单的 float 数组。我们用 `readonly` 和 `writeonly` 限定符帮助编译器优化内存访问。GPU 由此知道不必担心写后读的冒险。

*推送常量*：我们通过推送常量传入元素数量。对于少量数据，这比使用统一缓冲区更快。推送常量直接嵌入命令缓冲区。

*边界检查*：`if (global_id >= pc.num_elements)` 用来处理元素数量不是工作组大小整数倍的情况。没有这个检查，超出数组边界的线程会访问非法内存。

*计算*：`max(0.0, value)` 就是整个 ReLU 运算。在大多数硬件上，GPU 会把它编译成一条指令。

=== 派发着色器

下面是你在 Vulkan 应用中派发这个着色器的方式：

[source,cpp]
----
// Assuming you've already created the pipeline and descriptor sets

// Update descriptor set with input/output buffers
vk::DescriptorBufferInfo inputInfo{*inputBuffer, 0, VK_WHOLE_SIZE};
vk::DescriptorBufferInfo outputInfo{*outputBuffer, 0, VK_WHOLE_SIZE};

vk::WriteDescriptorSet writes[2] = {
    {
        .dstSet = *descriptorSet,
        .dstBinding = 0,
        .descriptorCount = 1,
        .descriptorType = vk::DescriptorType::eStorageBuffer,
        .pBufferInfo = &inputInfo
    },
    {
        .dstSet = *descriptorSet,
        .dstBinding = 1,
        .descriptorCount = 1,
        .descriptorType = vk::DescriptorType::eStorageBuffer,
        .pBufferInfo = &outputInfo
    }
};

device.updateDescriptorSets(writes, nullptr);

// Record commands
commandBuffer.bindPipeline(vk::PipelineBindPoint::eCompute, *reluPipeline);
commandBuffer.bindDescriptorSets(vk::PipelineBindPoint::eCompute,
                                 *pipelineLayout, 0, *descriptorSet, nullptr);

// Push constants
uint32_t numElements = 1000000;  // 1 million elements
commandBuffer.pushConstants(*pipelineLayout,
                           vk::ShaderStageFlagBits::eCompute, 0, sizeof(uint32_t), &numElements);

// Dispatch: ceil(numElements / 256) work groups
uint32_t numWorkGroups = (numElements + 255) / 256;
commandBuffer.dispatch(numWorkGroups, 1, 1);
----

关键的算式是工作组数量：`(numElements + 255) / 256`。这是向上取整除法——我们向上取整，确保有足够的线程覆盖所有元素。

=== 性能考量

ReLU 太快了，所以瓶颈几乎总是内存带宽，而不是计算。以下是最大化性能的策略：

*合并访存*：我们的着色器顺序访问内存——线程 0 读元素 0，线程 1 读元素 1，以此类推。这让 GPU 能把多次读取合并成一次内存事务。如果线程随机访问内存，性能会显著下降。

*向量化*：不必每个线程处理一个 float，你可以用向量类型（vec2、vec4）一次处理多个 float。在某些 GPU 上这能提升吞吐量：

[source,slang]
----
layout(set = 0, binding = 0) readonly buffer InputBuffer {
    vec4 input_data[];
};

layout(set = 0, binding = 1) writeonly buffer OutputBuffer {
    vec4 output_data[];
};

void main() {
    uint global_id = gl_GlobalInvocationID.x;

    if (global_id >= pc.num_elements) {
        return;
    }

    vec4 value = input_data[global_id];
    output_data[global_id] = max(vec4(0.0), value);
}
----

现在每个线程处理 4 个 float。你派发 `numElements / 4` 个工作组。在某些硬件上，这能带来 10-30% 的性能提升。

*原地运算*：如果不需要保留输入，你可以把输出写回输入缓冲区，从而省去一次缓冲区分配，并把内存带宽减半：

[source,slang]
----
layout(set = 0, binding = 0) buffer InOutBuffer {
    float data[];
};

void main() {
    uint global_id = gl_GlobalInvocationID.x;

    if (global_id >= pc.num_elements) {
        return;
    }

    data[global_id] = max(0.0, data[global_id]);
}
----

这种写法是安全的，因为每个线程只访问自己的元素——不存在竞争条件。

== Sigmoid：经典的激活函数

Sigmoid 的定义是：

[source]
----
sigmoid(x) = 1 / (1 + exp(-x))
----

它把任意输入映射到 (0, 1) 区间，因此可用于二分类（输出表示概率），也可用于循环网络（LSTM、GRU）中的门控。

Sigmoid 曾是早期神经网络的主导激活函数，但在隐藏层中已基本被 ReLU 取代。不过它仍用于特定场景：二分类的输出层、注意力机制，以及门控函数。

=== 数值稳定性问题

朴素实现有一个严重的问题。当 x 为很大的负数时（比如 x = -100），`exp(-x) = exp(100)` 会上溢到无穷大。于是 `1 / (1 + infinity) = 0`，这在数学上是对的，但中间的溢出可能产生 NaN 或其它取决于硬件的问题。

当 x 为很大的正数时（比如 x = 100），`exp(-x) = exp(-100)` 下溢为零。于是 `1 / (1 + 0) = 1`，结果正确。但我们白白做了一次会下溢的指数运算。

解决办法是对正负输入使用不同的表达式：

当 x >= 0 时：

[source]
----
sigmoid(x) = 1 / (1 + exp(-x))
----

当 x < 0 时：

[source]
----
sigmoid(x) = exp(x) / (1 + exp(x))
----

第二个表达式在数学上等价（分子分母同乘 exp(x)），但避免了上溢。对负的 x，exp(x) 始终小于 1，所以不会上溢。

=== Slang 实现

下面是数值稳定的 sigmoid 实现：

[source,slang]
----
#version 450

layout(local_size_x = 256) in;

layout(set = 0, binding = 0) readonly buffer InputBuffer {
    float input_data[];
};

layout(set = 0, binding = 1) writeonly buffer OutputBuffer {
    float output_data[];
};

layout(push_constant) uniform PushConstants {
    uint num_elements;
} pc;

float sigmoid(float x) {
    if (x >= 0.0) {
        // For positive x, use standard formulation
        return 1.0 / (1.0 + exp(-x));
    } else {
        // For negative x, use exp(x) / (1 + exp(x)) to avoid overflow
        float exp_x = exp(x);
        return exp_x / (1.0 + exp_x);
    }
}

void main() {
    uint global_id = gl_GlobalInvocationID.x;

    if (global_id >= pc.num_elements) {
        return;
    }

    float value = input_data[global_id];
    output_data[global_id] = sigmoid(value);
}
----

`sigmoid` 函数处理了两种情况。这个分支看起来代价不小，但当同一波前（warp）中的线程走同一条路径时（这很常见——输入的数值量级往往相近），现代 GPU 处理分支的效率很高。

=== 性能考量

Sigmoid 比 ReLU 更贵，贵在指数运算。在大多数 GPU 上，`exp()` 需要 10-20 个周期，而 `max()` 只要 1-2 个周期。这意味着在元素数量相同时，sigmoid 比 ReLU 慢 5-10 倍。

不过对大型张量而言，sigmoid 仍然是内存受限的。指数运算增加了延迟，但内存带宽仍是瓶颈。

*近似*：如果你需要极致性能，并且能容忍轻微的精度损失，可以用多项式近似来替代 sigmoid。这是用精度换速度：

[source,slang]
----
// Fast sigmoid approximation (less accurate)
float fast_sigmoid(float x) {
    return 0.5 + 0.5 * (x / (1.0 + abs(x)));
}
----

这个近似快得多（没有指数运算），但精度较差，尤其是在 |x| 很大时。只有在性能分析表明 sigmoid 确实是瓶颈、且精度要求允许的情况下才用它。

== Tanh：对称的激活函数

Tanh（双曲正切）的定义是：

[source]
----
tanh(x) = (exp(x) - exp(-x)) / (exp(x) + exp(-x))
----

它把输入映射到 (-1, 1) 区间，因而是零中心的（不同于 sigmoid 输出 0 到 1）。这种零中心特性对某些架构很有用，尤其是循环网络。

Tanh 与 sigmoid 在数学上相关：

[source]
----
tanh(x) = 2 * sigmoid(2x) - 1
----

这个关系提示我们可以用 sigmoid 来实现 tanh，但直接计算更高效。

=== 数值稳定性

Tanh 有与 sigmoid 类似的数值问题。当 x 为很大的正数时，`exp(-x)` 下溢；当 x 为很大的负数时，`exp(x)` 下溢。稳定的表达式是：

当 x >= 0 时：

[source]
----
tanh(x) = (1 - exp(-2x)) / (1 + exp(-2x))
----

当 x < 0 时：

[source]
----
tanh(x) = (exp(2x) - 1) / (exp(2x) + 1)
----

=== Slang 实现

下面是数值稳定的 tanh 实现：

[source,slang]
----
#version 450

layout(local_size_x = 256) in;

layout(set = 0, binding = 0) readonly buffer InputBuffer {
    float input_data[];
};

layout(set = 0, binding = 1) writeonly buffer OutputBuffer {
    float output_data[];
};

layout(push_constant) uniform PushConstants {
    uint num_elements;
} pc;

float tanh_stable(float x) {
    if (x >= 0.0) {
        float exp_neg_2x = exp(-2.0 * x);
        return (1.0 - exp_neg_2x) / (1.0 + exp_neg_2x);
    } else {
        float exp_2x = exp(2.0 * x);
        return (exp_2x - 1.0) / (exp_2x + 1.0);
    }
}

void main() {
    uint global_id = gl_GlobalInvocationID.x;

    if (global_id >= pc.num_elements) {
        return;
    }

    float value = input_data[global_id];
    output_data[global_id] = tanh_stable(value);
}
----

另一种做法是，很多 Slang 实现都提供内置的 `tanh()` 函数，它本身已经是数值稳定的。你可以直接使用：

[source,slang]
----
output_data[global_id] = tanh(input_data[global_id]);
----

查一下你的 GPU 厂商文档，看看这个内置函数是否为你的硬件做了优化。

== 算子融合

正如前面提到的，把激活函数当作独立的派发来运行是低效的。融合把多个运算合进一个着色器，消除中间的内存传输。

=== 融合卷积与 ReLU

常见的模式是卷积后接 ReLU。与其这样：

1. 派发卷积着色器 → 把结果写入缓冲区
2. 插入管线屏障
3. 派发 ReLU 着色器 → 从缓冲区读取，写入另一个缓冲区

不如这样做：

1. 派发融合后的卷积+ReLU 着色器 → 直接写出最终结果

下面是一个融合着色器的简化示例：

[source,slang]
----
#version 450

layout(local_size_x = 16, local_size_y = 16) in;

layout(set = 0, binding = 0) readonly buffer InputBuffer {
    float input_data[];
};

layout(set = 0, binding = 1) readonly buffer WeightBuffer {
    float weights[];
};

layout(set = 0, binding = 2) writeonly buffer OutputBuffer {
    float output_data[];
};

// ... push constants for dimensions ...

void main() {
    // Compute convolution (simplified)
    float sum = 0.0;
    // ... convolution computation ...

    // Apply ReLU immediately, before writing to memory
    float activated = max(0.0, sum);

    // Write final result
    output_data[output_index] = activated;
}
----

关键在于 `sum` 从未离开寄存器——它在一趟里完成计算、激活和写出。这省掉了一次缓冲区分配和两次内存传输（写中间结果、再读回来）。

=== 融合的好处

*减少内存带宽*：读写次数更少，内存带宽的压力就更小，而内存带宽往往是瓶颈。

*更低的延迟*：派发次数更少，命令提交、管线绑定和同步的开销都更少。

*更好的缓存利用率*：运算之间数据留在缓存中，而不是被逐出再重新加载。

代价是着色器更复杂、模块化程度更低。你必须为每一种组合准备单独的融合着色器（卷积+ReLU、卷积+sigmoid 等）。对生产系统而言，性能收益通常大于复杂度成本。

== 批处理与内存访问模式

处理多个张量（批处理）时，内存布局对性能影响很大。

=== 连续访存与跨步访存

如果你的张量批次在内存中连续排布：

[source]
----
[tensor0_element0, tensor0_element1, ..., tensor1_element0, tensor1_element1, ...]
----

那么相邻线程访问相邻的内存位置，从而实现合并访存。这是理想情况。

如果张量是交错排布的：

[source]
----
[tensor0_element0, tensor1_element0, tensor2_element0, tensor0_element1, tensor1_element1, ...]
----

那么线程会以跨步方式访问内存，降低合并效率。性能可能下降 2-3 倍。

只要可能，就把数据安排成连续访问。如果不得不用跨步访问，可以考虑借助共享内存来改善访问模式。

=== 多维张量

对于多维张量（例如形状为 [batch, channels, height, width] 的 4D 张量），你需要把 3D 线程 ID 映射到线性的缓冲区索引。

[source,slang]
----
layout(local_size_x = 16, local_size_y = 16, local_size_z = 1) in;

void main() {
    uint x = gl_GlobalInvocationID.x;
    uint y = gl_GlobalInvocationID.y;
    uint z = gl_GlobalInvocationID.z;

    // Map 3D coordinates to linear index
    // Assuming NCHW layout: [batch, channels, height, width]
    uint index = z * (channels * height * width) +
                 channel * (height * width) +
                 y * width +
                 x;

    if (x >= width || y >= height || z >= batch) {
        return;
    }

    output_data[index] = max(0.0, input_data[index]);
}
----

你用 3D 工作组来派发：`vkCmdDispatch(cmd, width/16, height/16, batch)`。

这种做法对 2D 和 3D 张量都很合适。维度更高时，你可以把某些维度展平，或者使用多次派发。

== 小结

逐元素运算是 ML 中最简单的运算，但要达到最佳性能仍需仔细实现。要点如下：

*ReLU* 是最快也最常见的激活函数。它的实现微不足道（`max(0, x)`），非常适合实时推理。

*Sigmoid* 和 *tanh* 需要数值稳定的实现，以避免上溢/下溢。对正负输入要使用不同的表达式。

*内存带宽*是逐元素运算的瓶颈，而不是计算。把精力放在合并访存和减少传输上。

*算子融合*把多个运算合进一个着色器，消除中间的内存传输。这对生产系统的性能至关重要。

*批处理*与恰当的内存布局能保证 GPU 高效运转。连续内存访问可以合并，跨步访问则损害性能。

这些逐元素运算实现之后，你就有了神经网络推理引擎中激活函数的构建块。下一章讲矩阵运算——神经网络的计算主力。
