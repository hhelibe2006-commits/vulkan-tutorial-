= 物理集成：结语

== 我们构建了什么

本章搭建了角色系统的物理层，值得退后一步，看看我们究竟解决了多少个各不相同的问题。

我们从确立一个前提开始：*为什么*你不能直接把网格几何体交给物理引擎，还指望得到好结果。务实的答案是代理碰撞体——听起来像是一种妥协，其实不然。与网格碰撞体相比，胶囊体和盒体产生的模拟更稳定、运行更快、占用内存更少，而由此得到的布娃娃行为在视觉上与更高保真的近似无法区分。为每个身体部位选择合适的形状是一门手艺，会随经验增长；我们建立的 glTF extras 系统让美术无需改动代码就能直接控制这些形状。

我们用物理约束把代理碰撞体连接成一副能正常工作的骨架。这里的概念飞跃——理解球窝约束代表肩膀、铰链约束代表膝盖——比任何代码都更重要。一旦建立起这个心智模型，角度限制值就只是需要调校的数字。我们给出的参考人体范围只是起点，不是规范；每个游戏希望角色呈现的手感都不一样。

接着我们妥善解决了**布娃娃交接问题**，具体包括：用角色当前的运动初始化物理刚体速度，用状态机管理过渡，在混合期间持续向物理引擎送入运动学更新，让约束位置始终大致有效，最后再把物理结果读回场景图，使计算蒙皮管线看到正确的动画状态。

最后，我们用位掩码设计处理了自碰撞过滤：把相邻且互相约束的身体部位排除在彼此的接触生成之外，从而避免经典的「布娃娃炸开」现象，同时仍允许角色与世界以及其他角色正确交互。

== 你应该理解的权衡

我们构建的系统假定拓扑固定：每个角色一副布娃娃、一套骨骼、一组约束。这对骨骼结构可预测的人形角色很好用，但对四足动物、解剖结构奇特的生物，以及骨骼在资产创建时无法确定的程序化生成角色，就不太合适。在这些情况下，由 extras 驱动的方式就更有价值——你可以用通用方式定义约束，并在运行时解析——但你也会需要更精细的工具来创作和校验约束图。

我们在交接中使用的混合权重方案（在固定时长内从 0 线性增加到 1）简单可靠，但有局限。150ms 的混合对一个平稳倒下的角色效果很好，但对被突然的巨大冲量击中的角色就可能显得不对——那种情况下，你可能想直接切到布娃娃，而不是做混合。我们设计的状态机支持这一点：如果传入的冲量超过某个阈值，你可以完全跳过 BLENDED 状态，直接转到 RAGDOLL。

我们构建的碰撞过滤系统使用一张扁平的位掩码，每个身体区域占一位。这在 32 位掩码中给你 32 个不同的碰撞层，对单个角色绰绰有余，但对大规模人群系统就成了限制。Jolt Physics 和 PhysX 都提供更精细的过滤机制（宽阶段层、窄阶段回调），让你能把过滤系统扩展到成百上千个角色。

== 接下来是什么

既然视觉渲染和物理系统都基于同一张场景图运作，并产出正确、物理精确的行为，我们就处在有利位置，可以加上最后一层精巧之处：**程序化动画**。

程序化动画是这样一门技艺：在运行时用算法生成或修改关节变换，而不是依赖美术创作的关键帧。它在游戏中最重要的应用是**逆向运动学（IK）**：我们不去直接给脚的位置做动画，而是根据希望脚落在哪里来反算所需的关节角度。这让角色能把脚正确放在不平的地形上，能够去够那些并不在动画师预期位置上的物体，并以自然而非预设僵化的方式响应物理事件。

第 5 章将从头构建一套 IK 系统，先讲清为什么正向运动学无法解决脚部放置问题、而 IK 可以。我们会实现简单的 CCD（循环坐标下降）算法和更精确的 FABRIK（前向与后向到达 IK）算法，并把它们接入本系列一路构建的同一张场景图和动画混合基础设施。

== 验证：该看什么

要验证你的物理集成：
1.  **运动学同步**：让角色处于 `ANIMATED` 状态，开启调试可视化。碰撞胶囊应当随渲染网格移动而完美跟随。
2.  **布娃娃交接**：触发布娃娃时，角色不应突然「跳」或「弹」到新姿势。过渡应当平滑，并保留角色的动量。
3.  **自碰撞**：确保角色的四肢在运动过程中不会互相碰撞。如果四肢在互相「推开」，检查你的碰撞过滤位掩码。
