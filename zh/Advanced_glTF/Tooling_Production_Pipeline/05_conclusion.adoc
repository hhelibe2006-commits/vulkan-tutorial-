= 工具链：小结与下一步

== 我们确立了哪些东西

本章有意不写代码，而是讲流程——正是这套纪律让角色管线可靠、可维护，而不是无穷无尽的神秘问题之源。

我们把命名约定确立为美术与工程师之间的不成文契约。一致的骨骼命名——小写、下划线分隔、左右后缀——让引擎里每一个需要按名字查找关节的系统默认就可靠。我们讨论了 Blender 一侧会污染导出蒙皮数据的具体问题：未归一化的权重、每个顶点超过四个影响、权重为零的幽灵影响，以及导出时休息姿势不匹配。每一种都会产生特定类别的视觉瑕疵，知道哪种瑕疵对应哪种原因，诊断就很快。

我们深入讲了物理 extras 工作流：在 Blender 的 Script Editor 里由 Python 脚本写入的自定义属性如何变成 glTF 文件中的 JSON "extras"，这份数据又如何流入第 2 章的碰撞体与约束解析代码。把配置脚本与 blend 文件放在一起并纳入版本控制，能确保物理参数可复现、可审计。

glTF 导出设置的讨论覆盖了最关键的几个选择：二进制格式还是分离格式（生产环境用二进制）、叶子骨骼选项（关闭）、应用修改器（最终导出时开启），以及动画的强制采样（默认关闭，对程序化驱动器有例外）。

Khronos glTF-Validator 提供了快速、权威的规范符合性检查。把它集成进构建管线，能确保无效资产在源头而不是在运行时被发现。四个输出级别——Error、Warning、Info、Hint——提供了渐进的资产质量视图；错误必须修，警告应当查。

最后，参考查看器（Khronos glTF Sample Viewer 与 Babylon.js Sandbox）提供了让引擎调试变得可行的基准。在下结论说某个视觉问题出在引擎代码之前，先在参考查看器里检查资产，这是图形程序员能养成的最有用的习惯之一。

== 接下来是什么

第 8 章以**调试与视觉审计**为整个教程系列收尾：介绍在运行中的引擎里定位问题的工具与技术。我们已经说明资产问题应当在源头被抓住；第 8 章处理的是资产正确、问题出在引擎里的情形。

我们将实现引擎侧的调试绘制器，用于骨架、碰撞形状和物理约束——这些可视化叠加层让你能在渲染出的角色旁边看到物理表示。我们会讲蒙皮权重热力图，它把顶点的骨骼影响渲染成颜色，用来找出只有动起来才看得见的「夹紧」几何体或错误的权重绘制。我们还会逐步演示如何用 RenderDoc 检查计算蒙皮的输出缓冲区，在光栅化器读取之前确认蒙皮后的顶点位置与法线正确。

== 验证：该看什么

要验证你的生产管线：

1.  **验证器通过**：每个导出的 `.glb` 都应当零错误、零警告地通过 **glTF-Validator**。
2.  **命名一致**：检查物理元数据里的 `"parent_bone"` 字符串与 glTF JSON 中实际的节点名是否一致。
3.  **导出设置**：在 Babylon.js sandbox 这类第三方查看器中打开导出文件，确认 **自定义属性**、**形态键** 和 **顶点权重** 都包含在里面。
