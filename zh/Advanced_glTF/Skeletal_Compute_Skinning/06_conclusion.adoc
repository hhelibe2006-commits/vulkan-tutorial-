= 骨骼与计算蒙皮：结语

== 我们构建了什么

在本章中，我们把动画系统从基于顶点着色器的近似方案，改造成了一条专用的、生产级计算管线。让我们花点时间回顾一下所构建内容的完整范围，以及每一部分为何重要。

我们从数学基础开始，讲清了逆绑定矩阵（Inverse Bind Matrix）为什么存在、解决了什么问题。那个三步蒙皮方程——变换到骨骼局部空间、施加动画后的关节变换、混合多个影响——不再是黑盒。现在当你看到一个损坏或错位的蒙皮网格时，你能推断出方程中哪一步最可能是元凶。

我们把这套蒙皮数学从顶点着色器搬进了 Vulkan 计算着色器，并由此创建了一个常驻 GPU 的持久输出顶点缓冲区，它保存着角色网格权威的动画状态。正是这次架构改变，让后续的一切成为可能。

通过让光栅化器、光线追踪 BLAS 和物理回读系统都指向同一个输出缓冲区，我们消除了朴素实现中那种碎片化。不再有 T-pose 阴影。不再有落后于可视网格的碰撞外壳。不再为不同的渲染特性重复付出多次蒙皮开销。一次派发、一个缓冲区，所有使用者都受益。

最后，我们提升了运动本身的质量——从线性插值（准确但没有生命力）转向三次 Hermite 样条（保留动画师的意图），并加入交叉淡化混合，让角色在状态之间平滑过渡，而不是生硬地瞬间切换。

== 从动画到场景图的桥梁

初学者常感到困惑的一点是：动画系统的输出——`Pose`——究竟如何让角色在世界中移动。`Pose` 保存了骨架中每个关节的局部变换，而这些关节同时也是我们场景图中的 `Node` 对象。要把两者桥接起来，我们必须把姿势数据写回节点：

[source,cpp]
----
void apply_pose_to_scene_graph(
    std::vector<Node>& nodes,
    const Pose& pose,
    const std::vector<uint32_t>& joint_indices)
{
    // For each joint in the animation, update its corresponding node
    for (size_t i = 0; i < joint_indices.size(); ++i) {
        Node& node = nodes[joint_indices[i]];
        node.translation    = pose.translations[i];
        node.local_rotation = pose.rotations[i];
        node.scale          = pose.scales[i];

        // Mark as dirty so world matrices are recomputed!
        node.mark_dirty();
    }
}
----

这一步是角色专属动画系统与引擎级场景图之间的「胶水」。一旦写回，下一次场景图更新就会把这些动画变换沿层级向下传播，确保挂在角色身上的任何东西（比如一把剑或一顶头盔）都完美跟随运动。

== 你应该理解的权衡

在继续之前，有必要把我们所采用方法的局限与权衡讲清楚。

**线性混合蒙皮并不完美。** LBS 之所以成为行业标准，是因为它快，而且通常「足够好」，但它有一个众所周知的瑕疵，叫**「糖纸」或「肘部塌陷」问题**。当某个关节旋转 180 度（比如手腕从掌心朝上转到掌心朝下）时，LBS 会经过零体积——网格在关节处先塌陷再重新膨胀。另一种方案**双四元数蒙皮（DQS）**混合的是基于四元数的刚体变换而不是矩阵，从而避开这一瑕疵。许多商业游戏的主力角色用 DQS，远处或不重要的物体用 LBS。实现 DQS 只是在我们这里搭好的数学上做直接扩展——计算着色器的结构完全不变，只有混合公式改变。

**BLAS refit 有质量代价。** 虽然 refit 比完整重建快得多，但 BVH 树结构是针对静止姿势几何优化的，网格越偏离静止姿势，它就越不最优。极端情况下（角色做幅度极大、速度极快的动作），这会导致光线遍历性能下降。常见的生产做法是偶尔做一次完整 BLAS 重建（每 N 帧，或骨架位移超过阈值时），中间帧则使用 refit。

**为物理做 GPU 到 CPU 的回读是最后手段。** 我们为了完整性介绍了这个选项，但角色物理的正确默认做法是由 CPU 侧关节矩阵直接驱动的骨骼代理碰撞体。回读方案应当只保留给我们描述过的那些特定场合——布料、软体，以及需要精确到网格的查询——那里没有实际可行的替代方案。

== 接下来是什么

我们构建的系统非常好地解决了角色形变的「怎么做」。但角色管线还有整整一层我们尚未触及：角色身体的物理属性。

目前我们有一个能正确形变的可视网格，以及一组驱动它的关节变换。但对于每根骨骼代表什么物理形状，我们没有正式定义。我们没有阻止角色肘部朝错误方向弯曲的关节限制。我们也没有定义布娃娃各关节如何相互作用的约束。

在下一章**物理集成：碰撞体与布娃娃**中，我们将构建这一物理层。我们会自动生成骨骼代理碰撞胶囊体，定义带正确限制的关节约束（这样即使在布娃娃状态下手臂也能正确弯曲），并实现管理「动画控制」与「物理控制」之间切换的状态机。我们还会更深入地讨论上一章提到过的一个话题——碰撞组过滤，探讨如何让角色与世界正确碰撞，同时不与自己打架。

== 验证：该检查什么

要验证你的计算蒙皮实现：
1.  **逆绑定矩阵**：如果你的网格看起来「炸开」或翻了个面，很可能是逆绑定矩阵被应用到了错误的空间或坐标系中。
2.  **管线屏障**：如果你看到几何体抖动或闪烁，检查 `VkPipelineBarrier2` 是否被正确放在计算派发与绘制调用之间。
3.  **法线/切线质量**：如果动画角色的光照看起来不对（比如关节处出现接缝），确认你在 Slang 着色器中正确地对动画后的法线与切线做了归一化。
