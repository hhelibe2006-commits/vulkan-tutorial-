= 高级骨骼与计算蒙皮

== 蒙皮到底是什么

如果你已经做完「构建一个简单引擎」系列，你已经见过骨骼动画的实际运作。我们加载 glTF 文件，解析它的动画通道，每帧更新骨骼矩阵来驱动模型的关节。但在那套教程里，我们有意保持简单：网格形变——也就是让顶点*跟随*骨骼的实际过程——发生在顶点着色器里，一个顶点一个顶点地算，作为常规光栅化管线的一部分。

这种做法行得通。对于只有几个动画角色的简单场景，它完全可以接受。但它背着一个隐藏成本，只有规模上去才会显露：每个需要访问形变后网格的系统，都得自己孤立地再做一遍这套数学。

想想给场景加入物理之后会发生什么。角色的布娃娃需要知道网格表面在哪，这样环境物体才会与*动画后*的身体碰撞，而不是与原始的 T 姿势碰撞。但物理引擎不知道你的顶点着色器。它看不到形变后的位置。于是你要么为物理系统在 CPU 上再跑一整套蒙皮计算，要么接受物理碰撞体位置错误——这种近似在动画幅度越大时看起来越糟。

再把光线追踪加进这幅图景，问题会叠加。Vulkan 光线追踪加速结构——那个让反射、环境光遮蔽和光追阴影成为可能的数据结构——是用网格的顶点位置构建的。如果这些位置还停留在 T 姿势，因为蒙皮只发生在光栅化顶点着色器里，那么投下阴影和反射的将是一个毫无生气的假人，而不是你动画中的角色。

所有这些问题有一个统一的解法，我们称之为**「蒙皮一次，处处使用」**。不是把蒙皮当作渲染的副作用，而是把蒙皮当作一个专门步骤*先*做掉，把形变后的顶点位置存进 GPU 缓冲区。随后光栅化器、光线追踪器和物理系统都从这*同一个*缓冲区读取。每个系统看到的都是正确的动画网格，而我们每帧只做一次昂贵的形变计算。

实施这个策略，需要把蒙皮工作从顶点着色器搬到**Vulkan 计算着色器**里。本章就是从零构建这条基于计算的蒙皮管线。

== 需要先掌握什么

在深入实现之前，值得明确说明：本章假定你已经掌握什么，以及它会从头教你什么。

你应当熟悉「构建一个简单引擎」系列里的 glTF 骨骼动画基础。具体来说，你需要理解 glTF 文件中的**关节**与**蒙皮**是什么、动画通道如何随时间驱动骨骼变换，以及 `AnimationSampler` 与 `AnimationChannel` 这两个结构如何配合产出一个姿势。如果其中任何术语对你陌生，建议先回头复习那部分内容再继续。

你还应当扎实掌握本系列上一章构建的**场景图**系统。我们即将构建的蒙皮系统与该层级深度集成。我们会直接从 `Node` 数组读取关节的世界矩阵，因此理解这些矩阵如何用脏标记模式计算与缓存是必要的。

本章*会*教你的，是顶点静止位置与动画位置之间的数学关系——具体来说，是**逆绑定矩阵**的作用，以及它如何把蒙皮计算锚定到原始 T 姿势。接着会展示如何把这套数学写进 Vulkan 计算着色器，如何管理输入输出缓冲区，以及如何组织管线，让输出能被多个下游系统同时使用。

== 本章安排

我们会分层构建这个系统。首先建立数学基础——明确每个顶点上需要做什么计算，以及为什么。不理解数学，着色器代码就只是一串变出魔法的矩阵乘法。理解了它，着色器里的每一行都会成为有意图、有依据的一步。

其次，我们会设计并实现 Vulkan 计算管线。这包括为输入顶点、关节矩阵和输出顶点创建着色器存储缓冲区，用 Slang 编写计算着色器，并每帧正确地派发它。

第三，我们会把输出缓冲区接成共享资源。我们会展示光栅化管线如何从它而不是原始顶点缓冲区读取，如何把它用作光线追踪底层加速结构（BLAS）的几何来源，以及如何把它暴露给物理系统以进行准确的碰撞查询。

最后，我们会处理动画中更精细的部分：用于平滑自然运动的**三次样条插值**，以及用于动画片段之间过渡的**交叉淡化混合**——包括从脚本动画混合到物理驱动布娃娃这一关键场景。
