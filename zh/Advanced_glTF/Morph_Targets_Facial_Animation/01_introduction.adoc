= 形变目标与面部动画

== 另一种形变

到目前为止我们介绍的每种技术——场景图、计算蒙皮、布娃娃、IK——都建立在同一个基础之上：一副由关节组成的骨架，每个关节带一个变换，驱动网格的形变。对于身体、四肢，以及任何形变在性质上大致属于旋转的网格区域，骨骼动画都既强大又高效。但它有一个致命弱点，这个弱点就是脸。

人脸的形变方式与四肢有本质区别。嘴周围的皮肤并不像膝盖弯曲那样旋转——它滑动、鼓起、压缩、拉伸，这些复杂模式由数十条各自独立、方向还部分冲突的肌肉拉扯出来。用关节来表达这一切需要不切实际的数量（电影制作中的专业面部绑定光脸部就可能有几百个关节），而且即便如此，姿态之间的插值仍会产生瑕疵，因为关节旋转的球面线性插值与皮肤位移的线性混合并不是一回事。

业界的面部动画方案是**形变目标**（morph target），根据你所用软件包的不同，它也被称为**混合形状**（blend shape）或**形态键**（shape key）。思路很直接：不去动画关节旋转，而是存储多套完整的顶点位置，每套代表一种面部表情。一个「微笑」形变目标存储微笑状态下每个面部顶点的位置，一个「扬眉」形变目标存储扬眉状态下的位置。运行时，你按各个目标的贡献权重，在基础网格与一个或多个形变目标之间做线性混合。如果微笑权重是 0.7，每个顶点就从静止位置向微笑位置移动 70%。如果微笑（权重 0.5）与扬眉（权重 0.8）同时生效，位移会相加，顶点移动到合成后的位置。

这就是**线性混合形状**模型，也是 glTF 中 `WEIGHTS` 动画通道所表达的内容。

== glTF 为形变目标存储什么

glTF 规范把形变目标存成一个访问器列表，每个目标一个，各自包含逐顶点的位移向量。具体来说，对于一个有 `N` 个顶点、`K` 个形变目标的网格图元，glTF 文件包含：

- 基础顶点缓冲区：N 个条目，含位置、法线、切线和纹理坐标。
- K 个额外的「稀疏」或稠密访问器数组，每个含 N 个位置位移向量（即每个顶点上形变目标位置与基础位置的差）。
- 可选地，K 个额外的法线位移数组和 K 个额外的切线位移数组，用于那些改变表面曲率的形变目标（比如鼓起脸颊）。

即对全部 `K` 个目标：`final_position = base_position + sum(weight[i] * displacement[i])`。

这是线性混合，它与骨骼线性混合蒙皮有同样的优点：天然易于 GPU 并行化。每个顶点相互独立，每份位移只是一次向量加法和一次标量乘法。

== 内存挑战

形变目标有一个严重问题：内存。如果你有一个 5 万个顶点的面部网格和 50 个形变目标（对于一个覆盖完整 FACS——面部动作编码系统——的写实角色来说，这是合理的数量），你就有了 50 × 50,000 = 2,500,000 个位移向量。按每个 3D 浮点向量 12 字节计算，单个角色的脸部就有 30 MB 位移数据。若再有法线位移，翻倍到 60 MB。对于一款同时有多个角色说话的游戏，这个数字会迅速膨胀。

我们将采用的方案是**无绑定**的形变目标缓冲区配合**稀疏激活**：不是无条件地把所有角色的全部形变目标数据都加载进常驻 GPU 的缓冲区，而是只把*当前激活*的形变目标数据提升进去，并用 Vulkan 1.4 的描述符索引在单个着色器中访问其中任意一个。这与材质用无绑定纹理图集是同一套设计哲学——不是为每个资源绑定一个描述符，而是一次性绑定一个大的描述符数组，再用推送常量或统一值去索引它。

== 本章内容

我们会分三个阶段实现完整的形变目标管线。首先，从 glTF 解析并上传形变目标的位移数据——这需要特殊处理 glTF 的稀疏访问器格式，它只存储真正发生变化的顶点（对于「眨眼」这类只有眼睑顶点与基础不同的形变目标，这是可观的优化）。其次，我们搭建无绑定的 Vulkan 描述符基础设施——一个大的缓冲区数组，供蒙皮计算着色器随意索引。第三，我们扩展第 3 章的计算蒙皮着色器，在骨骼蒙皮步骤之前施加形变位移，产出一个同时反映面部表情与身体姿态的最终顶点缓冲区。

我们还会简要讨论形变目标与骨骼绑定在生产中的关系。专业角色通常两者并用：用一套粗略的关节绑定处理头部和下颌（应对张嘴这类大尺度形变），再用一层密集的形变目标处理细粒度的表面细节（口型同步、鼻翼翕动、眉间皱纹）。理解这两层如何配合，能帮你在自己的角色管线中做出正确的取舍。
