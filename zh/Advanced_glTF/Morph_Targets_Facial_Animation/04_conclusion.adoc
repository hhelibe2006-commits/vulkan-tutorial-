= 形变目标：小结与下一步

== 我们构建了什么

本章补全了从第 3 章开始的形变管线。骨骼蒙皮负责身体：四肢、脊柱与头部的大尺度、旋转驱动的形变。形变目标负责脸：皮肤随肌肉激活而滑动、起皱、鼓起的细微非刚性形变。

我们从 glTF 文件格式处理形变目标的方式入手：稀疏访问器只存储基础网格与每种表情之间真正发生变化的顶点。正确地解析稀疏访问器——把它们展开成完整的稠密位移数组——是第一步，也是最容易出错的一步，尤其因为索引分量类型可能因导出器而异。我们编写了一个健壮的 `expand_sparse_accessor` 函数，能处理字节、短整型和整型三种索引宽度，并对没有显式列出的顶点平稳地返回零。

位移数据在 CPU 上之后，我们用前几章的暂存缓冲区模式把每个形变目标上传到自己的 GPU 缓冲区。我们给这些缓冲区打上 `VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT` 标记，为无绑定架构做准备。

无绑定描述符基础设施使用 `VK_DESCRIPTOR_BINDING_VARIABLE_DESCRIPTOR_COUNT_BIT` 与 `VK_DESCRIPTOR_BINDING_PARTIALLY_BOUND_BIT`，创建一个包含运行期大小存储缓冲区描述符数组的描述符集。所有形变目标缓冲区都在加载时注册进这个数组。派发时，我们只提供*激活*形变目标的索引与权重，避免触碰未激活缓冲区的开销。

扩展后的计算着色器在骨骼蒙皮步骤之前、在绑定姿态下施加形变位移，用 `NonUniformResourceIndex` 以逐线程的值安全索引无绑定数组。输出仍是光栅化器、光线追踪器和物理系统已经在使用的那个共享顶点缓冲区——形变目标支持没有给下游管线增加任何新的同步要求。

== 需要留意的取舍

形变目标在现代 GPU 硬件上求值很快，因为它高度并行：每个顶点相互独立，每个顶点的工作量只是每个激活目标的几次乘加。瓶颈几乎总是内存带宽——从 GPU 内存取回位移数组——而不是算术。这就是「剔除未激活目标」这一步之所以重要的原因：如果你有 60 个形变目标，但这一帧只有 8 个非零，那么用 8 个激活目标而不是 60 个来派发，能把带宽降低 7.5 倍。

上一节提到的推送常量大小问题值得进一步说明。对于大量同时激活的形变目标，把权重与索引数据移入一个小的统一缓冲区（用 `vkCmdUpdateBuffer` 或一次暂存拷贝更新）是正确做法。在这个用例中，推送常量与小统一缓冲区取数之间的性能差异可以忽略——你在性能分析里根本看不出来——但不依赖超出最低限度的推送常量大小所带来的健壮性收益是实实在在的。

本章提到了法线形变目标（表面法线的位移向量），但没有完整实现。如果你的角色有显著改变皮肤曲率的形变目标——鼓起脸颊、皱起眉梢——你应该在位置形变之外实现法线形变。着色器的扩展很直接：为法线位移再加一个无绑定数组，用同样的方式累积即可。没有法线形变时，形变后脸部的光照会略有偏差，在强烈的平行光下尤其明显。

== 接下来是什么

第 7 章我们会从渲染与物理代码中退后一步，考察**生产管线**：从美术的 Blender 文件到经过校验、可进引擎的 glTF 资产的完整工作流。我们会介绍让引擎侧代码可靠工作的命名约定与导出设置、如何用 Khronos glTF-Validator 在格式错误到达加载器之前捕获它们，以及如何用专业的 glTF 查看器为材质和动画建立「基准真值」，免得你花几个小时去调试一个其实是导出问题的东西。

理解生产管线与理解渲染代码同样重要——许多看似引擎的 bug 其实是资产 bug，懂得如何区分二者能为你省下大量调试时间。

== 验证：该看什么

要验证你的形变目标实现：

1.  **稀疏访问器展开**：确认在某个形变目标中不带位移的顶点正确地保持在其基础位置。
2.  **无绑定索引**：用 GPU 调试器（比如 RenderDoc）检查 `morphTargets[]` 数组。确保 `PushConstants` 中传入的描述符索引对应正确的缓冲区槽位。
3.  **操作顺序**：确保形变位移在骨骼蒙皮**之前**施加。如果放在之后，头部旋转时面部特征会显得「漂浮」或脱离。
