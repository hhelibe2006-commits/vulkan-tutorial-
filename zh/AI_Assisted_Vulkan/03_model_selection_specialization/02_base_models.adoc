= 选择基础模型

== 图形开发者的约束

为 Vulkan 开发挑选基础模型，并不只是挑一个能拿到的最大的。图形工作有一条特殊约束：模型每占用 1GB VRAM，就意味着有 1GB 无法用于纹理、顶点缓冲区和帧缓冲区。

所以目标是一个这样的模型：它的推理能力与你实际负担得起的硬件占用之间取得平衡——毕竟它得和你的应用一起常驻。

== 如何评估一个模型

「最好的」模型每几个月就换一次，所以拥有一套评判标准，比记住某个榜单更有用。对图形工作来说，最重要的有三点：

=== 1. VRAM 成本：参数量与量化

第一个问题是：模型能否和你的 Vulkan 应用一起装进你的硬件。参数量越大通常推理越强，但如果一个 70B 模型会逼得你的应用只能待在更慢的系统内存里，那就不值得。

量化（GGUF、EXL2 这类压缩格式）能让更大的模型装进消费级硬件。4 位（Q4）量化是常见的折中——它把内存占用降低约 75%，而精度只小幅下降。

=== 2. 推理深度

一个合理的测试问题：「请解释一个计算到图形依赖的同步要求：计算着色器写入存储缓冲区，随后该缓冲区在下一个通道中被用作顶点缓冲区。」

较弱的模型往往用一句笼统的 `vkDeviceWaitIdle` 作答，或者给出一个没有指定访问掩码的泛化屏障。较强的模型会指出需要从 `VK_ACCESS_SHADER_WRITE_BIT` 到 `VK_ACCESS_VERTEX_ATTRIBUTE_READ_BIT` 的转换，并说出正确的管线阶段。

NB: 这个测试，以及任何具体的模型推荐，都会过时。请把标准当作长期有效的，把点名的模型当作写作时的示例——新模型发布时，你应当重新评估。模型（以及它经过多少微调）其实只是另一个参数，你根据某个任务需要多少帮衬来调它。

=== 3. 上下文窗口

Vulkan 引擎的文件很多。上下文窗口小的模型（比如 4,000 个 token）读完你的管线搭建代码之后，就已经跟丢你的内存分配器了。如果你希望助手在做某个具体实现时能一直把渲染器的头文件留在视野里，至少要有 32k–128k token 的上下文。

== 当下的例子（截至写作时）

以下是能说明上述标准的当下例子——具体名字会变。

=== Qwen 3-Coder（30B）：推理强

Qwen 3-Coder（30B）目前是 C{pp} 本地（非云端）编码模型中较强的一个。

**示例：无绑定纹理重构。** 把一个引擎迁到无绑定纹理，会牵扯到描述符集布局绑定、`descriptorIndexing` 特性，以及 GLSL 的访问方式如何映射到 SPIR-V。面对这个任务，Qwen 3-Coder 能看你着色器里 `sampler2D textures[]` 的用法，并给出为避免校验错误所需的那几个具体 `DESCRIPTOR_BINDING_PARTIALLY_BOUND_BIT` 标志；它也往往能抓住小模型漏掉的同步问题。这让它成为架构工作和 Vulkan 1.3/1.4 特性的合理选择——代价是 Q4_K_M 下约 20GB VRAM，实际上意味着你要有 24GB 的显卡或一台本地服务器。

=== Llama 4（17B）：低延迟

如果你要的是打字时的快速行内反馈，Llama 4（17B）是个稳妥的选择。你写 `VkPipelineShaderStageCreateInfo` 数组时，它能预测接下来的若干行；它能从项目上下文里正确推断入口点名称；看到你没用特化常量时，它会把 `pSpecializationInfo` 设为 `nullptr`。

它大约占 6GB VRAM，在中端硬件（12–16GB 显卡）上能和 Vulkan 应用舒适共存，因此很适合自动补全、单元测试和快速的着色器迭代。

=== Mistral-Nemo（12B）：大上下文

Mistral-Nemo（12B）由 NVIDIA 与 Mistral AI 联合发布，针对高效推理做了调优，上下文窗口为 128k。

**示例：引擎范围的重构。** 一个涉及场景图、多个通道和后处理的全局光照系统，需要模型能同时把不止一个文件留在视野里。由于 Mistral-Nemo 能容纳最多 128,000 个 token 的上下文，它可以跨着读一个渲染器的头文件目录，给出的建议与代码库其余部分保持一致——这对大型重构很有用，也能跟上小模型容易跟丢的类继承层次。它约占 8–10GB VRAM（Q4），位置介于快速的 17B 模型和更笨重的 30B+ 模型之间。

== 交互方式：云端与本地

与云端模型和本地模型对话的方式不一样，搞清楚哪个是哪个能省掉不少挫败感。

=== 云端模型：高层意图

Claude 4.6 或 GPT-5.3 这类云端模型善于处理抽象——你大致可以像跟同事说话那样和它交流。如果你说「远处地形有 Z-fighting，用的是标准 24 位深度缓冲区，我该先查什么？」，模型能推断出你想修好这个瑕疵，并给出可能的原因（深度精度、近远平面比例），而不需要你把自己的投影矩阵设置一一说明。

=== 本地模型：明确指令

本地模型，即便是 Qwen 3-Coder（30B）这种能力不错的，通常也需要更具体的指令——与其当作对话伙伴，不如当作一个按规格干活的老练实现者。一个更有效的本地模型提示词是：「我遇到了 Z-fighting。检查近平面是否太近（当前为 0.01）或远平面是否太远（10000.0）。如果比例超过 1:1,000,000，建议改用对数深度缓冲区，并给出顶点着色器更新所需的 GLSL。」这样把话说清楚，能把本地模型留在正轨上。

== 云端到本地：用一方给另一方交底

有一种值得了解的工作流：让推理能力强的云端模型写技术规格，再把这份规格交给本地模型去实现。

=== 撰写交接文档

用 Claude 4.6 这类模型做规划时，不要直接要代码，而是让它产出一份给本地助手的指令文档。

*   **流程：**
    1.  和云端模型讨论高层目标（例如「我想实现一个 GPU 驱动的剔除系统」）。
    2.  让它写一个文件，比如 `LLM_NOTES.md`，把刚讨论过的结构体、内存布局和同步要求，用明确、无歧义的措辞记录下来。
    3.  在 IDE 里打开 `LLM_NOTES.md`，让你的本地助手（通过 Goose 或 Junie）照着它干。这样本地模型有了一份具体规格可循，不必再去猜你的意图。

=== 为什么值得这么做

云端模型负责把模糊表达的意图翻译成精确的规格，省得你手写；本地模型随后做实现，你的专有代码不必离开这台机器。这种「先规划、再实现」的分工效果最好，而且只有任务足够大、写规格本身划得来时才值得这份开销——对于琐碎的事，云端模型写规格花的时间可能和直接把事做完差不多。

NB: `LLM_NOTES.md` 是当前会话的工作文档，不是项目文档——不应该提交进 git。

这种做法在需要多轮迭代的较长任务上最有用；它也是把陷在某个问题上打转的本地模型解救出来的合理手段：一次简短的云端会话往往就能把它拉回正轨。

== 按阶段选择模型

一个合理的默认做法是让模型匹配工作阶段，同时把这些分工看作流动的、而非固定的角色：

在 **规划与系统设计** 阶段，面对跨平台帧图或线程安全分配器这类工作，使用高推理能力的云端模型或 Qwen 3-Coder（30B），因为这里推理深度比速度更重要。在 **实现与验证** 阶段，用 Mistral-Nemo（12B）或 Qwen 3-Coder 把设计变成满足校验要求的代码。**快速迭代** 时用 Llama 4（17B）或快速的云端模型，这时速度比深度更重要。

== 小结

模型选择主要就是把推理深度与 VRAM 预算匹配起来，并判断什么时候值得为云端模型的推理付费、什么时候用本地的快模型就够了。云端模型负责规划、中等规模的本地模型负责精确的实现工作、小而快的模型负责日常内层循环，这样一套配置既响应及时，又不会在更难的问题上算力不足。

关键的能力在于把模型选择当作一件主动调整的事——根据当前任务的实际需要放大或缩小、在本地与云端之间切换——而不是一个模型包打所有事。
