= MCP 与 RAG 特化

== 训练截止的问题

即便是 Qwen 3-Coder 这样强的基础模型，也只了解其训练数据中存在的东西。如果 Vulkan 工作组今天发布了一个新扩展，模型不会知道——而且它可能会很有信心地编造出并不存在的结构体成员或位掩码，这会实实在在浪费你的调试时间。

MCP 和 RAG 是让模型获取训练数据之外信息的两种主要方式。

== 两种上下文

把模型需要的两类知识分开看是有帮助的：

1.  **Vulkan 规范本身**——对每个开发者都一样。MCP 把模型接到这一类上。
2.  **你引擎特有的约定**——只属于你的项目，没有任何通用模型针对它训练过。RAG 把模型接到这一类上。

== MCP：接入规范

模型上下文协议让你的 AI 查询实时数据，而不是只依赖训练数据。

**示例。** 假设你需要知道 Android 上存储图像可用的 `VkImageUsageFlags`。与其自己去查，你可以让助手去查你本地 SDK 的 `vk.xml`。助手不会从训练数据里猜，而是读真正的 XML 文件并返回真实的位掩码定义——即便是昨天发布的扩展，结果也正确。

== RAG：接入你的代码库

MCP 处理结构化的规范数据，而 RAG 处理你自己的源码、内部文档和架构约定。

**示例。** 你正在写一个新的 `Buffer` 封装，希望它的风格与现有的 `Texture` 类一致。配好 RAG 之后，你让助手以 `Texture` 为参考，按同样的 RAII 和分配模式生成一个 `Buffer` 类。系统不是给你一个通用的 C{pp} 类，而是取回你真正的 `Texture` 实现，生成与你代码库现有约定相符的东西——而且无需重新训练底层模型。

== RAG 管线是如何工作的

理解这条管线很有用，因为正是靠它，你才能只用本地文件就把一个通用模型变成专门懂你引擎的东西。

=== 阶段 1：整理源文档

找出值得为你的引擎建立索引的文档：

*   **头文件**（`.h`、`.hpp` 等）——你的内部 API 接口面。
*   **工程指南**——讲内存管理或同步约定的文档。
*   **外部文档**——第三方库手册的本地副本（Slang、VMA、Volk、SDL3），或 MCP 工具尚未覆盖的厂商优化指南。

NB: 索引的广度与检索速度之间存在取舍——索引越宽可能越准确，但查询更慢，而且还会消耗 token，留给会话中实际工作的预算就更少。让索引保持聚焦，不要什么都收进来。

=== 阶段 2：嵌入与索引

1.  **分块：** 文件被拆成较小的、相互重叠的片段（一个函数、一个类定义）。
2.  **嵌入：** 一个小的嵌入模型（`bge-small-en`、`nomic-embed-text`）把每个片段转成向量。
3.  **向量数据库：** 向量被存储起来，使概念上相近的片段（例如 `VkBuffer` 和 `VkImage` 的创建代码）彼此靠近。

=== 阶段 3：检索

查询会被转成向量，并与最邻近的已存片段匹配。问「管线屏障」，就会检索出你引擎中真正处理同步的那些文件。

=== 阶段 4：增强

在模型生成回答之前，检索到的片段会作为上下文加入提示词：

[source,text]
----
Context: [Your engine's Buffer.cpp code]
Context: [The VMA Reference for allocation]
User Prompt: Create a new vertex buffer for our triangle.
----

== 建立知识索引

许多 IDE 插件会自动做这件事，但用环境搭建那一节已经介绍过的工具，搭一个更透明的东西是值得的。

=== 第 1 步：整理文档目录

为某个具体、经过挑选的目录建立索引，而不是你的整个主目录：

[source,text]
----
/vulkan_project
  /docs
    /vma_library_reference.md
    /engine_architecture.md
    /naming_conventions.md
  /src
    (Your engine code)
----

=== 第 2 步：用 Goose 手动检索

与其依赖一个看不见的插件，你可以用 Goose 把 RAG 显式地做出来。

1.  **加载上下文。** 在要代码之前，告诉代理该读什么：
+
[source,text]
----
Goose, read 'docs/naming_conventions.md' and
'src/core/Buffer.hpp'. We are going to implement
a new Index Buffer class.
----

2.  **提问，并引用你加载的内容：**
+
[source,text]
----
Using our naming conventions and the RAII pattern
seen in 'Buffer.hpp', generate 'IndexBuffer.hpp'
and 'IndexBuffer.cpp'. Ensure it uses 'vmaCreateBuffer'
for allocation.
----

这之所以可行，是因为检索这一步由你自己完成，而 MCP（经由 Goose）让代理把你真实的文件当作事实依据来读，而不是去猜你的约定。

=== 第 3 步：规模化向量索引

如果你的项目长到几千个文件，手动检索就慢了。到那时，一个本地向量数据库（ChromaDB、Pinecone，通过 MCP 接入）能让 AI 在毫秒级搜遍整个引擎，甚至不需要知道确切的文件名。

=== 第 4 步：用知识图谱表达结构

向量搜索擅长找相似的文本；知识图谱更擅长找相关的结构——比如追查哪个 `VkCommandPool` 是由哪个 `VkDevice` 创建的。把项目当作图来索引，你就能问「列出所有依赖 `GlobalDescriptorSet` 的系统」之类的问题，返回的不只是用到它的类，还有在逻辑上与它关联的着色器和屏障。

=== 第 5 步：函数注册表

函数注册表是一份能力清单，AI 可以调用这些能力，而不是重新实现它们。如果你让它抓一帧，它会先检查你的引擎里是否已经有 `RenderDoc::CaptureFrame()` 方法，有就直接用，而不是从头写一套新的抓帧系统。

**提示：用云端模型准备 RAG 素材。** 你可以用更强的云端模型来做最初的整理——把渲染器的约定汇总成一个 markdown 文件，之后让较小的本地模型从它那里检索，这样就能获得大模型的部分理解力，而不必付出 VRAM 代价。

=== 有良好 RAG 索引的小模型能抗衡大得多的模型

7B–30B 量级的模型，只要给它一份你代码库的良好 RAG 索引，就能在特定于你引擎的任务上胜过一个大得多的通用模型——因为它不必把有限的注意力花在从训练中回忆你的类名上；索引负责这件事，模型可以专注于推理眼前这段逻辑。

== 小结

把基础模型的预训练知识，与 MCP 对当前规范的访问、RAG 对你代码库的访问结合起来，你就得到一个既了解 Vulkan 规范、又了解你这个具体引擎的助手。

*   MCP 负责规范。
*   RAG 负责你项目的约定。
