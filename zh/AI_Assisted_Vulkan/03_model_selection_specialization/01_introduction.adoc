= 模型选择与特化：简介

== 选择模型策略

上一节我们搭好了上下文桥：让 AI 能看到你的代码、构建系统和 Vulkan 规范的基础设施。接下来的问题是：实际该用哪个模型，以及用它来做什么。

并非所有 LLM 都同样适合这类工作。有些擅长推理和架构问题，但速度慢；有些为快速的 C{pp}23 代码补全做了调优，在高层设计上却较弱。这一节讲的是让模型匹配任务，而不是默认跟风选最流行的那个。

== 基础权重与实时上下文

区分「模型从训练中学到了什么」与「它在推理时能看到什么」是很有用的：

1.  **基础模型。** 就是模型发布时的样子，基于某个时间点的公开 C{pp} 代码快照和当时的 Vulkan 规范训练而成。
2.  **附加的上下文。** 这是你向模型提供项目专属信息的方式。主要机制有：
    *   **MCP（Model Context Protocol）：** 实时访问当前的 Vulkan 规范和你的本地项目文件。
    *   **RAG（Retrieval-Augmented Generation，检索增强生成）：** 一个可搜索的索引，覆盖你引擎的内部文档、编码规范和过往的决策。
    *   **微调（LoRA）：** 一次小规模的训练调整，让模型学会你的命名约定——例如这个引擎使用 `vk::raii`，从不使用裸指针。

== 为什么这对 Vulkan 重要

Vulkan 变化相当频繁——新扩展不断落地，推荐做法也随时间推移而改变（动态渲染取代渲染通道，描述符缓冲区取代描述符集，等等）。这会带来两点实际后果：

*   通用模型可能仅仅因为某个旧模式在其训练数据中更常见，就建议你采用它。
*   图形代码对内存偏移、对齐和同步上的小错误毫不宽容。一个通常正确但偶尔在这些细节上出错的模型，带来的调试时间可能比它省下的还多——除非它也了解你引擎特有的封装。

== 本节接下来的内容

接下来几章会逐步讲如何选择和调整模型：

我们先从 **选择基础模型** 开始，比较 Qwen 3-Coder、Mistral-Nemo、Llama 4 等选项，看看哪些值得为架构工作付出延迟代价，哪些更适合快速补全和着色器迭代。

然后我们讲 **硬件与 VRAM 预算**。在本机跑模型会实实在在占用 GPU 内存，我们会把账算一遍——包括 KV 缓存和量化——弄清在和 Vulkan 应用共存时你实际有多少可用空间。

之后是 **MCP 与 RAG 特化**：用 MCP 让 AI 指向实时的 Vulkan 注册表（`vk.xml`），用 RAG 为你自己引擎的代码和文档建立索引，让建议既符合规范又与你的代码库一致。

最后，对于想更进一步的人，还有 **用 LoRA 微调**——借助更强的云端模型帮助生成训练数据，再训练一个小适配器，把你引擎的约定固化进本地模型，这样就不必反复提醒它。

到本节结束时，你将拥有这样一套模型配置：它既了解 Vulkan 规范的总体情况，也了解你的代码库的具体情况，而不是一个没有项目上下文的通用助手。
