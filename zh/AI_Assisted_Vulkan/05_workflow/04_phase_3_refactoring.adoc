= 阶段 3：重构

== 简介：引擎一直在变

Vulkan 的最佳实践会随时间推移而变化。在 Vulkan 1.0 里算标准做法的东西——为每个小通道配一对 `VkRenderPass` 和 `VkFramebuffer`——放到 Vulkan 1.3 的动态渲染旁边，如今已被视为遗留做法。

这个阶段与其说是和模型一起写新代码，不如说是监督一个代理自己完成范围更大的重构。与一次只处理一个函数的 IDE 助手不同，代理（如 Goose）可以跨整个引擎工作，这对那些需要从初始化一路到最终绘制调用都保持一致落地的改动来说很重要。

== 把工作交出去

在阶段 3，你不是在共同编写代码——你是在给代理一个目标，并审查它的产出。

*   **问题：**把你的引擎从 GLSL 迁移到 Slang。这会牵涉每个着色器、你的描述符绑定逻辑，以及着色器编译脚本——手工做的话是乏味且易错的一周工作。
*   **代理式做法：**让代理访问你的终端和项目，并描述目标：「把我们的 `post_process/` 目录迁移到 Slang。更新 `CMakeLists.txt` 改用 Slang 编译器，重构 C{pp} 以使用新的反射数据，并修掉所有编译错误。」

一个能干的代理不只是提出一份 diff——它会修改文件、运行构建、读取产生的错误，并持续迭代直到编译通过。这不代表结果正确；只代表构建通过，而这比「正确」的标准低得多。审查仍是你的工作。

== 为什么这类改动适合用代理

重构 Vulkan 代码往往有级联依赖。移除一个 `VkRenderPass` 还意味着要更新：

1.  改用 `VkPipelineRenderingCreateInfo` 的 `VkGraphicsPipelineCreateInfo`。
2.  把 `vkCmdBeginRenderPass` 调用改为 `vkCmdBeginRendering`。
3.  每个受影响的内存屏障中的布局转换。

一个能运行构建并读取编译器错误的代理，非常适合这类特定任务——它能顺着跨文件的错误链，持续修复，直到构建重新成功。

== 示例：把 Bloom 迁移到动态渲染

=== 步骤 1：先划定边界
从一个干净的 git 分支开始。明确说明范围：「只修改 `BloomRenderer` 类及其关联的着色器。暂时不要碰核心的 `VulkanDevice` 初始化。」

=== 步骤 2：让它迭代
下达指令：「重构 `BloomRenderer.cpp` 以使用动态渲染。把所有 `VkRenderPass` 成员替换为 `VkPipelineRenderingCreateInfo`。确保图像屏障更新为使用 `VkImageMemoryBarrier2`。」

观察代理实际做了什么。一次典型的运行中，它会：

*   阅读代码，理清依赖链。
*   修改管线。
*   运行构建（`ninja`，或你的项目使用的任何工具）。
*   撞上「找不到变量」的错误，因为它漏掉了针对 synchronization2 的 `vulkan_core.h` 更新。
*   修正 include 并重新构建。

=== 步骤 3：合并前先审查
构建通过不等于代码好。读一遍 diff。常见的情况是，代理为了让东西先跑起来，到处都用 `IMAGE_LAYOUT_GENERAL`——明确纠正它：「优化 Bloom 通道中的布局：渲染目标用 `ATTACHMENT_OPTIMAL`，源纹理用 `READ_ONLY_OPTIMAL`。」

== 小结

阶段 3 用代理来完成那种机械但手工易错的多文件重构，而审查实际落地的内容仍由你负责。审查这一步不是可选的——构建通过只说明代码能编译，并不说明它正确，或在你的引擎里符合惯用法。
