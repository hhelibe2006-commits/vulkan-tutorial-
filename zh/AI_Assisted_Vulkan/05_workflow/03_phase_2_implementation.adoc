= 阶段 2：实现

== 简介：把方案变成代码

阶段 1 给了我们一份设计文档——一份经过核验的后处理系统方案。阶段 2 则是把这份方案变成真正的 C{pp} 与 Slang/HLSL 代码。

这时就值得从高推理的云端模型切换到一个更快、专精代码的本地模型——比如 Qwen 3-Coder（30B）或 Mistral-Nemo（12B）。这类模型很适合 Vulkan 中重复性的部分：描述符集更新、管线状态对象和着色器逻辑，并且响应足够快，能维持紧凑的「编辑—检查」循环。

== 小步推进

实现一个特性时，一系列小而聚焦的请求比一次大规模生成效果更好。

*   **问题：**你需要一个用于 Bloom 升采样通道的 `VkGraphicsPipelineCreateInfo`。手工写通常意味着复制一条已有管线，再手动调整混合状态和着色器阶段。
*   **更快的路径：**把阶段 1 的技术路线图作为上下文交给本地模型，然后直接问：「生成升采样管线的状态。对颜色附件使用加法混合，并确保顶点输入状态与我们的 `ScreenQuad` 类匹配。」

因为模型以路线图为上下文，它在第一遍就写对混合因子和四边形渲染约定的几率，比你从头描述这条管线时要高。尽管如此，仍值得把输出与方案对照检查，而不是假定它正确。

== 为什么这个阶段用本地模型

实现工作受益于快速的反馈循环。一小时内你会问很多小的、语法层面的问题：

*   「一维采样器的枚举又是什么来着？」
*   「为这些 mip 生成 `VkDescriptorImageInfo` 数组。」
*   「把这个着色器重构成用结构化缓冲区存 bloom 权重。」

通过 Ollama 运行的本地模型能在几毫秒内回答这些问题，而不是托管 API 调用那样的往返延迟；在这个阶段，这比原始推理质量更重要。

== 示例：实现 Bloom 通道

=== 步骤 1：生成骨架
让本地模型读 `bloom_design.md`。
**提示：**「生成 `BloomRenderer.hpp` 头文件。使用 `VulkanDevice` 包装，并实现设计文档中定义的 `recordDownsampleCommand` 与 `recordUpsampleCommand` 方法。」
**结果：**一个遵循你引擎 RAII 约定与命名的头文件，不过在接受之前你仍应扫一遍。

=== 步骤 2：管线样板代码
Vulkan 管线设置是常见的缺陷来源，主要来自复制粘贴错误。
**提示：**「在 `BloomRenderer.cpp` 中实现管线创建逻辑。使用路线图中的图像布局要求。对降采样通道，关闭深度测试，把多边形模式设为 FILL。」
**结果：**一份可用的管线初始化代码初稿，在继续之前值得对照设计文档仔细读一遍。

=== 步骤 3：着色器迭代
在着色器开发上，本地模型可以加快迭代，但输出需要比 C{pp} 那边更仔细地审查。
**提示：**「为 13 抽头降采样滤波器生成一个 Slang 着色器。使用 Karis 平均来防止 bloom 中出现萤火虫（firefly），如路线图的性能部分所述。」
**结果：**一个实现了所需技术的着色器——但要知道，多数模型在训练中见过的 HLSL 和 GLSL 远多于 Slang，往往会产出 HLSL 风格的输出，无法直接编译。把生成的着色器当作起点：检查 Slang 特有的构造（`[shader("fragment")]`、`ParameterBlock`、`interface` 类型）是否使用正确，并预期在干净编译之前还要修好几个问题。

== 小结

用本地模型做实现，把 Vulkan 大量固有的啰嗦变成简短的迭代循环，而不是漫长的手工敲代码过程。代价是你要更频繁地审查更多生成代码——阶段 1 的路线图正是让这种审查保持可控、不至于漫无边界的关键。
