= 概览

本章首先介绍 Vulkan 以及它要解决的问题。接着，我们会看看绘制第一个三角形所需的各项要素。这样你就能有一个全局认识，把后续每一章放进这幅图景中。最后，我们会讲解 Vulkan API 的结构和一般使用模式。

== Vulkan 的起源

和之前的图形 API 一样，Vulkan 被设计为对 GPU 的跨平台抽象。这些 API 大多有个问题：它们被设计的年代，图形硬件基本只局限于可配置的固定功能。程序员必须以标准格式提供顶点数据，而在光照与着色选项上则完全听凭 GPU 厂商安排。

随着显卡架构逐渐成熟，它们开始提供越来越多的可编程功能。所有这些新功能都得想办法与既有 API 集成起来。结果就产生了并不理想的抽象，驱动程序那一侧还要做大量猜测，才能把程序员的意图映射到现代图形架构上。这就是为什么会有那么多驱动更新来提升游戏性能，有时提升幅度还相当可观。由于这些驱动非常复杂，应用开发者还得应付不同厂商之间的不一致，比如着色器可接受的语法差异。除了这些新特性，过去十年还涌现了大量配备强大图形硬件的移动与嵌入式设备。这些移动 GPU 为了满足功耗与空间要求，采用了不同的架构。瓦片渲染就是一个例子，如果能给程序员更多控制权，这类架构的性能会更好。这些 API 的另一个年代遗留限制是对多线程支持不足，这可能在 CPU 一侧造成瓶颈。

Vulkan 从零开始针对现代图形架构设计，从而解决了这些问题。它让程序员用一个功能更全但也更冗长的 API 清楚表达意图，从而降低驱动开销，并允许多个线程并行创建和提交命令。它改用由单一编译器生成的标准化字节码格式，减少了着色器编译中的不一致。最后，它把图形与计算功能统一到同一个 API 中，承认了现代显卡的通用计算能力。

=== 编码约定

所有 Vulkan 函数、枚举和结构体都定义在 `vulkan.h` 头文件中，该头文件包含在 LunarG 开发的 Vulkan SDK 里。我们会在下一章讲解如何安装这个 SDK。本教程使用 `vulkan.hpp` 头文件提供的 C++ Vulkan API，它随官方 Vulkan SDK 一起发布。这个头文件在原始 C 版 Vulkan API 之上提供了类型安全、对 RAII 友好、也更顺手的接口，同时仍与底层 Vulkan 函数和结构体保持非常贴近的低层映射。

== 绘制一个三角形需要哪些步骤

现在我们概览一下，在行为规范的 Vulkan 程序中渲染一个三角形需要经历哪些步骤。这里引入的所有概念都会在后续章节详细展开。这里只是给你一个全局认识，好把各个组件对应起来。

=== 第 1 步 —— 实例与物理设备选择

Vulkan 应用的第一步是通过 `vk::raii::Instance` 初始化 Vulkan API。创建实例时要描述你的应用以及你会用到的所有 API 扩展。创建实例之后，你就可以查询支持 Vulkan 的硬件，并选择一个或多个 `vk::raii::PhysicalDevice` 用于后续操作。你可以查询显存大小、设备能力等属性来挑选想要的设备，例如优先使用独立显卡。

=== 第 2 步 —— 逻辑设备与队列族

选好要用的硬件设备后，你需要创建 `vk::raii::Device`（逻辑设备），在其中更具体地说明会用到哪些物理设备特性，比如多视口渲染和 64 位浮点。你还需要指定想使用哪些队列族。Vulkan 中的大部分操作，例如绘制命令和内存操作，都是通过提交到 `vk::raii::Queue` 来异步执行的。队列从队列族中分配，每个队列族中的队列支持一组特定的操作。例如，图形、计算和内存传输操作可能分别有各自的队列族。队列族的可用性也可以作为选择物理设备时的区分依据。支持 Vulkan 的设备有可能不提供任何图形功能；不过如今所有支持 Vulkan 的显卡通常都支持我们关心的全部队列操作。

=== 第 3 步 —— 窗口表面与交换链

除非你只关心离屏渲染，否则你需要创建一个窗口来呈现渲染结果。窗口可以用原生平台 API 创建，也可以用 GLFW、SDL 这类库创建。本教程使用 GLFW，下一章会详细说明。

要真正渲染到窗口，还需要另外两个部分：窗口表面（`vk::raii::SurfaceKHR`）和交换链（`vk::raii::SwapchainKHR`）。注意 `KHR` 后缀，它表示这些对象属于某个 Vulkan 扩展。Vulkan API 本身完全与平台无关，因此我们需要使用标准化的 WSI（Window System Interface，窗口系统接口）扩展来与窗口管理器交互。表面是对渲染窗口的跨平台抽象，通常通过提供原生窗口句柄的引用来创建，例如 Windows 上的 `HWND`。好在 GLFW 库内置了函数来处理这些平台相关的细节。

交换链是一组渲染目标。它的基本用意是保证我们当前正在渲染的图像与屏幕上正在显示的那张不同。这对确保只显示完整的图像很重要。每次要绘制一帧时，我们都必须向交换链申请一张可供渲染的图像。绘制完一帧后，图像会归还给交换链，由它在某个时刻呈现到屏幕上。渲染目标的数量以及把绘制完成的图像呈现到屏幕的条件取决于呈现模式。常见的呈现模式有双缓冲（垂直同步）和三缓冲。我们会在创建交换链那一章详细讨论。

某些平台允许你通过 `VK_KHR_display` 和 `VK_KHR_display_swapchain` 扩展直接渲染到显示器，而不与任何窗口管理器交互。这些扩展让你能创建一个代表整个屏幕的表面，例如可以用来实现你自己的窗口管理器。

=== 第 4 步 —— 交换链图像视图

要绘制到从交换链获取的图像上，我们通常会把它包装成 `vk::raii::ImageView`。图像视图引用图像的某个特定部分，用于诸如颜色写入之类的用途。由于交换链中可能有多张不同的图像，我们会预先为每张图像各创建一个图像视图，并在绘制时选用正确的那一个。

=== 第 5 步 —— 动态渲染概览

在 Vulkan 的早期版本中，渲染通道配合帧缓冲区定义了渲染操作应当如何进行，指定所用图像的类型（如颜色、深度）以及它们的内容应如何处理（如清除、加载或存储）。`vk::raii::RenderPass` 会定义子通道和附件用法，而 `vk::raii::Framebuffer` 则把具体的图像视图绑定到这些附件上。

不过，有了动态渲染（Vulkan 1.3 引入），你完全不再需要创建 `vk::raii::Framebuffer`。动态渲染免去了预定义渲染通道和帧缓冲区的需要，允许你在录制命令时直接指定渲染附件。这让 API 简单得多，因为我们可以随用随定渲染目标，不必操心管理帧缓冲区的开销。

使用动态渲染时，你不再需要预先定义 `vk::raii::RenderPass` 或 `vk::raii::Framebuffer`。取而代之的是，在开始录制命令时，用 `vk::raii::CommandBuffer::beginRendering` 和 `vk::RenderingInfo` 之类的结构体动态提供全部必要的附件信息。

在我们最初的三角形渲染程序中，会用动态渲染指定单张图像作为颜色目标，并让 Vulkan 在绘制前把它清除为纯色。

=== 第 6 步 —— 图形管线

Vulkan 中的图形管线通过创建 `vk::raii::Pipeline` 对象来设置。它描述了显卡的可配置状态，比如视口大小和深度缓冲区操作，以及用 `vk::raii::ShaderModule` 对象表示的可编程状态。`vk::raii::ShaderModule` 对象由着色器字节码创建。驱动还需要知道管线中会用到哪些渲染目标，这一点我们通过引用渲染通道来指定。

与既有 API 相比，Vulkan 最有特色的地方之一是：图形管线的几乎所有配置都必须预先设置好。这意味着，如果你想换用别的着色器，或者稍微改动顶点布局，就得完全重建图形管线。你必须为渲染操作所需的各种不同组合预先创建许多 `vk::Pipeline` 对象。只有少数基本配置可以动态修改，比如视口大小和清除颜色。所有状态都必须显式描述；例如，不存在默认的颜色混合状态。

好消息是，这相当于用提前编译取代即时编译，驱动因此有更多优化机会。由于切换到不同图形管线这类大的状态变更被明确暴露出来，运行时性能也更可预测。

=== 第 7 步 —— 命令池与命令缓冲区

如前所述，Vulkan 中我们想执行的许多操作，比如绘制操作，都需要提交到队列。这些操作必须先录制到 `vk::raii::CommandBuffer` 中才能提交。命令缓冲区从与特定队列族关联的 `vk::raii::CommandPool` 中分配。在动态渲染出现之前，要绘制一个三角形，我们得录制一个包含以下操作的命令缓冲区：

* 开始渲染通道
* 绑定图形管线
* 绘制三个顶点
* 结束渲染通道

不过，动态渲染改变了这一点。你不再「开始」和「结束」渲染通道，而是在用 `vk::BeginRendering` 开始渲染时直接定义渲染附件。

这简化了流程，因为你可以随用随定必要的附件，更适应交换链图像被动态选取的场景。因此，你不必为交换链中的每张图像各录制一个命令缓冲区，也不必每帧重复录制同一个命令缓冲区。操作变得更精简高效，Vulkan 处理渲染场景时也更灵活。

=== 第 8 步 —— 主循环

既然绘制命令已经封装进命令缓冲区，主循环就相当直接了。我们先用 `device.acquireNextImageKHR` 从交换链获取一张图像。然后为该图像选择相应的命令缓冲区，用 `graphicsQueue.submit()` 执行它。最后，用 `presentQueue.presentKHR(presentInfo)` 把图像归还给交换链，以便呈现到屏幕。

提交到队列的操作是异步执行的。因此，我们必须使用信号量之类的同步对象来保证正确的执行顺序。绘制命令缓冲区的执行必须设置为等待图像获取完成；否则可能会出现这种情况：我们开始渲染的图像仍在被读取用于屏幕呈现。反过来，`presentQueue.presentKHR(presentInfoKHR)` 调用需要等待渲染完成，为此我们会使用第二个信号量，在渲染完成后发出信号。

=== 小结

这番快速巡览应该能让你大致了解绘制第一个三角形之前要做的工作。真实程序还包含更多步骤，比如分配顶点缓冲区、创建统一缓冲区、上传纹理图像，这些会在后面的章节讲到。不过我们会从简单处入手，因为 Vulkan 的学习曲线本来就够陡了。请注意，我们一开始会把顶点坐标直接写进顶点着色器，而不用顶点缓冲区，算是偷个懒。这是因为管理顶点缓冲区需要先熟悉命令缓冲区。

简而言之，要绘制第一个三角形，我们需要：

* 创建实例（Instance）
* 选择一块受支持的显卡（`PhysicalDevice`）
* 创建用于绘制与呈现的 `Device` 和 `Queue`
* 创建窗口、窗口表面和交换链
* 把交换链图像包装成 `vk::raii::ImageView`
* 设置动态渲染
* 设置图形管线
* 为每一张可能的交换链图像分配并录制一个包含绘制命令的命令缓冲区
* 通过获取图像、提交正确的绘制命令缓冲区、把图像归还给交换链来绘制每一帧

步骤很多，但每个步骤的目的都会在接下来的章节中讲得简单明了。如果你对某一步与整个程序的关系感到困惑，回头翻翻本章就好。

== API 概念

本章最后简要概览 Vulkan API 在较低层次上的结构。

例如，对象创建通常遵循这样的模式：

[,c++]
----
vk::XXXCreateInfo createInfo{};
createInfo.sType = vk::StructureType::eXXXCreateInfo;
createInfo.pNext = nullptr;
createInfo.foo = ...;
createInfo.bar = ...;

vk::XXX object;


try {
    object = device.createXXX(createInfo);
} catch (vk::SystemError& err) {
    std::cerr << "Failed to create object: " << err.what() << std::endl;
    return false;
}
----

Vulkan 中的许多结构体要求你在 `sType` 成员中显式指定结构体类型。`pNext` 成员可以指向扩展结构体，在本教程中它始终是 `nullptr`。创建或销毁对象的函数会有一个 `vk::AllocationCallbacks` 参数，允许你为驱动内存使用自定义分配器，本教程中同样会把它留作 `nullptr`。

几乎所有函数都返回 `vk::Result`，其值是 `vk::Result::eSuccess` 或某个错误码。规范中描述了每个函数可能返回哪些错误码以及它们的含义。

这类调用的失败通过 C++ 异常报告。异常会带出更多关于错误的信息，包括一个 `vk::Result`。这样我们就能用一次调用检查多条命令，同时保持命令语法干净。

=== 验证层

如前所述，Vulkan 为高性能和低驱动开销而设计。因此，它默认只包含非常有限的错误检查与调试能力。如果你做错了什么，驱动往往会直接崩溃，而不是返回错误码；更糟的是，它可能在你的显卡上看起来正常，在别的显卡上却彻底失败。

Vulkan 允许你通过被称为_验证层_（validation layers）的特性启用大量检查。验证层是一段段可以插入到 API 与图形驱动之间的代码，用来做诸如对函数参数执行额外检查、跟踪内存管理问题之类的事情。一个重要的好处是，你可以在开发期间启用它们，而在发布应用时完全禁用，从而获得零开销。任何人都可以编写自己的验证层，但 LunarG 的 Vulkan SDK 提供了一套标准验证层，我们将在本教程中使用它。你还需要注册一个回调函数来接收来自这些层的调试消息。

由于 Vulkan 对每个操作都如此显式，而验证层又如此全面，比起 OpenGL 和 Direct3D，查清屏幕为什么是黑的实际上可能容易得多！

在开始写代码之前只剩一步，那就是 xref:02_Development_environment.adoc[开发环境] 的搭建。
