== 介绍
目前为止，几何体的颜色都是通过逐顶点着色实现的，这种方法比较局限。在本教程的这一部分，我们将实现纹理映射，使几何体看起来更加生动有趣。这也有助于我们在后续章节中加载和绘制基本的3D模型。

为应用程序添加纹理将涉及以下步骤：

- 创建由设备内存支持的图像对象
- 用图像文件中的像素填充它
- 创建图像采样器
- 添加组合图像采样器描述符，以从纹理中采样颜色。

我们之前已经使用过图像对象，但那些都是由交换链扩展自动创建的。这次我们需要自己创建一个。创建图像并填充数据与创建顶点缓冲区类似，但由于 GPU 处理图像的方式不同，所以会更复杂一些。我们将首先创建一个暂存资源并填充像素数据，然后将其复制到最终用于渲染的图像对象中。虽然可以为此目的创建一个暂存图像，但 Vulkan 也允许直接将像素从缓冲区复制到图像。这种方法更简洁、限制更少，通常也 https://developer.nvidia.com/vulkan-memory-management[更快]。为此，我们首先创建一个主机可访问的缓冲区，并用像素值填充它，然后再创建一个图像来复制这些像素。创建图像与创建缓冲区并没有太大区别。它涉及到查询内存需求、分配设备内存并将其绑定，就像我们之前看到的那样。

然而，在处理图像时，还有一些额外的事项需要注意。图像可以有不同的布局，这会影响像素在内存中的组织方式。例如，由于图形硬件的工作方式，简单地逐行存储像素可能无法获得最佳性能。对图像执行任何操作时，必须确保其布局最适合该操作。实际上，我们在指定渲染通道时已经见过一些这样的布局：

- `vk::ImageLayout::ePresentSrcKHR`：最适合演示
- `vk::ImageLayout::eColorAttachmentOptimal`：最适合作为从片段着色器写入颜色的附件
- `vk::ImageLayout::eTransferSrcOptimal`：作为传输操作中的源，是最佳选择，例如 `vk::raii::CommandBuffer::copyImageToBuffer`
- `vk::ImageLayout::eTransferDstOptimal`：作为转运操作中的目的地，例如 `vk::raii::CommandBuffer::copyBufferToImage`
- `vk::ImageLayout::eShaderReadOnlyOptimal`：最适合从着色器中采样

转换图像布局最常用的方法之一是使用管道屏障。管道屏障主要用于同步资源访问，例如确保图像在读取之前已写入，但它们也可以用于转换布局。本章将介绍如何使用管道屏障来实现此目的。此外，在使用时，屏障还可以用于转移队列族的所有权 `vk::SharingMode::eExclusive`。

== 加载图像

像这样引入图像库：

[source,c++]
----
#define STB_IMAGE_IMPLEMENTATION
#include <stb_image.h>
----

默认情况下，头文件仅定义了函数的原型。代码文件需要包含该头文件及其 `STB_IMAGE_IMPLEMENTATION` 定义才能包含函数体，否则会出现链接错误。

[source,c++]
----
void initVulkan()
{
    ...
    createCommandPool();
    createTextureImage();
    createVertexBuffer();
    ...
}

...

void createTextureImage()
{
}
----

建一个新函数 `createTextureImage`，用于加载图像并将其上传到 Vulkan 图像对象中。我们将使用命令缓冲区，因此该函数应该在之后调用 `createCommandPool`。

`textures` 在用于存储纹理图像的目录旁边创建一个新目录 `shaders`。我们将从 `texture.jpg` 该目录中加载一张名为“images”的图像。我选择使用以下这张 https://pixabay.com/en/statue-sculpture-fig-historically-1275469/[CC0 许可]的图像，并将其调整为 512 x 512 像素，但您可以随意选择任何您想要的图像。该库支持大多数常见的图像文件格式，例如 JPEG、PNG、BMP 和 GIF。

image::../../images/纹理映射/CC0 许可的图像.png[]

使用此库加载图像非常简单：

[source,c++]
----
void createTextureImage()
{
    int            texWidth, texHeight, texChannels;
    stbi_uc       *pixels    = stbi_load("textures/texture.jpg", &texWidth, &texHeight, &texChannels, STBI_rgb_alpha);
    vk::DeviceSize imageSize = texWidth * texHeight * 4;

    if (!pixels)
    {
        throw std::runtime_error("failed to load texture image!");
    }
}
----


该 `stbi_load` 函数接受文件路径和要加载的通道数作为参数。该 `STBI_rgb_alpha` 值强制加载带有 alpha 通道的图像，即使图像本身没有 alpha 通道，这有助于将来与其他纹理保持一致。中间三个参数分别输出图像的宽度、高度和实际通道数。返回的指针指向像素值数组的第一个元素。像素值按行排列，每个像素占用 4 个字节，总共包含 4 个 `STBI_rgb_alpha` 值 `texWidth * texHeight * 4`。

== 暂存缓冲区

接下来，我们需要将图像上传到GPU，以便在着色器读取期间获得最佳访问效果。为此，我们将在主机可见内存中创建一个缓冲区，用于映射并复制像素。该缓冲区将作为向GPU复制数据的源。

NOTE: 图像应始终驻留在 GPU 内存中。如果将它们留在仅主机可见的内存中，GPU 就需要通过 PCI 接口读取每一帧的数据，而 PCI 接口的带宽远小于 GPU 内存的带宽。这将严重影响性能。暂存是将图像数据加载到 GPU 内存的过程。并非总是需要暂存，因为有些设备可能提供主机可见和设备本地两种类型的内存。在这种情况下，可以跳过暂存步骤。

缓冲区应位于主机可见内存中（`eHostVisible`），以便我们可以对其进行映射。它还应与主机内存保持一致（`eHostCoherent`），以确保写入其中的数据能够立即可用（而不是以某种方式被缓存）。此外，它还应可用作传输源（`eTransferSrc`），以便我们稍后将其复制到镜像中：自动类型化的返回值分别为 `vk::raii::Buffer` 和 `vk::raii::DeviceMemory`。

[source,c++]
----
auto [stagingBuffer, stagingBufferMemory] =
    createBuffer(imageSize, vk::BufferUsageFlagBits::eTransferSrc, vk::MemoryPropertyFlagBits::eHostVisible | vk::MemoryPropertyFlagBits::eHostCoherent);
----
然后我们可以直接将从图像加载库获取的像素值复制到缓冲区：

[source,c++]
----
void* data = stagingBufferMemory.mapMemory(0, imageSize);
memcpy(data, pixels, imageSize);
stagingBufferMemory.unmapMemory();
----

请记住现在要清理原始像素数组：

[source,c++]
----
stbi_image_free(pixels);
----

== 纹理图像

虽然我们可以设置着色器来访问缓冲区中的像素值，但最好使用 Vulkan 中的图像对象来实现此目的。图像对象允许我们使用二维坐标，从而可以更轻松快捷地检索颜色。图像对象中的像素被称为纹素（texel），我们之后将使用这个名称。添加以下新的类成员：

[source,c++]
----
vk::raii::Image        textureImage       = nullptr;
vk::raii::DeviceMemory textureImageMemory = nullptr;
----

图像的参数在一个vk::ImageCreateInfo结构体中指定：

[source,c++]
----
vk::ImageCreateInfo imageInfo{.imageType   = vk::ImageType::e2D,
                              .format      = format,
                              .extent      = {width, height, 1},
                              .mipLevels   = 1,
                              .arrayLayers = 1,
                              .samples     = vk::SampleCountFlagBits::e1,
                              .tiling      = tiling,
                              .usage       = usage,
                              .sharingMode = vk::SharingMode::eExclusive};
----

图像类型（在 `imageType` 字段中指定）告诉 Vulkan 将使用哪种坐标系来寻址图像中的纹素。可以创建 1D、2D 和 3D 图像。一维图像可用于存储数据数组或梯度，二维图像主要用于纹理，而三维图像可用于存储体素体积等。该
`extent` 字段指定图像的尺寸，即每个轴上的纹素数量。这就是为什么 `depth` 必须使用 `1` 而不是 `0` 的原因。我们的纹理不是数组，而且目前我们也不会使用 mipmapping。

Vulkan 支持多种图像格式，但我们应该对缓冲区中的纹素使用与像素相同的格式，否则复制操作将失败。

该 `tiling` 设置指定了纹素在内存中的排列方式。Vulkan 支持两种截然不同的模式：

- `vk::ImageTiling::eOptimal`：纹素的布局方式取决于具体的实现方式。这使得内存访问更加高效。
- `vk::ImageTiling::eLinear`：纹理元素在内存中按行优先顺序排列，每行可能有一些填充。

NOTE: 线性平铺图像的局限性非常大。例如，它们可能仅适用于二维图像，不能用于深度/模板，也不能拥有多个 mip 级别或图层。此外，GPU 访问速度也比优化后的平铺图像慢得多。因此，它们的适用场景非常有限。

因此，我们将使用它 `vk::ImageTiling::eOptimal` 来实现从着色器进行高效访问。

`initialLayout` 图像的值只有两个可能的值：

- `vk::ImageLayout::eUndefined`：GPU 无法使用，第一次转换就会丢弃纹素。
- `vk::ImageLayout::ePreinitialized`：GPU 无法使用，但第一次过渡将保留纹素。

极少数情况下，需要在首次转换过程中保留纹素。例如，如果您想使用线性平铺图像作为暂存图像，则需要保留纹素。在这种情况下，您需要将纹素数据上传到该图像，然后将该图像转换为传输源，同时确保数据不丢失。

然而，在我们的例子中，我们首先要将图像转换为传输目标，然后将纹素数据从缓冲区对象复制到该图像，因此我们不需要 `vk::ImageLayout::eUndefined` 属性，可以安全地使用它。

`usage` 字段的语义与缓冲区创建期间的字段相同。图像将用作缓冲区副本的目标位置，因此应将其设置为传输目标。我们还希望能够从着色器访问图像以对网格进行着色，因此用法应包含 `vk::ImageUsageFlagBits::eSampled`。

该图像将仅供一个队列族使用：即支持图形（因此也支持传输操作）的队列族。

`samples` 标志与多重采样有关。它仅与用作附件的图像相关，因此请坚持使用单一样本

[source,c++]
----
image = vk::raii::Image(device, imageInfo);
----

图像是使用 `vk::raii::Image` 构造函数创建的，该构造函数没有任何特别值得注意的参数。,图形硬件可能不支持 `vk::Format::eR8G8B8A8Srgb` 格式。您应该准备一份可接受的替代方案列表，并选择最佳且受支持的方案。然而，由于这种特定格式的支持非常广泛，我们将跳过此步骤。使用其他格式也需要进行繁琐的转换。我们将在深度缓冲区章节中再讨论这个问题，届时我们将实现这样一个系统。

[source,c++]
----
vk::MemoryRequirements memRequirements = image.getMemoryRequirements();
vk::MemoryAllocateInfo allocInfo{.allocationSize  = memRequirements.size,
                                 .memoryTypeIndex = findMemoryType(memRequirements.memoryTypeBits, properties)};
imageMemory = vk::raii::DeviceMemory(device, allocInfo);
image.bindMemory(imageMemory, 0);
----

为图像分配内存的方式与为缓冲区分配内存的方式完全相同。使用默认 `vk::raii::DeviceMemory` 构造函数，并 `bindMemory` 在其上使用 `image`。

这个函数已经相当庞大了，而且在后面的章节中还需要创建更多图像，所以我们应该在 `createImage` 像处理缓冲区那样，将图像创建抽象成一个函数。创建该函数，并将图像对象的创建和内存分配移到其中：

[source,c++]
----
std::pair<vk::raii::Image, vk::raii::DeviceMemory> createImage(
  uint32_t width, uint32_t height, vk::Format format, vk::ImageTiling tiling, vk::ImageUsageFlags usage, vk::MemoryPropertyFlags properties )
{
  vk::ImageCreateInfo imageInfo{.imageType   = vk::ImageType::e2D,
                                .format      = format,
                                .extent      = {width, height, 1},
                                .mipLevels   = 1,
                                .arrayLayers = 1,
                                .samples     = vk::SampleCountFlagBits::e1,
                                .tiling      = tiling,
                                .usage       = usage,
                                .sharingMode = vk::SharingMode::eExclusive};

  vk::raii::Image image = vk::raii::Image(device, imageInfo);

  vk::MemoryRequirements memRequirements = image.getMemoryRequirements();
  vk::MemoryAllocateInfo allocInfo{.allocationSize  = memRequirements.size,
                                   .memoryTypeIndex = findMemoryType(memRequirements.memoryTypeBits, properties)};
  vk::raii::DeviceMemory imageMemory = vk::raii::DeviceMemory(device, allocInfo);
  image.bindMemory(imageMemory, 0);

  return {std::move(image), std::move(imageMemory)};
}
----

我已经设置了宽度、高度、格式、平铺模式、使用情况和内存属性参数，因为这些参数在我们整个教程中创建的图像中都会有所不同。

`createTextureImage` 函数现在可以简化为：

[source,c++]
----
void createTextureImage()
{
  int            texWidth, texHeight, texChannels;
  stbi_uc       *pixels    = stbi_load("textures/texture.jpg", &texWidth, &texHeight, &texChannels, STBI_rgb_alpha);
  vk::DeviceSize imageSize = texWidth * texHeight * 4;

  if (!pixels)
  {
    throw std::runtime_error("failed to load texture image!");
  }

  auto [stagingBuffer, stagingBufferMemory] =
      createBuffer(imageSize, vk::BufferUsageFlagBits::eTransferSrc, vk::MemoryPropertyFlagBits::eHostVisible | vk::MemoryPropertyFlagBits::eHostCoherent);

  void *data = stagingBufferMemory.mapMemory(0, imageSize);
  memcpy(data, pixels, imageSize);
  stagingBufferMemory.unmapMemory();

  stbi_image_free(pixels);

  std::tie(textureImage, textureImageMemory) = createImage(texWidth,
                                                           texHeight,
                                                           vk::Format::eR8G8B8A8Srgb,
                                                           vk::ImageTiling::eOptimal,
                                                           vk::ImageUsageFlagBits::eTransferDst | vk::ImageUsageFlagBits::eSampled,
                                                           vk::MemoryPropertyFlagBits::eDeviceLocal);
}
----

== 布局过度

如前所述，Vulkan 中的图像可以采用不同的布局，这会影响像素数据在内存中的组织方式。这些布局针对特定操作进行了优化——有些布局更适合从着色器读取，有些布局更适合作为渲染目标，还有一些布局更适合作为传输操作的源或目标。

布局转换是 Vulkan 设计中的关键环节，它赋予用户对这些内存组织的显式控制权。与其他一些图形 API 不同，Vulkan 不会自动处理这些转换，而是要求用户显式地进行管理。这种方式能够更好地优化性能，因为用户可以根据需要精确调度转换，并高效地批量处理操作。

对于我们的纹理图像，我们需要执行几个过渡：1. 从初始的未定义布局过渡到针对接收数据优化的布局（传输目标）；2. 从传输目标过渡到针对着色器读取优化的布局，以便我们的片段着色器可以从中采样。

这些转换是通过管线屏障实现的，它不仅会改变图像布局，还能确保访问图像的操作之间正确同步。如果没有正确的同步，就可能出现竞态条件，即着色器在复制操作完成之前就尝试从纹理读取数据。

接下来我们要编写的函数需要再次记录和执行命令缓冲区，所以现在是将该逻辑移到一两个辅助函数中的好时机：

[source,c++]
----
vk::raii::CommandBuffer beginSingleTimeCommands()
{
  vk::CommandBufferAllocateInfo allocInfo{.commandPool = commandPool, .level = vk::CommandBufferLevel::ePrimary, .commandBufferCount = 1};
  vk::raii::CommandBuffer       commandBuffer = std::move(vk::raii::CommandBuffers(device, allocInfo).front());

  vk::CommandBufferBeginInfo beginInfo{.flags = vk::CommandBufferUsageFlagBits::eOneTimeSubmit};
  commandBuffer.begin(beginInfo);

  return std::move(commandBuffer);
}

void endSingleTimeCommands(vk::raii::CommandBuffer &&commandBuffer)
{
  commandBuffer.end();

  vk::SubmitInfo submitInfo{.commandBufferCount = 1, .pCommandBuffers = &*commandBuffer};
  queue.submit(submitInfo, nullptr);
  queue.waitIdle();
}
----

这些函数的代码基于现有代码。现在您可以将 `copyBuffer` 函数简化为：

[source,c++]
----
void copyBuffer(vk::raii::Buffer &srcBuffer, vk::raii::Buffer &dstBuffer, vk::DeviceSize size)
{
  vk::raii::CommandBuffer commandCopyBuffer = beginSingleTimeCommands();
  commandCopyBuffer.copyBuffer(*srcBuffer, *dstBuffer, vk::BufferCopy{.size = size});
  endSingleTimeCommands(std::move(commandCopyBuffer));
}
----

如果我们仍然使用缓冲区，那么现在我们可以编写一个函数 `copyBufferToImage` 来记录并执行以完成任务，但此命令要求图像首先处于正确的布局中。创建一个新函数来处理布局转换：

[source,c++]
----
void transitionImageLayout(vk::raii::CommandBuffer &commandBuffer, const vk::raii::Image &image, vk::ImageLayout oldLayout, vk::ImageLayout newLayout)
{
}
----

执行布局转换最常用的方法之一是使用图像内存屏障 `vk::SharingMode::eExclusive` 。这种流水线屏障通常用于同步资源访问，例如确保在读取缓冲区之前完成写入操作，但它也可以用于转换图像布局并在需要时转移队列族的所有权。对于缓冲区，也存在等效的缓冲区内存屏障来实现此功能。

[source,c++]
----
vk::ImageMemoryBarrier barrier{.oldLayout           = oldLayout,
                               .newLayout           = newLayout,
                               .srcQueueFamilyIndex = vk::QueueFamilyIgnored,
                               .dstQueueFamilyIndex = vk::QueueFamilyIgnored,
                               .image               = image,
                               .subresourceRange    = {.aspectMask = vk::ImageAspectFlagBits::eColor, .levelCount = 1, .layerCount = 1}};
----

`oldLayout` 和 `newLayout` 指定布局过渡效果。您可以 `vk::ImageLayout::eUndefined` 像 `oldLayout` 不关心图像现有内容一样使用它。

如果您使用屏障来转移队列族的所有权，那么 `srcQueueFamilyIndex` 和 `dstQueueFamilyIndex` 字段应该是队列族的索引。 如果您不想这样做，则必须将它们设置为 `vk::QueueFamilyIgnored`（不是默认值！）。

`image` 和 `subresourceRange` 参数指定受影响的图像及其具体部分。我们的图像不是数组，也没有 mipmapping 层级，因此只指定了一个层级和图层。

屏障主要用于同步，因此您必须指定哪些涉及资源的操作必须在屏障之前执行，以及哪些涉及资源的操作必须等待屏障执行。正确的值取决于新旧布局，因此我们将在确定要使用的转换之后再讨论这个问题。

[source,c++]
----
commandBuffer.pipelineBarrier(sourceStage, destinationStage, {}, {}, {}, barrier);
----

所有类型的管线屏障都使用同一个函数提交。第一个参数指定屏障之前的操作应在哪个管线阶段执行。第二个参数指定屏障之后的操作将等待的管线阶段。屏障前后允许指定的管线阶段取决于屏障前后资源的使用方式。允许的值列于规范的下表中。例如，如果要在屏障之后读取 uniform 变量，则应指定一个用法 `vk::AccessFlagBits::eUniformRead`，并将最早读取该 uniform 变量的着色器指定为管线阶段，例如 `vk::PipelineStageFlagBits::eFragmentShader`。为此类用法指定非着色器管线阶段是没有意义的，验证层会在您指定的管线阶段与用法不匹配时发出警告。

第三个参数可以是 `{}` 或 `vk::DependencyFlagBits::eByRegion` 。后者将屏障变为基于区域的条件。这意味着，例如，允许实现从资源中已写入的部分开始读取数据。

最后三个参数引用了三种可用类型的管道屏障数组：内存屏障、缓冲区内存屏障和图像内存屏障（例如我们在这里使用的图像内存屏障）。

== 将缓冲区复制到图像

在我们继续 `createTextureImage` 之前，我们还要编写另一个辅助函数 `copyBufferToImage`：

[source,c++]
----
void copyBufferToImage(vk::raii::CommandBuffer &commandBuffer, const vk::raii::Buffer &buffer, vk::raii::Image &image, uint32_t width, uint32_t height)
{
}
----

与缓冲区复制类似，您需要指定要将缓冲区的哪一部分复制到图像的哪一部分。这可以通过 `vk::BufferImageCopy` 结构体来实现：

[source,c++]
----
vk::BufferImageCopy region{.bufferOffset      = 0,
                           .bufferRowLength   = 0,
                           .bufferImageHeight = 0,
                           .imageSubresource  = {.aspectMask = vk::ImageAspectFlagBits::eColor, .mipLevel = 0, .baseArrayLayer = 0, .layerCount = 1},
                           .imageOffset       = {0, 0, 0},
                           .imageExtent       = {width, height, 1}};
----

== 准备纹理图像

现在我们已经拥有完成纹理图像设置所需的所有工具，所以我们回到之前的 `createTextureImage` 函数。我们最后一步是创建纹理图像。下一步是将暂存缓冲区复制到纹理图像。这包括两个步骤：

- 将纹理图像过渡到 `vk::ImageLayout::eTransferDstOptimal`
- 执行缓冲区到图像的复制操作

利用我们刚刚创建的函数，这很容易实现：

[source,c++]
----
vk::raii::CommandBuffer commandBuffer = beginSingleTimeCommands();
transitionImageLayout(commandBuffer, textureImage, vk::ImageLayout::eUndefined, vk::ImageLayout::eTransferDstOptimal);
copyBufferToImage(commandBuffer, stagingBuffer, textureImage, static_cast<uint32_t>(texWidth), static_cast<uint32_t>(texHeight));
----

该图像是使用布局创建的 `vk::ImageLayout::eUndefined`，因此在切换布局时应将其指定为旧布局 `textureImage`。请记住，我们可以这样做，因为在执行复制操作之前，我们并不关心其内容。

为了能够在着色器中开始对纹理图像进行采样，我们需要进行最后一次转换，使其准备好供着色器访问。最后，单次命令缓冲区即可结束。

[source,c++]
----
transitionImageLayout(commandBuffer, textureImage, vk::ImageLayout::eTransferDstOptimal, vk::ImageLayout::eShaderReadOnlyOptimal);
endSingleTimeCommands(std::move(commandBuffer));
----

== 过渡屏障面具

如果您现在启用验证层运行应用程序，您会发现它会报错，提示访问掩码和管道阶段 `transitionImageLayout` 无效。我们仍然需要根据转换中的布局来设置这些参数。

我们需要处理两个过渡阶段：

- 未定义 → 传输目标：无需等待任何操作的传输写入
- 传输目标 → 着色器读取：着色器读取操作应等待传输写入操作，特别是片段着色器中的着色器读取操作，因为我们将在那里使用纹理。

这些规则使用以下访问掩码和管道阶段进行指定：

[source,c++]
----
vk::PipelineStageFlags sourceStage;
vk::PipelineStageFlags destinationStage;

if (oldLayout == vk::ImageLayout::eUndefined && newLayout == vk::ImageLayout::eTransferDstOptimal)
{
  barrier.srcAccessMask = {};
  barrier.dstAccessMask = vk::AccessFlagBits::eTransferWrite;

  sourceStage      = vk::PipelineStageFlagBits::eTopOfPipe;
  destinationStage = vk::PipelineStageFlagBits::eTransfer;
}
else if (oldLayout == vk::ImageLayout::eTransferDstOptimal && newLayout == vk::ImageLayout::eShaderReadOnlyOptimal)
{
  barrier.srcAccessMask = vk::AccessFlagBits::eTransferWrite;
  barrier.dstAccessMask = vk::AccessFlagBits::eShaderRead;

  sourceStage      = vk::PipelineStageFlagBits::eTransfer;
  destinationStage = vk::PipelineStageFlagBits::eFragmentShader;
}
else
{
  throw std::invalid_argument("unsupported layout transition!");
}
commandBuffer.pipelineBarrier(sourceStage, destinationStage, {}, {}, nullptr, barrier);
----

如上表所示，传输写入操作必须发生在流水线传输阶段。由于写入操作无需等待任何条件，您可以为屏障前操作指定一个空的访问掩码 `vk::PipelineStageFlagBits::eTopOfPipe` 和最早的流水线阶段。需要注意的是，这 `vk::PipelineStageFlagBits::eTransfer` 并非图形和计算流水线中的实际阶段，而更像是一个伪阶段，传输操作在此阶段进行。有关更多信息和其他伪阶段示例，请参阅 https://docs.vulkan.org/spec/latest/chapters/synchronization.html#VkPipelineStageFlagBits[文档]。

图像将在同一管线阶段写入，随后由片段着色器读取，这就是为什么我们在片段着色器管线阶段指定着色器读取访问权限的原因。

如果将来需要添加更多过渡效果，我们会扩展该功能。目前应用程序应该可以成功运行，当然，目前还没有任何视觉变化。

需要注意的是，`vk::AccessFlagBits::eHostWrite` 命令缓冲区提交会在开始时进行隐式同步。由于 `transitionImageLayout` 函数仅使用单个命令执行命令缓冲区，因此您可以利用这种隐式同步，并在布局转换中需要 `srcAccessMask` 依赖关系时进行 `vk::AccessFlagBits::eHostWrite` 设置。是否显式地进行同步取决于您，但我个人不太喜欢依赖这些类似 OpenGL 的“隐藏”操作。

实际上有一种特殊的 `vk::ImageLayout::eGeneral` 图像布局支持所有操作。但是，除非使用某些扩展（本教程中未使用），否则使用通用布局可能会降低性能，因为它可能会禁用某些 GPU 上的某些优化。在某些特殊情况下，例如将图像同时用作输入和输出，或者在图像离开预初始化布局后读取图像时，必须使用通用布局。

图像现在包含了纹理，但我们仍然需要一种方法从图形管线中访问它。我们将在 xref:图像视图和采样器.adoc[下一章]中解决这个问题。
