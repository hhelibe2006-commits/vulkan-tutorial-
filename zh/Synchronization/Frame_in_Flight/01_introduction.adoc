= 飞行帧架构：引擎的心跳

== 引言

在图形编程的早期，我们常把渲染想成一个线性序列：CPU 录制一些命令，GPU 执行它们，然后 CPU 等 GPU 完成后才开始下一帧。这很简单，但也慢得惊人。GPU 渲染时 CPU 闲着，CPU 录制下一帧时 GPU 又在等工作。

为了获得高性能，我们需要让这两个过程重叠。这就是我们所说的**飞行帧架构**（Frame-in-Flight Architecture）。我们希望有多帧同时处于处理之中——例如，CPU 可能正在录制第 3 帧，GPU 还在渲染第 2 帧，而显示器正在显示第 1 帧。这个概念在基础教程的 xref:03_Drawing_a_triangle/03_Drawing/03_Frames_in_flight.adoc[飞行帧]一章中介绍过，但在这里我们借助时间线信号量把它提升到新的层次。

== 同步挑战

管理多个并发帧可以说是 Vulkan 引擎中最复杂的同步挑战。你必须确保：

1.  **数据完整性**：不要覆盖 GPU 正在为上一帧读取的统一缓冲区。
2.  **资源生命周期**：在你完全确定 GPU 用完之前，不要销毁纹理或命令缓冲区。
3.  **前向推进**：不要提交太多帧，以致引入巨大的输入延迟或耗尽内存。

在遗留的 Vulkan 1.0 世界里，这靠为每个飞行帧维护一组复杂的栅栏和二元信号量来实现。这导致代码“同步密集”，难以扩展且容易出错。

== 时间线的优势

以**时间线信号量**作为基础，我们可以大幅简化这套架构。不必为每一帧管理单独的栅栏，我们用一个单调递增的计数器表示“已完成的帧索引”。

在本章中，我们要重建引擎主循环，以处理任意数量的飞行帧。我们会探索如何用时间线在 CPU 与 GPU 之间协调，以及如何实现一套健壮的资源管理系统，用时间线精确判断何时可以安全销毁或复用 Vulkan 对象。

我们先从重建引擎的心跳开始：主渲染循环。
