= 执行依赖与内存依赖

== 简介

要理解同步为何如此关键，我们首先得看看 GPU 处理你的工作时底层发生了什么。CPU 一般以线性、可预测的方式执行指令，而 GPU 是一大块高度并行的专用硬件单元阵列。当你提交命令缓冲区时，GPU 并不会从顶部开始、到底部结束；它把任务分发到管线的各个阶段——几何处理、光栅化、片元着色等等——而且往往是同时进行的。

这种并行性正是 Vulkan 强大的原因，但危险也正在于此。如果你希望片元着色器读取计算着色器刚写入的数据，就必须精确定义这个依赖如何生效。在 Vulkan 中，它被拆成两个不同的概念：**执行依赖**与**内存依赖**。

=== 「何时」：执行依赖

**执行依赖**是最简单的同步形式。它回答的问题是：「这段工作什么时候可以开始？」

设想你有两条命令：命令 A 和命令 B。从 A 到 B 的执行依赖只是告诉 GPU：「在命令 A 的指定管线阶段完成之前，不要启动命令 B 的指定管线阶段。」

听起来很直接，但问题在于：在现代硬件上，命令 A 完成工作*并不*等于它的数据已经为命令 B 准备好了。执行只是触发器，内存才是实质。

=== 架构现实：缓存与内存类型

Vulkan 内存并不是一个存放纹理和缓冲区的大桶。取决于你的硬件，它是一片由不同物理位置和访问速度构成的复杂地貌。要有效同步，你需要知道自己是在对着什么同步。

在**独立 GPU** 上，你有专用的显存（VRAM），与系统内存物理分离。在两者之间搬运数据是 **DMA（直接内存访问）**引擎的工作——一个专用单元，可以跨 PCI Express 总线拷贝数据而不打扰主着色器核心。当你上传纹理时，通常是在让 DMA 引擎与图形管线同步。

另一方面，许多笔记本和移动设备使用**统一内存架构（UMA）**，CPU 和 GPU 共享同一批物理内存条。这听起来应该让事情更简单，实际上却增加了一层隐藏的复杂性：**缓存**。即使共享内存，CPU 有自己的 L1/L2/L3 缓存，GPU 也有自己的 L1/L2 缓存。如果 GPU 把数据写入共享缓冲区，这些数据可能停留在 GPU 的 L2 缓存里，从未真正到达物理内存。当 CPU 去读它时，看到的是内存或自己缓存里的旧值。

在 Vulkan 中，我们把这些行为归为三类主要内存类型：

*   **Device Local（设备本地）**：这是 GPU 访问「最快」的内存。在独立显卡上就是 VRAM；在 UMA 上，它就是共享内存的一部分。
*   **Host Visible（主机可见）**：这类内存可以「映射」到你 c{pp} 应用的地址空间，让 CPU 直接读写。
*   **Host Coherent（主机一致）**：一类特殊的主机可见内存，硬件会自动保证 CPU 与 GPU 看到相同的数据，无需你手动刷新缓存（不过你仍然需要执行依赖来确保写入已经*完成*！）。

=== 「何处」：内存依赖

许多 Vulkan 开发者正是在这里栽跟头。即使命令 A 已经完成，它的输出可能仍停留在某个着色器核心的本地 L1 缓存中，或者位于尚未写回主内存池的共享 L2 缓存里。如果命令 B——也许运行在 GPU 完全不同的部分，甚至运行在 CPU 上——在数据被「置为可用」之前就试图从主内存读取它，那它读到的就是陈旧数据。

这就是我们说「光有执行不够」的原因。你可以告诉硬件「等计算着色器完成后再启动片元着色器」，硬件会欣然照办。但片元着色器随后去读纹理，却发现是旧数据，因为计算着色器的写入还被困在某个本地缓存里。

**内存依赖**确保数据在缓存与主内存之间被正确搬运，从而可以被安全读取。它包含两个关键步骤：

1.  **可用性（Availability）**：该操作把数据从来源的本地缓存「刷新」出去，使其对共享内存池（如 L2 缓存或主内存）可见。
2.  **可见性（Visibility）**：该操作「无效化」目标阶段的本地缓存，迫使它从共享内存池读取新数据，而不是沿用可能已经过期的位。

如果没有执行依赖**和**内存依赖，你就生活在**危险**的世界里。最常见的是「读后写」（RAW）危险：片元着色器在计算着色器写完纹理之前就去读它，结果就是早期 Vulkan 实现里常见的闪烁伪影或「阴影痤疮」。

=== 实践中的握手

可以把它想成一次专业的握手。执行依赖是两个人约定见面；内存依赖是一个人真的把文件递给另一个人，而另一个人确认自己看的是新文件，而不是自己的旧笔记。

在 Synchronization 2 中，我们用 `vk::PipelineStageFlagBits2` 和 `vk::AccessFlagBits2` 来定义这次握手。阶段标志定义*何时*（执行依赖），访问标志定义*如何*（内存依赖）。正确搭配两者，你就能保证数据不仅按正确顺序被处理，而且在你去找它时真的在那里。

== Simple Engine 的实现：缓存与安全

在 `Simple Engine` 中，我们通过 `MemoryPool` 类（`memory_pool.cpp`）处理这些架构现实。当我们为缓冲区或图像分配内存时，会指定 `vk::MemoryPropertyFlags` 来决定它的角色。例如，我们的 `UniformBuffer` 对象通常分配为 `HostVisible | HostCoherent`。这意味着 CPU 可以写入它们，而且它们自动对 GPU 可见，无需手动调用 `flushMappedMemoryRanges`。

不过，**一致**并不意味着可以忽略执行依赖！即使在 `Simple Engine` 中，如果 CPU 在 GPU 正处于片元着色器读取某统一缓冲区的过程中更新了一个 `HostCoherent` 统一缓冲区，我们就会遇到**数据竞争**。正因如此，我们仍然使用 `inFlightFences` 和信号量，确保 GPU 用完某一帧的资源之后，CPU 才开始为下一帧修改它们。

对于纹理和顶点缓冲区，我们使用 `DeviceLocal` 内存以获得最高性能。由于它们不是主机一致的，我们必须使用 `vk::DependencyInfo` 和 `vk::ImageMemoryBarrier2` 显式管理「可用性」与「可见性」的握手。这保证了在 `vkCmdCopyBufferToImage` 命令之后，数据被正确地从传输单元的缓存中刷新出去，并对片元着色器的缓存失效。
