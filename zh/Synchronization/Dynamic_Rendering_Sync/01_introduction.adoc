= 动态渲染中的同步：无渲染通道的世界

== 引言

在 Vulkan 早期的很长一段时间里，同步与**渲染通道**（Render Pass）和**子通道**（Subpass）的概念紧密绑定。这样设计本是为了帮助移动 GPU 优化片内内存的使用，但对开发者来说常常令人困惑，并导致代码过度复杂。**子通道依赖**（Subpass Dependency）是在渲染通道不同阶段之间同步数据的主要手段，但它更像一种遗留结构，并不总能匹配现代引擎的工作方式。

随着 **动态渲染**（Dynamic Rendering，Vulkan 1.3 引入）的出现，API 已经摆脱了这些僵化的结构。不再有 `VkRenderPass` 或 `VkFramebuffer` 对象需要管理。你只需调用 `beginRendering` 和 `endRendering`。这一变化让 Vulkan 易用得多，但也把同步的责任完全交到了我们手上。

== 显式时代

在没有子通道依赖的世界里，每个同步点都必须是显式的。如果你想在同一次渲染块内把一次绘制调用的输出用作另一次绘制调用的输入，就不能再指望渲染通道替你完成转换。你必须使用第 3 章学过的 **Synchronization 2** 屏障。

这种转变其实是一大优势。它带来了高得多的清晰度和更强的控制力。你确切知道转换发生在哪里，因为是你自己录制的。它也让它更容易与现代引擎架构集成——在这些架构里，渲染过程是流动的，常常在运行时才确定。

== 本章内容

在本章中，我们会深入探讨在这个现代、无渲染通道的环境里同步是如何工作的。我们会探索：

1.  **替代子通道**：如何用显式屏障协调渲染附件之间的同步，取代遗留的 `VkSubpassDependency` 结构。
2.  **本地读取同步**：我们会看看 **Vulkan 1.4** 最令人兴奋的特性之一：`VK_KHR_dynamic_rendering_local_read`。它让你能进行片内操作（比如在片元着色器中读取深度缓冲区），性能与遗留子通道相当，却拥有动态渲染的简洁。

学完本章，你就能自信地用最新的 Vulkan 特性架构一个高性能渲染器，确保你的同步和渲染代码一样精简高效。
