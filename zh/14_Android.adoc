= Android：让你的 Vulkan 应用走向移动端

== 简介

上一章我们探讨了 Vulkan profile 如何简化特性检测、让代码更易维护。现在，我们借助 Android 把应用带到移动世界，让 Vulkan 知识再进一步。

Vulkan 从设计之初就着眼于跨平台，但部署到 Android 仍会带来一些新的挑战和机遇。Vulkan 核心 API 保持不变，但周边生态——从窗口管理到构建系统——需要另一套做法。

本章将带你把 Vulkan 应用适配到 Android，在满足平台专属要求的同时尽可能复用代码。你会看到，只要配置得当，就能维护一套同时运行在桌面和移动平台上的代码库。

== Android 特有的考量

在深入实现细节之前，先理解在 Android 上开发 Vulkan 应用与桌面开发的关键差异：

1. *窗口系统集成*：我们不再使用 GLFW，而是使用 Android 原生的窗口系统和 Activity 生命周期。
2. *应用生命周期*：Android 应用随时可能被系统暂停、恢复或终止，因此需要谨慎管理资源。
3. *资产加载*：资源被打包进 APK 文件，通过 Android 的资产管理器访问。
4. *构建系统*：我们同时使用 Gradle 和 CMake 来构建 Android 应用。
5. *输入处理*：触摸输入取代了鼠标和键盘，需要不同的事件处理方式。

这些差异乍看之下可能令人却步，但只要方法得当，就能在应对它们的同时保持代码库干净、易维护。

== 项目搭建

理解了这些关键差异之后，我们来搭建 Android 项目。目标是在满足 Android 专属要求的同时，尽可能复用桌面实现中的代码。

=== 前置条件

开始之前，请确认已安装以下工具：

* *link:++https://developer.android.com/studio[Android Studio]++[Android Studio]*：Android 官方开发 IDE
* *Android NDK（Native Development Kit）*：用于在 Android 上进行原生 C++ 开发
* *Android SDK*：需要较新的 API 级别（24+，对应 Android 7.0 或更高版本）以支持 Vulkan
* *CMake 和 Ninja 构建工具*：用于构建原生代码（可以通过 Android Studio 安装）
* *Vulkan SDK*：提供着色器编译工具和验证层

[IMPORTANT]
====
与桌面环境不同，Vulkan HPP（Vulkan 的 C++ 绑定）默认并不包含在 Android NDK 中。你需要从 https://github.com/KhronosGroup/Vulkan-Hpp[Vulkan-Hpp GitHub 仓库] 单独下载，或使用 Vulkan SDK 中包含的版本。
====

== 搭建 Android 项目

项目结构就绪之后，我们深入看看 Android Vulkan 应用的关键组成部分。先从必需的配置文件开始，再转向原生代码实现。

=== 清单文件

每个 Android 应用都需要一个清单文件，用来声明应用的重要信息。对我们的 Vulkan 应用来说，AndroidManifest.xml 文件尤其重要，因为它指定了 Vulkan 版本要求：

[source,xml]
----
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.vulkan.tutorial">

    <!-- Vulkan requires API level 24 (Android 7.0) or higher -->
    <uses-sdk android:minSdkVersion="24" />

    <!-- Declare that this app uses Vulkan -->
    <uses-feature android:name="android.hardware.vulkan.version" android:version="0x400003" android:required="true" />
    <uses-feature android:name="android.hardware.vulkan.level" android:version="0" android:required="true" />

    <application
        android:allowBackup="true"
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:roundIcon="@mipmap/ic_launcher_round"
        android:supportsRtl="true"
        android:theme="@style/AppTheme">
        <activity
            android:name=".VulkanActivity"
            android:label="@string/app_name"
            android:configChanges="orientation|keyboardHidden|screenSize"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>
    </application>

</manifest>
----

关键点：

* 最低 SDK 版本设为 24（Android 7.0），这是 Vulkan 支持所要求的。
* 我们声明应用使用 Vulkan，并给出具体的版本要求。
* 我们把主 Activity（VulkanActivity）设置为应用的入口。

=== Java Activity

配置好清单之后，我们需要创建应用的 Java 部分。尽管大部分 Vulkan 代码运行在原生 C++ 中，我们仍然需要一个 Java Activity 作为应用的入口。

我们的 Vulkan 应用将使用 Android Game SDK 提供的 GameActivity，而不是传统的 NativeActivity。这种现代做法性能更好，并提供了专为游戏和图形密集型应用设计的功能：

[source,java]
----
package com.vulkan.tutorial;

import android.os.Bundle;
import android.view.WindowManager;
import com.google.androidgamesdk.GameActivity;

public class VulkanActivity extends GameActivity {
    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);

        // Keep the screen on while the app is running
        getWindow().addFlags(WindowManager.LayoutParams.FLAG_KEEP_SCREEN_ON);
    }

    // Load the native library
    static {
        System.loadLibrary("vulkan_tutorial_android");
    }
}
----

关键点：

* 我们继承 Android Game SDK 中的 GameActivity，它在 Java 与原生代码之间提供更优化的桥接。
* 与 NativeActivity 相比，GameActivity 为游戏和图形密集型应用提供了更好的性能。
* 我们加载包含 Vulkan 实现的原生库（“vulkan_tutorial_android”）。

=== CMake 配置

Gradle 负责整个 Android 构建流程，而原生 C++ 代码则由 CMake 构建。我们在这里配置 Vulkan 环境、编译着色器，并链接所需的库。

我们来看 CMakeLists.txt 文件，它是原生代码配置的核心：

[source,cmake]
----
cmake_minimum_required(VERSION 3.22.1)

project(vulkan_tutorial_android)

# Set the path to the main CMakeLists.txt relative to this file
set(MAIN_CMAKE_PATH "${CMAKE_CURRENT_SOURCE_DIR}/../../../../../../CMakeLists.txt")

# Find the Vulkan package
find_package(Vulkan REQUIRED)

# Set up shader compilation tools
add_executable(glslang::validator IMPORTED)
find_program(GLSLANG_VALIDATOR "glslangValidator" HINTS $ENV{VULKAN_SDK}/bin REQUIRED)
set_property(TARGET glslang::validator PROPERTY IMPORTED_LOCATION "${GLSLANG_VALIDATOR}")

# Define shader building function
function(add_shaders_target TARGET)
  cmake_parse_arguments("SHADER" "" "CHAPTER_NAME" "SOURCES" ${ARGN})
  set(SHADERS_DIR ${SHADER_CHAPTER_NAME}/shaders)
  add_custom_command(
    OUTPUT ${SHADERS_DIR}
    COMMAND ${CMAKE_COMMAND} -E make_directory ${SHADERS_DIR}
  )
  add_custom_command(
    OUTPUT ${SHADERS_DIR}/frag.spv ${SHADERS_DIR}/vert.spv
    COMMAND glslang::validator
    ARGS --target-env vulkan1.0 ${SHADER_SOURCES} --quiet
    WORKING_DIRECTORY ${SHADERS_DIR}
    DEPENDS ${SHADERS_DIR} ${SHADER_SOURCES}
    COMMENT "Compiling Shaders"
    VERBATIM
  )
  add_custom_target(${TARGET} DEPENDS ${SHADERS_DIR}/frag.spv ${SHADERS_DIR}/vert.spv)
endfunction()

# Include the game-activity library
find_package(game-activity REQUIRED CONFIG)
include_directories(${ANDROID_NDK}/sources/android/game-activity/include)

# Set C++ standard to match the main project
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# (Optional) Add the Vulkan C++ module when ENABLE_CPP20_MODULE=ON
add_library(VulkanCppModule SHARED)
target_compile_definitions(VulkanCppModule
    PUBLIC VULKAN_HPP_DISPATCH_LOADER_DYNAMIC=1 VULKAN_HPP_NO_STRUCT_CONSTRUCTORS=1
)
target_include_directories(VulkanCppModule
    PRIVATE
    "${Vulkan_INCLUDE_DIR}"
)
target_link_libraries(VulkanCppModule
    PUBLIC
    ${Vulkan_LIBRARIES}
)
set_target_properties(VulkanCppModule PROPERTIES CXX_STANDARD 20)

# Set up the C++ module file set
target_sources(VulkanCppModule
    PUBLIC
    FILE_SET cxx_modules TYPE CXX_MODULES
    BASE_DIRS
    "${Vulkan_INCLUDE_DIR}"
    FILES
    "${Vulkan_INCLUDE_DIR}/vulkan/vulkan.cppm"
)

# Set up shader compilation for 34_android
set(SHADER_SOURCE_DIR "${CMAKE_CURRENT_SOURCE_DIR}/../../../../../../attachments")
set(SHADER_OUTPUT_DIR "${CMAKE_CURRENT_BINARY_DIR}/shaders")
file(MAKE_DIRECTORY ${SHADER_OUTPUT_DIR})

# Copy shader source files to the build directory
configure_file(
    "${SHADER_SOURCE_DIR}/27_shader_depth.frag"
    "${SHADER_OUTPUT_DIR}/27_shader_depth.frag"
    COPYONLY
)
configure_file(
    "${SHADER_SOURCE_DIR}/27_shader_depth.vert"
    "${SHADER_OUTPUT_DIR}/27_shader_depth.vert"
    COPYONLY
)

# Compile shaders
set(SHADER_SOURCES "${SHADER_OUTPUT_DIR}/27_shader_depth.frag" "${SHADER_OUTPUT_DIR}/27_shader_depth.vert")
add_shaders_target(android_shaders CHAPTER_NAME "${SHADER_OUTPUT_DIR}" SOURCES ${SHADER_SOURCES})

# Add the main native library
add_library(vulkan_tutorial_android SHARED
    ${CMAKE_CURRENT_SOURCE_DIR}/../../../../../../attachments/34_android.cpp
    game_activity_bridge.cpp
)

# Add dependency on shader compilation
add_dependencies(vulkan_tutorial_android android_shaders)

# Set include directories
target_include_directories(vulkan_tutorial_android PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}
    ${Vulkan_INCLUDE_DIR}
    ${ANDROID_NDK}/sources/android/game-activity/include
)

# Link against libraries
target_link_libraries(vulkan_tutorial_android
    VulkanCppModule
    game-activity::game-activity
    android
    log
    ${Vulkan_LIBRARIES}
)
----

关键点：

* 我们查找 Vulkan 包，并引入 game-activity 库，而不是 native_app_glue。
* 我们配置着色器编译工具，并定义一个编译着色器的函数。
* 我们把 C{pp} 标准设为 C{pp}20，并在启用模块时可选地创建 Vulkan C{pp} 模块（推荐）。
* 我们为 34_android 章节配置着色器编译，从主项目复制着色器源文件。
* 我们添加主原生库，它使用主项目中的 34_android.cpp 文件，以及一个与 GameActivity 连接的桥接文件。
* 我们链接所需的库，其中包括 game-activity。

== 原生实现

构建配置就绪之后，我们深入看看在 Android 上驱动 Vulkan 应用的原生 C++ 代码。真正的好戏就在这里：我们会看到如何把现有的 Vulkan 代码适配到 Android，同时把平台相关的改动降到最少。

这种做法的一大优势是代码复用。我们没有为桌面和 Android 分别维护代码库，而是把项目组织成尽可能共享代码的形式：

1. *34_android.cpp*：这就是主项目中使用的同一个文件，包含核心的 Vulkan 实现。复用它，可以确保渲染代码在各平台上完全一致。

2. *game_activity_bridge.cpp*：这个很小的桥接文件把 Android 的 GameActivity 连接到核心 Vulkan 代码，负责平台相关的初始化和事件处理。

这种关注点分离让我们可以专注于 Vulkan 实现，而不必陷在平台相关的细节里。当我们改进渲染代码时，桌面版和 Android 版都会自动受益。

=== GameActivity 桥接

我们仔细看看桥接代码，它把 Java 的 GameActivity 与原生 Vulkan 实现连接起来，是关键的一环。这个文件虽小却至关重要，负责在 Android 基于 Java 的 Activity 生命周期与我们的 C++ 代码之间做转接：

[source,cpp]
----
#include <game-activity/GameActivity.h>
#include <game-activity/native_app_glue/android_native_app_glue.h>
#include <android/log.h>

// Define logging macros
#define LOGI(...) ((void)__android_log_print(ANDROID_LOG_INFO, "VulkanTutorial", __VA_ARGS__))
#define LOGW(...) ((void)__android_log_print(ANDROID_LOG_WARN, "VulkanTutorial", __VA_ARGS__))
#define LOGE(...) ((void)__android_log_print(ANDROID_LOG_ERROR, "VulkanTutorial", __VA_ARGS__))

// Forward declaration of the main entry point
extern "C" void android_main(android_app* app);

// GameActivity entry point
extern "C" {
    void GameActivity_onCreate(GameActivity* activity) {
        LOGI("GameActivity_onCreate");

        // Create an android_app structure
        android_app* app = new android_app();
        memset(app, 0, sizeof(android_app));

        // Set up the android_app structure
        app->activity = activity;
        app->window = activity->window;

        // Call the original android_main function
        android_main(app);

        // Clean up
        delete app;
    }
}
----

这段桥接代码会：

1. 创建一个与我们的 Vulkan 代码兼容的 android_app 结构体
2. 建立 GameActivity 与我们的代码之间必要的连接
3. 调用 34_android.cpp 文件中的 android_main 函数

=== Android 入口点

桥接代码创建好 android_app 结构体后，会调用 android_main 函数，它是原生代码的入口。这个函数定义在 34_android.cpp 文件中，类似于桌面应用里的 main() 函数：

我们看看如何从这个入口初始化 Vulkan 应用：

[source,cpp]
----

=== 创建 Vulkan 表面

我们的 Vulkan 实现中，最关键的平台差异之一就是表面的创建方式。在桌面上，我们用 GLFW 创建窗口和表面；在 Android 上，则需要用 VK_KHR_android_surface 扩展从原生的 Android 窗口创建表面。

下面是在 Android 上创建 Vulkan 表面的代码：

[source,cpp]
----
void createSurface() {
    VkSurfaceKHR _surface;
    VkResult result = VK_SUCCESS;

    // Create Android surface
    result = vkCreateAndroidSurfaceKHR(
        *instance,
        &(VkAndroidSurfaceCreateInfoKHR{
            .sType = VK_STRUCTURE_TYPE_ANDROID_SURFACE_CREATE_INFO_KHR,
            .pNext = nullptr,
            .flags = 0,
            .window = androidApp->window
        }),
        nullptr,
        &_surface
    );

    if (result != VK_SUCCESS) {
        throw std::runtime_error("Failed to create Android surface");
    }

    surface = vk::raii::SurfaceKHR(instance, _surface);
}
----

另一个重要的平台相关方面是事件处理。与桌面应用相比，Android 应用的生命周期不同——它们随时可能被系统暂停、恢复或终止。我们需要正确处理这些事件，确保 Vulkan 资源得到妥善管理。

static void handleAppCommand(android_app* app, int32_t cmd) {
    auto* vulkanApp = static_cast<VulkanApplication*>(app->userData);
    switch (cmd) {
        case APP_CMD_INIT_WINDOW:
            // Window created, initialize Vulkan
            if (app->window != nullptr) {
                vulkanApp->initVulkan();
            }
            break;
        case APP_CMD_TERM_WINDOW:
            // Window destroyed, clean up Vulkan
            vulkanApp->cleanup();
            break;
        default:
            break;
    }
}

== 跨平台实现

虽然到目前为止我们关注的是 Android 专属代码，但我们的做法允许维护一套同时适用于桌面和 Android 平台的代码库。这得益于对预处理指令和平台相关抽象的谨慎使用。

=== 平台检测

跨平台方案的第一步是检测当前正在为哪个平台构建。我们用预处理指令检查平台相关的预定义宏：

[source,cpp]
----
// Platform detection
#if defined(__ANDROID__)
    #define PLATFORM_ANDROID 1
#else
    #define PLATFORM_DESKTOP 1
#endif
----

这种做法利用了标准预定义宏 `__ANDROID__`，在为 Android 平台构建时编译器会自动定义它。随后这些平台宏会在代码中用于条件编译平台相关的代码。

=== 一致的类结构

为了保持代码库干净一致，我们在两个平台上使用相同的类名（`HelloTriangleApplication`）。这让代码更易理解，也减少了平台相关分支的需要：

[source,cpp]
----
// Cross-platform application class
class HelloTriangleApplication {
public:
#if PLATFORM_DESKTOP
    // Desktop constructor
    HelloTriangleApplication() {
        // No Android-specific initialization needed
    }
#else
    // Android constructor
    HelloTriangleApplication(android_app* app) : androidApp(app) {
        // Android-specific initialization
    }
#endif
    // ... rest of the class ...
};
----

=== 平台相关的头文件包含

不同平台需要不同的头文件。我们用预处理指令引入合适的头文件：

[source,cpp]
----
// Platform-specific includes
#if PLATFORM_ANDROID
    // Android-specific includes
    #include <android/log.h>
    #include <android_native_app_glue.h>
    #include <android/asset_manager.h>
    #include <android/asset_manager_jni.h>
#else
    // Desktop-specific includes
    #define GLFW_INCLUDE_VULKAN
    #include <GLFW/glfw3.h>
    #include <stb_image.h>
    #include <tiny_obj_loader.h>
#endif
----

=== 跨平台文件加载

文件加载是桌面平台与 Android 平台之间的关键差异之一。在桌面上，我们从文件系统加载文件；在 Android 上，则从 APK 的资产中加载。我们编写了一个在两个平台上都能工作的跨平台文件加载函数：

[source,cpp]
----
// Cross-platform file reading function

#if PLATFORM_ANDROID
    // On Android, use asset manager if provided
    if (assetManager.has_value() && *assetManager != nullptr) {
        // Open the asset

    }

=== 平台相关的入口点

每个平台都有自己的入口。在桌面上使用标准的 `main()` 函数，在 Android 上则使用 `android_main()` 函数：

[source,cpp]
----
// Platform-specific entry point
#if PLATFORM_ANDROID
// Android main entry point
void android_main(android_app* app) {
    // Android-specific initialization
    try {
        HelloTriangleApplication vulkanApp(app);
        vulkanApp.run();
    } catch (const std::exception& e) {
        LOGE("Exception caught: %s", e.what());
    }
}
#else
// Desktop main entry point
int main() {
    try {
        HelloTriangleApplication app;
        app.run();
    } catch (const std::exception& e) {
        std::cerr << e.what() << std::endl;
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
#endif
----

=== 构建系统集成

我们的跨平台方案利用了编译器内置的平台检测能力。由于为 Android 构建时编译器会自动定义 `__ANDROID__` 宏，我们无需在构建系统中显式定义平台宏。

这种做法有几个好处：

1. *简单*：无需在 CMake 文件中维护平台相关的编译定义。
2. *可靠*：我们依赖编译器的标准行为，而不是自定义定义。
3. *易维护*：构建系统配置更少，潜在的失败点也更少。

借助编译器的预定义宏，我们可以维护一套同时适用于桌面和 Android 平台的代码库，平台相关代码极少。当我们改进渲染代码时，桌面版和 Android 版都会自动受益。

== Android 上的着色器处理

核心原生实现讲完之后，我们来看看 Android 上 Vulkan 开发的另一个重要方面：着色器处理。着色器是任何 Vulkan 应用的关键部分，我们需要确保它们在 Android 上被正确编译和加载。

在我们的做法中，着色器在构建过程中于本地编译，与主项目中的做法类似。这一策略有几个明显优势：

1. *一致性*：桌面和 Android 构建使用相同的着色器源文件，确保各平台的视觉效果一致。
2. *易维护*：需要更新着色器时，只需改动一处，桌面版和 Android 版都会受益。
3. *构建期校验*：着色器编译错误在构建过程中就会被发现，而不是留到运行时，调试起来容易得多。

=== 本地着色器编译

我们已配置好 CMake，在构建过程中于本地编译着色器：

1. *定义着色器构建函数*：
+
[source,cmake]
----
function(add_shaders_target TARGET)
  cmake_parse_arguments("SHADER" "" "CHAPTER_NAME" "SOURCES" ${ARGN})
  set(SHADERS_DIR ${SHADER_CHAPTER_NAME}/shaders)
  add_custom_command(
    OUTPUT ${SHADERS_DIR}
    COMMAND ${CMAKE_COMMAND} -E make_directory ${SHADERS_DIR}
  )
  add_custom_command(
    OUTPUT ${SHADERS_DIR}/frag.spv ${SHADERS_DIR}/vert.spv
    COMMAND glslang::validator
    ARGS --target-env vulkan1.0 ${SHADER_SOURCES} --quiet
    WORKING_DIRECTORY ${SHADERS_DIR}
    DEPENDS ${SHADERS_DIR} ${SHADER_SOURCES}
    COMMENT "Compiling Shaders"
    VERBATIM
  )
  add_custom_target(${TARGET} DEPENDS ${SHADERS_DIR}/frag.spv ${SHADERS_DIR}/vert.spv)
endfunction()
----

2. *从主项目复制着色器源文件*：
+
[source,cmake]
----

set(SHADER_OUTPUT_DIR "${CMAKE_CURRENT_BINARY_DIR}/shaders")

)
configure_file(
    "${SHADER_SOURCE_DIR}/27_shader_depth.vert"
    "${SHADER_OUTPUT_DIR}/27_shader_depth.vert"

)
----

3. *编译着色器*：
+

----

=== 以跨平台方式加载资产

统一的 readFile 函数让跨平台加载资产变得简单。下面是我们用它加载着色器文件的方式：

[source,cpp]
----
// Load shader files using cross-platform function
#if PLATFORM_ANDROID
std::optional<AAssetManager*> optionalAssetManager = assetManager;
#else
std::optional<AAssetManager*> optionalAssetManager = std::nullopt;
#endif
std::vector<char> vertShaderCode = readFile("shaders/vert.spv", optionalAssetManager);
std::vector<char> fragShaderCode = readFile("shaders/frag.spv", optionalAssetManager);
----

加载纹理图像和模型文件也用同样的方式：

[source,cpp]
----
// Load texture image
#if PLATFORM_ANDROID
std::optional<AAssetManager*> optionalAssetManager = assetManager;
std::vector<char> imageData = readFile(TEXTURE_PATH, optionalAssetManager);
// Process the image data...
#else
// Load directly from filesystem
// ...
#endif
----

这种统一的做法兼得两者之长：两个平台使用相同的代码结构，平台差异由 readFile 函数自身处理。这让代码更易维护、更易理解。

== 构建与运行

Android 项目的各个组件都已就位，现在我们把它们串起来，在 Android 设备上运行 Vulkan 应用。

== 结语

本章我们探索了如何通过适配 Android，把 Vulkan 应用从桌面带到移动端。我们看到，虽然 Vulkan 核心 API 在各平台上保持一致，但周边生态需要针对平台的适配。

我们的做法体现了若干关键原则，你可以把它们用到自己的 Vulkan 项目中：

1. *代码复用*：通过合理组织项目结构，我们可以在桌面和 Android 平台上使用同一套核心渲染代码（34_android.cpp），把重复和维护开销降到最低。

2. *现代 Android 集成*：我们利用 Android Game SDK 的 GameActivity，相比旧的 NativeActivity 方案，性能更好、集成更顺畅。

3. *高效的资产管理*：我们不复制资产，而是从主项目引用它们，既保证一致性，又减小 APK 体积。

4. *本地着色器编译*：在构建过程中编译着色器，可以尽早发现错误，并确保跨平台的兼容性。

5. *最少的平台相关代码*：我们把平台相关代码隔离在一个小的桥接文件中，让核心 Vulkan 实现保持干净、便于移植。

这种做法不仅让应用更易维护和更新，也为将来扩展到其他平台打下坚实基础。当你改进核心渲染代码时，桌面版和 Android 版都会自动受益。

完整的 Android 示例可以在 attachments/android 目录中找到。你可以随意把它当作模板，用于自己的 Android Vulkan 项目。
