== Vulkan的起源
与之前的图形API一样，Vulkan也被设计成基于 https://en.wikipedia.org/wiki/Graphics_processing_unit[GPU]的跨平台抽象层。这些API的共同问题在于，它们设计之初的图形硬件功能大多是可配置的固定功能。程序员必须以标准格式提供顶点数据，并且在光照和着色选项方面完全受制于GPU制造商。

随着显卡架构的日趋成熟，它们开始提供越来越多的可编程功能。所有这些新功能都必须以某种方式与现有的API集成。这导致抽象层不够理想，并且图形驱动程序端需要进行大量猜测才能将程序员的意图映射到现代图形架构上。这就是为什么会有如此多的驱动程序更新来提升游戏性能，有时甚至能带来显著的性能提升。由于这些驱动程序的复杂性，应用程序开发人员还需要处理不同供应商之间的不一致性，例如 https://en.wikipedia.org/wiki/Shader[着色器]可接受的语法。除了这些新功能之外，过去十年还见证了大量配备强大图形硬件的移动和嵌入式设备的涌现。这些移动GPU根据其能耗和空间需求采用了不同的架构。例如， https://en.wikipedia.org/wiki/Tiled_rendering[分块渲染]就受益于性能的提升，这可以通过赋予程序员对此功能的更多控制权来实现。这些API的年代久远带来的另一个限制是多线程支持有限，这可能会导致CPU端的瓶颈。

Vulkan 从零开始为现代图形架构设计，从而解决了这些问题。它通过允许程序员使用功能更丰富但更详细的 API 清晰地指定其意图，降低了驱动程序的开销，并允许多个线程并行创建和提交命令。它通过切换到使用单一编译器的标准化字节码格式，减少了着色器编译中的不一致性。最后，它将图形和计算功能统一到一个 API 中，从而充分利用了现代显卡的通用处理能力。

=== 编码规范
所有 Vulkan 函数、枚举和结构体都定义在 vulkan.h头文件中，该头文件包含在LunarG 开发的Vulkan SDK中 。我们将在下一章介绍如何安装此 SDK。在本教程中，我们将使用 vulkan.hpp 头文件提供的 C++ Vulkan API，该头文件包含在官方 https://lunarg.com/vulkan-sdk/[Vulkan SDK] 中。与原始 C Vulkan API 相比，该头文件提供了一个类型安全、兼容 RAII 且更符合人体工程学的接口，同时仍然保持与底层 Vulkan 函数和结构体的紧密底层映射。

== 画三角形需要什么条件
接下来，我们将概述在运行良好的 Vulkan 程序中渲染三角形的所有步骤。这里介绍的所有概念将在后续章节中详细阐述。这里只是为了提供一个整体框架，以便您将所有单独的组件联系起来。

=== 步骤 1 - 实例和物理设备选择

Vulkan 应用首先需要配置 Vulkan API里的 `vk::raii::Instance`。创建 Vulkan 实例时，需要描述您的应用以及您将使用的所有 API 扩展。创建实例后，您可以查询 Vulkan 支持的硬件，并选择一个或多个``vk::raii::PhysicalDevice``用于执行操作。您可以查询诸如显存大小和设备功能之类的属性，以选择所需的设备，例如，优先使用独立显卡。

=== 步骤 2 - 逻辑设备和队列系列

选择合适的硬件设备后，您需要创建一个 ``vk::raii::Device``逻辑设备，在其中更具体地描述您将使用的物理设备特性，例如多视口渲染和 64 位浮点运算。您还需要指定要使用的队列族。大多数使用 Vulkan 执行的操作（例如绘制命令和内存操作）都是通过提交到``vk::raii::Queue``队列来异步执行的。队列是从队列族中分配的，每个队列族在其队列中支持一组特定的操作。例如，可以有单独的队列族用于图形、计算和内存传输操作。队列族的可用性也可以作为选择物理设备的一个区分因素。支持 Vulkan 的设备可能不提供任何图形功能；但是，目前所有支持 Vulkan 的显卡通常都支持我们感兴趣的所有队列操作。

=== 步骤 3 - 窗口表面和交换链

除非您只对离屏渲染感兴趣，否则您需要创建一个窗口来显示渲染后的图像。可以使用原生平台 API 或 https://www.glfw.org/[GLFW]和 https://www.libsdl.org/[SDL]等库来创建窗口。本教程将使用 GLFW，但更多相关内容将在下一章介绍。

我们还需要两个部分才能真正渲染到窗口：窗口表面（`vk::raii::SurfaceKHR`）和交换链（`vk::raii::SwapchainKHR`）。注意KHR后缀，这意味着这些对象是 Vulkan 扩展的一部分。Vulkan API 本身完全与平台无关，因此我们需要使用标准化的 WSI（窗口系统接口）扩展来与窗口管理器交互。窗口表面是对窗口的跨平台抽象，用于进行渲染，通常通过提供对原生窗口句柄的引用来实例化，例如HWND在 Windows 上。幸运的是，GLFW 库有一个内置函数来处理这些平台特定的细节。

交换链是一组渲染目标。它的基本目的是确保当前正在渲染的图像与屏幕上显示的图像不同。这对于确保只显示完整的图像至关重要。每次绘制帧时，我们都必须请求交换链提供要渲染的图像。绘制完一帧后，图像会返回给交换链，以便在某个时刻呈现到屏幕上。渲染目标的数量以及将完成的图像呈现到屏幕的条件取决于呈现模式。常见的呈现模式包括双缓冲（垂直同步）和三缓冲。我们将在交换链创建章节中详细介绍这些内容。

某些平台允许您通过 `VK_KHR_display` 和 `VK_KHR_display_swapchain` 扩展直接渲染到显示器上，而无需与任何窗口管理器交互。这些扩展允许您创建一个代表整个屏幕的表面，例如，可用于实现您自己的窗口管理器。

=== 步骤 4 - 交换链图像视图

要绘制从交换链获取的图像，我们通常会用``vk::raii::ImageView``包装交换链图像。图像视图引用图像的特定部分，例如用于颜色写入。由于交换链中可能存在不同的图像，我们会预先为每个图像创建一个图像视图，并在绘制时选择正确的图像。

=== 步骤 5 - 动态渲染概述

在早期版本的 Vulkan 中，渲染通道定义了应如何配合帧缓冲执行渲染操作，指定所使用的图像类型（例如颜色、深度）以及应如何处理其内容（例如清除、加载或存储）。`vk::raii::RenderPass` 用于定义子通道和附件使用方式，而 `vk::raii::Framebuffer` 则用于将特定的图像视图绑定到这些附件上。

然而，借助动态渲染（Vulkan 1.3 引入），您完全不再需要创建 `vk::raii::Framebuffer`。动态渲染免除了预定义渲染通道和帧缓冲的需要，允许您在录制命令时直接指定渲染附件。这使 API 简单得多，因为我们可以即时定义渲染目标，而不必担心管理帧缓冲带来的开销。

使用动态渲染时，您不再需要预定义 `vk::raii::RenderPass` 或 `vk::raii::Framebuffer`。相反，您在开始录制命令时指定渲染附件，使用 `vk::raii::CommandBuffer::beginRendering` 和 `vk::RenderingInfo` 之类的结构体来动态提供所有必要的附件信息。

在我们最初的三角形渲染应用程序中，我们将使用动态渲染来指定单个图像作为颜色目标，并指示 Vulkan 在绘制前将其清除为纯色。

=== 步骤 6 - 图形管线
Vulkan 中的图形管线是通过创建``vk::raii::Pipeline``对象来设置的。它描述了显卡的可配置状态，例如视口大小和深度缓冲区操作，以及使用``vk::raii::ShaderModule``对象实现的可编程状态。这些``vk::raii::ShaderModule``对象由着色器字节码创建。在传统方式种，驱动程序还需要知道管线中将使用哪些渲染目标，这可以通过引用渲染通道来指定。

与现有 API 相比，Vulkan 最显著的特点之一是几乎所有图形管线的配置都需要预先设置。这意味着，如果您想切换到不同的着色器或稍微更改顶点布局，则需要完全重新创建图形管线。您必须预先创建大量对象``vk::Pipeline``，以满足渲染操作所需的各种组合。只有一些基本配置（例如视口大小和清除颜色）可以动态更改。所有状态也都需要显式描述；例如，没有默认的颜色混合状态。

好消息是，由于采用了相当于预编译而非即时编译的方式，驱动程序有更多优化空间。运行时性能也更可预测，因为像切换到不同的图形管线这样的大型状态变更会被非常明确地处理。

=== 步骤 7 - 命令池和命令缓冲区
如前所述，Vulkan 中许多需要执行的操作（例如绘制操作）都需要提交到队列中。这些操作必须先记录到``vk::raii::CommandBuffer``命令缓冲区中才能提交。这些命令缓冲区是从与特定队列族关联的``vk::raii::CommandPool``中分配的。要在动态渲染之前绘制一个三角形，我们需要记录一个包含以下操作的命令缓冲区：

* 开始渲染过程
* 绑定图像管线
* 画三个顶点
* 渲染过程结束

然而，动态渲染改变了这一切。你不再需要“开始”和“结束”渲染过程，而是在开始渲染时直接定义``vk::BeginRendering``渲染附件。

这简化了流程，允许您动态指定所需的附件，使其更适用于动态选择交换链图像的场景。因此，您无需为交换链中的每个图像记录命令缓冲区，也无需在每一帧重复记录相同的命令缓冲区。操作变得更加精简高效，使 Vulkan 在处理渲染场景时更加灵活。

*步骤 8 - 主循环*
现在绘图命令已经封装到命令缓冲区中，主循环就相当直接了。我们首先用 `device.acquireNextImageKHR` 从交换链获取一张图像。然后，我们可以为该图像选择相应的命令缓冲区，并用 `graphicsQueue.submit()` 执行它。最后，我们用 `presentQueue.presentKHR(presentInfo)` 将图像交还给交换链，以便呈现到屏幕上。

提交到队列的操作是异步执行的。因此，我们必须使用信号量等同步对象来确保正确的执行顺序。绘制命令缓冲区的执行必须设置为等待图像获取完成；否则，可能会出现我们开始渲染的图像仍在被读取以用于屏幕呈现的情况。而 `presentQueue.presentKHR(presentInfoKHR)` 调用又需要等待渲染完成，为此我们将使用第二个信号量，它在渲染完成后发出信号。

=== 概括
这次快速入门讲解应该能让您在绘制第一个三角形之前对相关工作有一个基本的了解。实际的程序包含更多步骤，例如分配顶点缓冲区、创建统一缓冲区以及上传纹理图像，这些内容将在后续章节中介绍。不过，我们将从简单的入手，因为 Vulkan 的学习曲线本身就相当陡峭。需要注意的是，我们将采用一种“作弊”的方法，即首先将顶点坐标嵌入到顶点着色器中，而不是使用顶点缓冲区。这是因为管理顶点缓冲区需要先熟悉命令缓冲区。

简而言之，要画出第一个三角形，我们需要：

* 创建实例
* 选择支持的显卡（`PhysicalDevice`）
* 创建用于绘图和演示的``Queue``和``Device``
* 创建窗口、窗口表面和交换链
* 将交换链图像包装起来``vk::raii::ImageView``
* 设置动态渲染
* 设置图形管线
* 分配并记录一个命令缓冲区，其中包含每个可能的交换链映像的绘制命令。
* 通过获取图像、提交正确的绘制命令缓冲区并将图像返回到交换链来绘制帧。

步骤很多，但每个步骤的目的都会在接下来的章节中得到清晰的阐述。如果您对某个步骤与整个程序的关系感到困惑，请回顾本章内容。

== API概念
本章最后简要概述了 Vulkan API 在底层是如何构建的。

例如，对象的创建通常遵循以下模式：
[source,c++]
----
vk::XXXCreateInfo createInfo{};
createInfo.sType = vk::StructureType::eXXXCreateInfo;
createInfo.pNext = nullptr;
createInfo.foo = ...;
createInfo.bar = ...;

vk::XXX object;


try {
    object = device.createXXX(createInfo);
} catch (vk::SystemError& err) {
    std::cerr << "Failed to create object: " << err.what() << std::endl;
    return false;
}
----

Vulkan 中的许多结构体都需要您在成员中显式指定sType结构体类型。pNext成员可以指向扩展结构体，并且在本教程中始终如此。创建或销毁对象的函数会有一个参数，允许您使用自定义驱动程序内存分配器，本教程中也不会涉及这部分内容。

几乎所有函数都会返回一个值``vk::Result``，该值要么是空值``vk::Result::eSuccess`` ，要么是错误代码。规范中描述了每个函数可以返回哪些错误代码以及它们的含义。

此类调用失败会由 C++ 异常报告。异常会返回更多错误信息，包括一个``vk::Result``. 这使我们能够从一次调用中检查多个命令，并保持命令语法的简洁性。

=== 验证层
如前所述，Vulkan 的设计目标是高性能和低驱动开销。因此，默认情况下它包含的错误检查和调试功能非常有限。如果您操作失误，驱动程序通常会崩溃而不是返回错误代码；更糟糕的是，它在您的显卡上似乎可以正常工作，但在其他显卡上却完全失效。

Vulkan 允许您通过名为“验证层”的功能启用全面的检查 。验证层是一段代码，可以插入到 API 和图形驱动程序之间，用于执行诸如对函数参数进行额外检查以及跟踪内存管理问题等操作。一个重要的优势是，您可以在开发期间启用它们，然后在发布应用程序时完全禁用它们，从而实现零开销。任何人都可以编写自己的验证层，但 LunarG 的 Vulkan SDK 提供了一组标准的验证层，我们将在本教程中使用这些验证层。您还需要注册一个回调函数来接收来自验证层的调试消息。

由于 Vulkan 对每个操作都非常明确，并且验证层非常广泛，因此与 OpenGL 和 Direct3D 相比，找出屏幕变黑的原因实际上要容易得多
