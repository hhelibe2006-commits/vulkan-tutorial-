= 不透明度微图：面向真实世界的更智能阴影
:imagesdir: ../../../images

到这一步，你已经完成了简易游戏引擎教程，也构建出了真正漂亮的东西。你的光线追踪阴影以物理上的精确度落在地板和墙壁上。实心物体投下实心的轮廓；而柔和阴影也确实让这些阴影更好看。光知道几何体在哪里，黑暗便随之而来。对于简单的建筑场景——一间方盒子房间、一张桌子、几把椅子——结果近乎完美，而且一切顺利，毫无波折。

但真实世界并不是由盒子和椅子组成的。走到户外，你会立刻遇到一个拒绝配合简单光线-三角形求交的世界。树木不会投下边缘锐利的矩形阴影。锻铁栅栏不会均匀地遮挡光线。窗帘飘动时会漏出光的缝隙。头发不是一个表面，而是上百万根半透明的发丝。自然的视觉丰富性——以及模仿自然的人类世界——几乎完全来自那些几何上简单、光学上复杂的物体。

在实时渲染中，我们用一种叫 **alpha 测试**（有时也叫 alpha 遮罩）的技术来处理这种复杂性。我们并不用真实几何体为树上的每片叶子建模，而是取一个宽大的平面四边形，把叶子纹理画上去。纹理带有一个 **alpha 通道**——取值从 0 到 1，表示每个纹素有多不透明。在叶子的边缘，alpha 为 0：透明，忽略这个像素。在叶子的主体部分，alpha 为 1：不透明，这个像素存在。借助这一技巧，单个平面三角形就能表现出令人信服的复杂轮廓。

在光栅化期间，alpha 测试的代价很低。GPU 在每个屏幕像素上计算 alpha，直接丢弃透明的那些。对阴影贴图也有类似的捷径：只写深度的、带 alpha 测试的阴影通道，已经被充分理解和充分优化。

光线追踪改变了这个等式。在光线追踪阴影系统中，阴影光线不是把纹理投影到屏幕上——它在三维空间中与几何体求交。当这条光线击中一片叶子三角形时，它不能只问「我击中了吗？」它必须问「我击中的东西在这个确切位置上真的是实心的吗？」要回答这个问题，它必须在精确的交点处查询 alpha 纹理。而且对于光线可能穿过的每个三角形，它都要这么做。一棵树就有成千上万个叶子三角形，场景中又有许多棵树，还要在高分辨率下每像素投射多条阴影光线——算下来数字很快就变得惊人。

这不是一个假想的问题。带 alpha 测试的植被是实时光线追踪场景中最常见的性能瓶颈来源之一。性能分析工具一再揭示：只要画面中出现自然景物，占满 GPU 时间的就总是 any-hit 着色器调用——也就是负责这次 alpha 查询的那个着色器阶段。

**不透明度微图（Opacity Micromaps，OMM）** 是 Vulkan 对这个问题的回答，通过 `VK_KHR_opacity_micromap` 扩展提供。核心思想很优雅，而且一旦理解就几乎觉得理所当然：与其强迫 GPU 在运行时去发现每个三角形每一部分的不透明度，不如在绘制第一帧之前就把这些信息预先烘焙进 GPU 的加速结构。我们把每个三角形细分成由微小**微三角形**组成的网格，把每一个分类为永久不透明、永久透明，或边界情况未知。硬件遍历单元直接读取这个分类，不运行任何着色器代码，就能立即判断光线是否被挡住。

结果是，昂贵的 any-hit 着色器触发次数大幅减少——只在那圈很窄的边缘像素上触发，那里确实存在歧义。对叶子表面的绝大部分来说，答案都是预先知道的。硬件在一个周期内就能据此行动。

本课程会给你完整的概念理解：这个问题为什么存在、微图如何解决它，以及在简易引擎的源代码中实现是什么样子。我们先从阴影自身的视觉语言讲起——阴影为什么长成那样，以及为什么植被打破了快速阴影算法所依赖的假设。接着我们会深入到 GPU 的光线遍历硬件，弄清性能代价究竟来自哪里。然后我们从零开始构建微图这个概念，依次走过细分模型、2 状态与 4 状态分类格式，以及微图数据挂接到加速结构上的方式。最后，我们会浏览引擎中的 `OpacityMicromapBuilder` 实现，并讨论这项优化在什么时候值得采用——以及什么时候不值得。

你不需要事先了解 GPU 硬件内部细节，但应当熟悉光线追踪的基础：BVH 是什么、阴影光线如何工作、加速结构起什么作用。如果这些概念对你来说已经扎实，就可以开始了。
