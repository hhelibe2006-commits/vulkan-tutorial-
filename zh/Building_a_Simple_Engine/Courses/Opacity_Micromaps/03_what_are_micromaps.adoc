= 微图：教导硬件它本应知道的事

== 核心思想

迄今为止讨论的一切都汇聚到同一个洞见：GPU 正在做昂贵的运行时工作，去发现那些完全可以提前知晓的信息。叶子的 alpha 纹理不会动，栅栏网格的不透明度分布也不会逐帧改变。如果我们能把这类信息直接烘焙进加速结构本身——也就是硬件用于 BVH 遍历的同一套数据结构——硬件就完全不必调用任何着色器，就能做出不透明度判定。

这就是**不透明度微图**的完整描述：一种附着在 GPU 加速结构中三角形网格上的数据结构，它把每个三角形细分成由更小三角形组成的规则网格，并为每个小三角形赋予预先计算好的不透明度状态。「微」（micro）这个词用得恰如其分：它们并不是光线追踪器必须遍历的额外几何三角形，而是子三角形分类，遍历硬件把它们当作元数据读取，用以加速判断某次光线-三角形相交是否代表真正的命中。

== 两种格式：2 态与 4 态

`VK_KHR_opacity_micromap` 定义了两种不透明度微图格式。选择哪种格式，取决于你的 alpha 内容在边界处需要多高的精度。

**2 态格式**（`VK_OPACITY_MICROMAP_FORMAT_2_STATE_EXT`）为每个微三角形存储一个比特。每个微三角形要么是透明（0），要么是不透明（1）。这种二分类是最简单的模型：永远不调用任何着色器——硬件直接依据存储的比特确认或丢弃每次命中。当你完全掌控 alpha 内容、并能保证没有哪个微三角形真正跨越 alpha 边界时，2 态格式最为理想；或者当你愿意接受强制二分类带来的少量视觉误差时，也是如此。

**4 态格式**（`VK_OPACITY_MICROMAP_FORMAT_4_STATE_EXT`）为每个微三角形存储两个比特，支持四种不同状态：

* **透明（0）**：立即丢弃命中，不运行任何着色器。零开销。
* **未知-透明（1）**：调用任意命中着色器；如果着色器没有明确做出判定，遍历默认把该命中当作透明处理。
* **未知-不透明（2）**：调用任意命中着色器；如果着色器没有明确做出判定，遍历默认把该命中当作不透明处理。
* **不透明（3）**：立即确认命中，不运行任何着色器。零开销。

两个未知状态是让 4 态方案既正确又实用的关键。我们不必事先把每个三角形的每个像素都完美分类——那将需要无限细分——而可以采取保守策略。凡是 alpha 纹理在整个微三角形范围内明显为实体，就编码为不透明（3）；明显为空，就编码为透明（0）。只有在边界区域，也就是单个微三角形跨越 alpha 裁剪阈值边缘的地方，我们才承认不确定性，并用两个未知状态之一回退到任意命中着色器。对植被来说，未知-透明是典型选择：这个提示把驱动器的倾向引向透明，符合 alpha 边界处的统计预期。

对于设计良好的叶子纹理，不透明与透明区域占绝大多数，二者之间的边界只是一圈很窄的周长。如果微三角形网格足够细，这圈边界区域大约只占全部微三角形的百分之五到百分之十。其余百分之九十到九十五都被明确分类，任意命中着色器从不为它们触发。开销的下降与这个比例成正比。

== 可视化细分

image::images/omm_triangle_subdivision.svg[图示：一个叶子形状的三角形被细分成规则的微三角形网格；中心微三角形为绿色，表示不透明；外围微三角形为红色，表示透明；叶子边缘一圈细环为黄色，表示未知, 600, 500]

设想单个叶子三角形——一个平坦的四边形，它的 alpha 纹理显示出枫叶的形状。微图细分在这个三角形上叠加一层规则网格。在叶子中心，alpha 稳定为 1.0，该区域的每个微三角形经采样都判定为完全不透明。在我们的心智模型里它们被涂成绿色——落在其中的任何命中，硬件都会瞬间确认。

在远离叶子形状的四边形边缘，alpha 稳定为 0.0。该区域的每个微三角形经采样都判定为完全透明。它们被涂成红色——落在其中的任何命中，硬件都会瞬间跳过。

在叶子轮廓的精确边界上，纹理设计师为了让边缘不生硬，把 alpha 从 1.0 混合到 0.0，于是有些微三角形同时跨越这两个值。它们被涂成黄色——未知。只有它们在遍历期间会触发任意命中着色器。这圈黄环很窄，也许只有一两个微三角形宽，只占三角形面积的一小部分。

== 细分级别：以开销换精度

**细分级别**决定微三角形网格有多细。在级别 0，整个三角形只获得一个分类——整体共用一个状态。这只适用于真正均匀的几何（完全不透明或完全透明），对 alpha 测试内容来说并不常见。

在级别 1，每个原始三角形细分成 4 个微三角形；级别 2 变成 16 个；级别 3 变成 64 个；级别 4 变成 256 个。级别每提升一级，微三角形数量大致翻四倍，分类精度随之提高，代价是更多存储和更多前期计算。

对典型植被纹理，级别 2 或级别 3 提供了良好的平衡。单个叶子三角形的级别 3 微图包含 64 个微三角形。叶子形状在这个分辨率下得到相当好的近似——大部分叶体被分类为不透明，大部分空白被分类为透明，未知环很窄。升到级别 4 只会略微提高精度，却让内存占用翻四倍，而运行时收益很可能十分有限。

正确的选择取决于纹理内容和应用的性能目标。具有锐利、高对比 alpha 掩码的内容（比如近乎二值的铁丝网围栏）即使细分级别很低也能大幅受益，因为边界清晰。具有柔和、渐变 alpha 过渡的内容（比如毛发卡片或羽毛）可能需要更高的细分级别，才能把未知比例控制在较小范围。

== 构建微图：一次性投入

微图的构建过程有两个概念上不同、时间上可以分离的阶段：

**阶段 1——分类（CPU，每个资产一次）：** 对 alpha 测试网格中的每个三角形，以及在选定细分级别下的每个微三角形，构建器会在微三角形内若干位置采样 alpha 纹理——通常取质心，或在多个抖动位置上采样。它对采样值求平均并与阈值比较。如果平均 alpha 高于上阈值（接近 1.0），该微三角形被分类为不透明；如果低于下阈值（接近 0.0），分类为透明；如果落在两个阈值之间，分类为未知（具体是未知-透明还是未知-不透明，取决于应用策略）。输出是一个紧凑的每微三角形 2 比特数组——典型网格只需几百千字节。

**阶段 2——GPU 构建（仅设备端，在加载时运行）：** 分类得到的 2 比特数据被上传到 GPU 内存。一条 `vkCmdBuildAccelerationStructuresKHR` 命令被录制并提交到设备队列。驱动器执行内部布局转换与压缩，产出硬件原生遍历格式的微图 `VkAccelerationStructureKHR`。`VK_KHR_opacity_micromap` 不提供宿主端构建路径——这个 GPU 提交步骤始终必需。

两个阶段可以在加载时合并（**在线模式**），也可以分离（**离线模式**）。在线模式下，分类和 GPU 构建都在场景首次加载时运行——开发期间很有用，但会增加与网格和纹理复杂度成正比的启动开销。离线模式下，阶段 1 作为内容制作期间的预处理运行；产出的 2 比特数组保存到磁盘，随应用一起发布。运行时只执行阶段 2，把启动开销压到最低。GPU 构建本身无法预先烘焙：驱动器需要在目标硬件上运行它，才能产出其原生内部表示。

这是每个网格、每个纹理、每个细分级别的一次性操作。对要发布的游戏或可视化应用来说，收益比是巨大的——分类开销在制作期间只付一次，而收益会在应用渲染的每一帧中累积。

这个过程产出的是一段紧凑的 2 比特值数组（针对 4 态格式）：每个微三角形一个值。不透明编码为 3，透明编码为 0，未知-透明编码为 1，未知-不透明编码为 2。对大多数植被，边界微三角形使用未知-透明（1）：它让任意命中着色器做最终判定，同时提示结果更可能是透明。对于一个有 10,000 个叶子三角形、细分级别为 3 的网格，微图数据是 10,000 乘 64 个微三角形再乘 2 比特，约 160 千字节。改用 2 态格式可以把它减半到约 80 千字节，代价是完全取消任意命中回退。与网格数据本身相比，这点内存占用可以忽略。

== 数据存放在哪里

分类后的微三角形数据被上传到 GPU，用来构建一个类型为 `VK_ACCELERATION_STRUCTURE_TYPE_OPACITY_MICROMAP_KHR` 的 **`VkAccelerationStructureKHR`**。这是 KHR API 中一次刻意的统一：`VK_KHR_opacity_micromap` 没有为微图数据引入单独的对象类型，而是把微图直接并入既有的加速结构抽象。你用于 BLAS 和 TLAS 的同一个 `VkAccelerationStructureKHR` 句柄，也是微图的句柄——创建时的 `type` 字段负责区分它们。微图加速结构通过 `vkCreateAccelerationStructureKHR`（来自 `VK_KHR_acceleration_structure`）分配，并传入 `VK_ACCELERATION_STRUCTURE_TYPE_OPACITY_MICROMAP_KHR` 作为类型。构建微图使用 `vkCmdBuildAccelerationStructuresKHR`，并把 `geometryType` 设为 `VK_GEOMETRY_TYPE_MICROMAP_KHR`——与所有加速结构构建所用的是同一条设备端命令。KHR API 中没有单独的宿主端微图构建路径；所有微图构建都由 GPU 驱动。

微图加速结构构建完成后，会在 BLAS 构建或重建期间附着到对应的 BLAS 上。附着通过 `VkAccelerationStructureTrianglesOpacityMicromapKHR` 结构指定，该结构被链入传给加速结构构建的几何描述。其中的 `micromap` 字段就是你刚构建的微图的 `VkAccelerationStructureKHR` 句柄。`indexBuffer` 字段把原始三角形映射到它们的微图条目，它是一个普通的 `VkDeviceAddress`——KHR API 中没有宿主地址变体，这体现了仅设备端的设计哲学。到这一步，微图数据就成了加速结构本身的一部分——以硬件原生遍历格式存放在 GPU 内存中。

遍历硬件在 BVH 遍历过程中，把微图数据当作常规操作的一部分读取。没有额外的 API 调用，不需要修改着色器，也没有任何需要逐帧管理的同步原语。一旦 BLAS 带着附着的微图构建完成，硬件就会每一帧、对每条触及该网格的光线直接使用它——自动、透明、以硬件速度。光线查询着色器确实需要 `OpacityMicromapKHR` SPIR-V 执行模式（通过 `SPV_KHR_opacity_micromap` 扩展声明），以告知编译器不透明度微图数据可能影响遍历结果；这只是 GLSL 或 HLSL 源码里的一行声明，没有任何运行时开销。

== 有损构建：用完美换更高精度

`VK_KHR_opacity_micromap` API 还提供了一个额外的自由度：**有损构建标志** `VK_BUILD_ACCELERATION_STRUCTURE_MICROMAP_LOSSY_BIT_KHR`。在微图构建期间设置该标志后，驱动器就被允许对微图数据施加有损压缩。作为交换，驱动器或许能支持更高的有效细分级别——把微三角形网格推到原本无法在可用内存预算内容纳的精细程度。超过标准上限 `maxOpacity4StateSubdivisionLevel` 的细分级别可能变得可用，最高可达 `maxOpacityLossy4StateSubdivisionLevel` 报告的值。

实际影响比较微妙。有损构建可能会依据压缩后的状态，偶尔把某个微三角形从未知提升为不透明或透明，这意味着即使未压缩的分类本来是模糊的，该微三角形的任意命中着色器也不会触发。对大多数植被、大多数观察距离而言，这在视觉上无法察觉。对于 alpha 边界精度至关重要的内容——细发丝、羽毛或特写的叶子几何——你可能更愿意避开有损标志，接受稍粗一些的细分。选择权属于应用。

== 深刻的简洁

退后一步，品味一下发生了什么。我们把 alpha 测试光线遍历中最昂贵的部分——每次命中、每一帧为发现不透明度而调用的着色器——彻底移出了热路径。我们用一个预先烘焙的数据结构取代它，硬件以固定功能的速度读取这个结构。我们没有改变视觉结果：任意命中着色器仍会为未知微三角形触发，保证边界处的正确性。我们也没有显著改变应用的 API 足迹。我们只增加了一个构建步骤和一个附着结构。

对大多数植被而言，这意味着与叶子几何的阴影光线交互中，可能有 95% 在着色器意义上已不再有开销——它们完全由硬件处理，与不透明几何遍历处于同一周期预算。只有那圈细窄的边缘像素——真正跨越 alpha 边界的 5%——仍然要付任意命中着色器的开销。这一改进不是舍入误差，而是工作负载性质上的质变。
