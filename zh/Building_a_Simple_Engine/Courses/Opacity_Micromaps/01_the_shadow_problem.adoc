= 阴影、光照与树叶的麻烦

== 黑暗的几何学

阴影是缺失。当某个东西挡在表面与光源之间时，剩下的就是阴影。然而这种缺失承载着巨大的感知重量——阴影告诉我们形状、告诉我们一天中的时刻、告诉我们深度，也告诉我们场景中物体之间的关系。早在任何算法出现之前，画家们就花了几百年学习如何令人信服地绘制阴影，因为人类视觉系统对阴影极其敏感。

最容易分析的阴影是**硬阴影**——在阳光明媚的日子里，你会在室内看到窗户在地板上投下一个边缘完全锐利的矩形光斑。这种锐利来自几何。理想的点光源会照亮它能看到的每个表面，其余一切则留在彻底的黑暗中。边界处没有任何歧义。一个表面点要么能看见光源，要么看不见。阴影的边缘是一条数学曲线——从光源视角看到的遮挡物轮廓的投影。

image::images/omm_hard_shadow.svg[点光源投下边界锐利的硬阴影示意图, 600, 380]

在光线追踪阴影系统中，计算这件事在概念上很干净。我们从表面点向光源投射一条光线。如果这条光线在到达光源之前与任何几何体相交，该点就在阴影中。如果它不受阻挡地到达光源，该点就被照亮。阴影之所以锐利，是因为每像素只投射一条光线，答案是二值的。

== 真实光线的柔和

自然界并不提供点光源。太阳虽远，在天上仍然张开一个很小但不为零的角度——大约半度弧，实际上相当于一个圆盘。室内照明使用面光源：灯管、灯板、球泡和漫射器。就连蜡烛火焰也有实际的尺寸。

当光源有面积时，阴影的几何就变得更有意思。设想一个朝向太阳的表面点。如果遮挡物（比如屋檐的边缘）把整个太阳圆盘都从视野中挡住，该点就处于**本影**中——完全在阴影里，根本接收不到直射阳光。如果遮挡物只挡住太阳圆盘的一部分，该点就处于**半影**中——它从圆盘未被遮挡的那部分接收到一部分直射阳光，但不是全部。被遮挡与未被遮挡的圆盘面积之比，决定了该点看起来有多亮。

image::images/omm_soft_shadow.svg[面光源产生柔和阴影的示意图，显示本影与半影区域以及渐变边界, 600, 420]

**半影**就是阴影边缘那道漂亮的渐变——从全影到全亮的模糊过渡。它在日常经验中如此熟悉，以至于渲染图像里一旦缺少它，立刻就会显得不真实。我们的眼睛已经习惯了柔和边缘。当我们看到一个又大又亮的光源投下完全锐利的阴影边缘时，总觉得哪里不对，哪怕说不出原因。

在我们的引擎中，软阴影的近似方式是：每像素投射多条阴影光线，在光源表面采样不同的点，再对结果取平均。每条光线给出二值答案（被挡住或没有），平均值产生平滑的渐变。软阴影的质量随采样数提高，性能代价也随之增长。

== 树登场

现在设想一个有一棵树的场景。不是风格化的卡通树——而是有成千上万片叶子的写实树。制作这棵树的美术并没有把每片叶子都建模成有厚度、每个面都有几何的三维实体。那会需要多得无法管理的多边形。他们用的是一种在游戏和可视化领域几十年来已成标准的技术：每一簇叶子都由少量大而平的三角形表示，每个三角形带一张显示叶子细节形状的纹理。

这张纹理有两个组成部分：叶子的颜色（绿色，带叶脉图案和光散射的微妙变化）以及 **alpha 通道**——一个掩码，精确地定义纹理矩形中哪些像素是「叶子」、哪些是「天空」。叶子存在的地方 alpha 值为 1.0，不存在的地方为 0.0，边缘处有一段很窄的渐变，以避免生硬的像素级锯齿。

从远处看，效果非常漂亮。三角形几乎看不见，你只看到由 alpha 定义的叶子形状。轮廓看起来很自然、很复杂，尽管底层几何只是一组稀疏的平面四边形。这就是 **alpha 遮罩**几何体，它在实时内容中无处不在：树木、灌木、草、铁丝网围栏、锻铁栏杆、窗帘、粒子精灵，等等。

== 当阴影光线遇到叶子

麻烦就从这里开始。当一条阴影光线穿过场景并遇到这棵树时，BVH 遍历引擎会找出包围盒与光线相交的候选三角形。对一堵实心墙来说，事情到此为止：光线击中三角形，命中被确认，表面点处于阴影中。结束。

对叶子三角形来说，事情还没有结束。从几何上讲，三角形确实在那里——光线与这个平面矩形相交了。但交点究竟落在叶子上，还是落在叶子之间的透明空隙里？GPU 只看三角形本身无法知道。它必须在与光线交点对应的具体 UV 坐标处查询 alpha 纹理。只有查完之后，它才能决定是确认这次命中（该点位于一片实心叶子上），还是忽略它（该点位于透明空间，光线继续前进）。

这次查询由 **any-hit 着色器**执行——当几何体被标记为带 alpha 测试时，每出现一个候选命中，这个小小的可编程着色器就会被触发。而关键在于，光线不会在第一个候选处停下。一条穿过树冠的光线可能会穿过几十个叶子三角形。每一个都会触发 any-hit 着色器。每一个都需要一次纹理采样。每一个都在拖延遍历。

== 问题的规模

为了让这件事变得可感：想象你要判断自己的手是否处在树荫里。但这棵树不是实心不透明的物体，而是每一片叶子都由瑞士奶酪做成——奶酪上的孔里什么也没有，就是空的。要知道某个孔是否挡住了照到你手上的光，你得亲手把那片叶子拿起来，举到光前，看孔是否与光源对齐。然后拿起下一片叶子。再下一片。一整棵树，以 4K 分辨率渲染，每像素 16 条软阴影采样光线，每秒刷新 60 次——「检查奶酪」的次数每秒会达到数十亿。

image::images/omm_foliage_problem.svg[显示带 alpha 纹理的叶子网格的示意图，多条阴影光线各自都必须逐一测试每个叶子三角形, 600, 400]

这些检查中的每一次都需要执行着色器、采样纹理并做出判断。大多数时候，答案是「透明的，继续前进」。但无论答案是什么，提问的代价都已经付出了。

== 换个更好的问题

现在该换一个更好的问题了。在场景加载时，我们就确切知道叶子纹理长什么样。我们知道每个三角形哪些部分不透明、哪些部分透明。这些信息在帧与帧之间不会变化——叶子并不会在纹素级别做动画。那么我们为什么要在每一条阴影光线、每一帧上重新发现它呢？

如果能在加载时一次性告诉硬件，每个三角形哪些部分肯定是实心的、哪些部分肯定是空的，会怎样？如果 GPU 能在遍历期间查询这份预先烘焙的知识，只对真正有歧义的边缘区域运行昂贵的着色器，又会怎样？这正是「不透明度微图」的承诺。
