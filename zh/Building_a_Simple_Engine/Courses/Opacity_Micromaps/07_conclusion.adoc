= 结语：连接美术与硬件

== 反向重走这段旅程

我们以漂亮的阴影和一个隐藏的问题开启了这门课程。阴影看起来是对的，帧也在正常渲染。但在视觉正确性的底下，GPU 正在进行大量重复的探索——每秒六十次地重新弄清每片树叶的哪些部分是实体、哪些部分是空气。我们把这个冗余追溯到 GPU 遍历硬件的根源，精确理解了 any-hit 着色器为什么必要、为什么昂贵、为什么发散与缓存未命中会让开销进一步叠加，以及为什么问题恰恰会随着那些让渲染最具视觉吸引力的特性而增长。

随后我们完整地学到了解决方案。不透明度微图把 GPU 反复提出的问题的答案预先烘焙好。它们把每个三角形细分成一张微三角形网格，并为每一个赋予永久状态。这份分类结果存储在加速结构自身之中，使固定功能的遍历硬件能够解决绝大多数经过 alpha 测试的相交，而无需进入可编程着色器的领域。any-hit 着色器从无所不在的主力降级为少见的专家，只在真正不确定的边缘区域被调用。

结果就是，植被茂密的场景中的阴影运行得显著更快、看起来完全一致，而且不需要对阴影着色器做任何修改。节省会随软阴影采样数成倍增长，恰恰在那些对视觉质量最重要的渲染配置中变得最有价值。

== 图形学中反复出现的主题

这里从问题到解决方案的旅程，遵循了实时图形优化史上反复出现的一种模式：把工作从运行时移到预处理，从通用计算移到专用硬件，从探索移到已有知识。

光照贴图把动态光照求值移到了离线烘焙中。预计算辐射传输把复杂的光照积分移到了预计算中。网格着色器把几何放大移到了更贴合硬件的阶段。在每一个例子中，底层的洞见都是相同的：如果答案可以提前知道，就一次性付出代价，并把结果以硬件最容易访问的形式缓存起来。不透明度微图是这个原则一个格外干净的实例，因为预烘焙的数据很小、收益很大，而且集成到现有渲染管线几乎是无缝的。

理解这个模式会给你一项可迁移的技能。下次在光线追踪或光栅化管线中遇到性能瓶颈时，首先要问的问题之一就是：「这是不是本可以提前知道的信息？」如果答案是肯定的，很可能就存在一个可以找到的优化。

== 你现在理解了什么

你理解了一个真正现代、硬件级别的 GPU 特性。`VK_KHR_opacity_micromap` 把微图对象统一进标准的 `VkAccelerationStructureKHR` 句柄，并使用纯设备端的 API——微图构建与所有其他加速结构构建一样，走同一条 `vkCmdBuildAccelerationStructuresKHR` 命令。这种设计让生命周期管理保持简单而一致。许多图形开发者对微图还并不熟悉；把这套扩展理解透彻本身就是一项有分量的差别。

你理解的不只是 API 表面，还有 API 存在的原因。你知道它解决什么问题、它工作在硬件的哪个层级，以及实践中存在哪些取舍。这种深度的理解，正是能把一个特性用起来的人与能评估它、扩展它并向他人解释它的人之间的区别。

== 下一步

打开 `Courses/` 附件文件夹中的 `OpacityMicromapBuilder` 源文件。带着这门课程建立的概念框架去通读实现。留意三个阶段——分析、分类、构建——是如何对应代码结构的。找一找细分层级的启发式逻辑，想一想它是否适合你正在渲染的内容。

检查光线查询着色器时，找一下 `OpacityMicromapKHR` 的 SPIR-V 执行模式声明。遍历启用了微图的加速结构的着色器必须声明这个执行模式；按照 SPIR-V 规范，省略它会产生**未定义行为**。这是个很小的细节，但在阅读或编写与启用微图的几何体交互的光线查询着色器时，认识到它很重要。

在引擎中用配置开关启用和禁用 OMM，然后用 GPU 性能分析器——NVIDIA Nsight Graphics 或 AMD Radeon GPU Profiler——在植被茂密的场景上分别捕获两种配置。查看 any-hit 着色器调用次数、BVH 遍历阶段的耗时，以及 warp 占用率指标。这些数字会给你任何解释都无法完全替代的直觉。

当你准备好更进一步时，去研究 `VK_EXT_displacement_micromap`——这个姊妹扩展使用了类似的微三角形细分模型，但目的不是不透明度，而是几何位移。不透明度微图让你把 alpha 烘焙进加速结构，而位移微图让你把精细的表面细节——通常存储在位移图中的那一类——直接烘焙进 BVH，而无需为把这些细节镶嵌进网格而付出多边形开销。你在这门课程中建立的概念基础可以直接迁移过去。

硬件很聪明。学着与它并肩思考，正是你成为更高效的图形工程师的途径。
