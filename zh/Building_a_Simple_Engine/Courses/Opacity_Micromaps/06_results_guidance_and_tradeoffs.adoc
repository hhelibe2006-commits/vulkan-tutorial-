= 看清差异并掌握使用时机

== 阴影看起来是什么样

先从你实际能看到的东西说起。在简易引擎中启用不透明度微图，渲染一个植被茂密的场景时，视觉结果应当与非微图版本无法区分。树叶投下的阴影应当具有同样精细的轮廓。树冠下方的半影渐变应当同样柔和。在下方地面的阴影图案中，应当能辨认出每一片树叶的形状。

这是特性，不是局限。不透明度微图是一种性能优化，而不是一种近似。它们的设计目标是产生与完全着色器驱动的路径完全相同的视觉输出，唯一的例外是分类边界（那圈薄薄的 Unknown 微三角形）仍然依赖与之前相同的 any-hit 着色器。输出的视觉一致性并非巧合——它是该扩展的一项设计要求。

发生变化的是性能分析器显示的内容。在以植被为主的场景中——林间空地、种着阔叶植物的花园露台、头顶树冠茂密的公园——花在 any-hit 着色器上的时间应当大幅下降。降幅取决于内容、细分层级，以及阴影光线与经过 alpha 测试的几何体相交的比例，但在非常适合的场景中，any-hit 调用次数下降 60% 到 90% 很常见。对于采样数较高的软阴影，这直接转化为帧时间节省，GPU 性能分析器会显示为光线遍历阶段的耗时减少。

对于 bistro 风格的场景——摆着藤椅的露台、枝叶繁茂的头顶藤蔓、半透明的咖啡馆遮阳伞——OMM 带来的帧时间改善可能足以在不超出帧预算的前提下再提升一档软阴影采样数。这种免费得来的画质提升，正是找准目标的 GPU 优化给人的感觉。

== OMM 何时才物有所值

不透明度微图在特定条件组合下效果最强。第一个条件是**阴影路径中存在经过 alpha 测试的几何体**：被 alpha 掩码的对象必须真的投射出能到达被渲染像素的阴影。场景另一头的一棵漂亮的树，如果位于阴影相机的视锥之外，或者背对光源，就不会产生任何阴影光线流量，也就无法从 OMM 中获得任何好处。

第二个条件是**较高的阴影光线数量**。OMM 带来的节省是按每条光线计的，因此会随每像素阴影光线数成比例放大。每像素 8、16 或 32 个采样的软阴影配置会按比例放大收益。如果你渲染的是每像素一条光线的硬阴影，OMM 仍然有帮助，但绝对的帧时间节省更小。

第三个条件是**阴影路径中的几何复杂度**。稀疏的几片树叶三角形不足以形成足够的 any-hit 着色器压力，让 OMM 的开销变得划算。而拥有成千上万个相互重叠的树叶层、光线必须穿过许多层才能找到实体命中或离开的茂密树冠，正是 OMM 被设计用来应对的情形。

室内植被、茂密的森林走廊、公园、丛林环境以及写实的城市绿化，都是很好的候选场景。带有铁丝网围栏、工业格栅、穿孔板以及基于粒子的效果（其中粒子四边形使用 alpha 掩码）的场景，同样能显著受益。

== OMM 帮不上忙的时候

对于完全不透明的几何体——实心墙体、地板、载具、没有经过 alpha 测试的头发或衣物的角色——硬件本来就使用快速的已提交命中路径。此时不存在需要消除的 any-hit 着色器调用。OMM 对不透明几何体的性能没有影响，你也不会给不透明网格挂上微图。

三角形数量很少的简单场景不是好的候选对象。构建微图、把它们存进 GPU 内存并挂到 BLAS 上的开销是真实存在的，即使很小。对于一个只有十几片树叶三角形的场景，这笔开销比它省下的还多。

对那些经过 alpha 测试的几何体很少处于投射阴影配置的场景，收益也有限。如果太阳在相机后方、植被完全被逆光照射，那么植被中经过 alpha 测试的三角形大多不在任何表面点与光源之间——阴影光线根本到不了它们。该几何体的 any-hit 着色器调用次数本来就很低。

最后，要注意 OMM 对传统意义上的**部分透明**没有任何帮助——带有中间 alpha 值的几何体（例如烟雾、玻璃或半透明植被着色器）无法使用 OMM，因为这些材质需要由 any-hit 着色器计算出物理正确的部分遮挡。OMM 专门用于二值的 alpha 掩码，也就是正确答案始终是完全不透明或完全透明、绝不会是中间值的情况。

== 选择细分层级

细分层级决定了精度与内存占用之间的平衡。对大多数植被纹理来说，从层级 2（每个原始三角形 16 个微三角形）开始是个不错的首选。在这个层级上，树叶边缘被捕捉得足够精细，可以把 Unknown 的比例保持在较低水平，而内存开销也很温和。

如果性能分析显示 any-hit 着色器仍然占用大量时间——说明 Unknown 比例偏高——提升到层级 3（64 个微三角形）通常能把分类精度提高到足以产生明显差别的程度。升到层级 4（256 个微三角形）很少有必要，而且可能生成超出大型场景内存预算的微图数据。

引擎的 `OpacityMicromapBuilder` 提供了一个方法，用于在分类之后查询 Unknown 的比例：有多少百分比的微三角形最终处于 Unknown 状态。如果这个比例高于 15% 或 20%，提高细分层级很可能是值得的。如果已经在 5% 以下，当前层级大概就是最优的。

`VK_KHR_opacity_micromap` 引入了**有损构建模式**，通过在建微图时设置 `VK_BUILD_ACCELERATION_STRUCTURE_MICROMAP_LOSSY_BIT_KHR` 标志来启用。设置该标志后，驱动被允许在内部进行有损压缩，作为交换，它可以支持超过标准 `maxOpacity4StateSubdivisionLevel` 上限的细分层级——最高可达 `maxOpacityLossy4StateSubdivisionLevel` 中报告的值。对于偶尔重新分类边界微三角形可以接受的内容，这是一个把分类精度推到超出标准硬件限制的有用手段，代价是驱动可以对存储的状态采取更大的自由度。

硬件还对单个微图对象内可容纳的微三角形总数施加了绝对上限，即 `maxMicromapTriangles`。对于密度极高的网格，例如大片地形块，或是在较高细分层级下拥有成千上万个基础三角形的极精细植被簇，展开后的微三角形数量可能超过这个上限。出现这种情况时，必须把网格拆分成多个子网格，每个子网格带有自己的微图，确保没有任何单个微图超过报告的最大值。在构建期的规划阶段就针对该上限做检查，可以避免运行时的意外。

== 硬件要求与优雅回退

特性可用性在设备初始化时通过查询 `VkPhysicalDeviceOpacityMicromapFeaturesKHR` 来检测——当该结构的 `micromap` 字段为 `VK_TRUE` 时，即认为该扩展存在且可用。特性缺失时，`OpacityMicromapBuilder` 会优雅地回退。

回退行为不只是一层安全网——它是一等的配置。许多用户会在不支持 OMM 的硬件上运行应用，体验必须正确且可接受。由于 OMM 不会改变渲染出的图像，回退路径在视觉上完全一致。唯一的差别是性能，它会优雅地退化到引入 OMM 之前的基线。

始终为回退路径做设计。绝不要假定 OMM 可用。用性能分析器分别测量两条路径，并为你自己的内容记录性能差异。优雅回退的姿态是精心设计的 GPU 特性的标志。
