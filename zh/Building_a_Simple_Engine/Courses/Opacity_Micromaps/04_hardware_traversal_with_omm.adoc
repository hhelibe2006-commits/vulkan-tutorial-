= 遍历内部：GPU 如何使用你的微图

== 一条阴影光线的两段旅程

理解不透明度微图在运行时做了什么，最好的方式是让一条阴影光线穿过两个世界——先是没有 OMM 的世界，然后是有 OMM 的世界——观察工作究竟在哪里发生、又在哪里消失。

image::images/omm_traversal_comparison.svg[并排对比图：没有 OMM 时的阴影光线遍历（大量任意命中着色器调用）与有 OMM 时的遍历（多数命中由硬件解决，着色器调用很少）, 700, 420]

=== 没有 OMM 的旅程

我们的阴影光线从树冠正下方地面上的一个表面点射出，目标是上方面光源上的采样位置。光线进入 BVH。

首先，它测试整个场景的顶层包围盒，发现相交。它下探到场景的子节点，逐层测试包围盒。树干、地面、附近的墙等非叶子几何被 BVH 快速排除。光线的路径穿过包含叶冠的包围盒区域，而这片区域里有几百个叶子三角形。

在 BVH 的叶子层级，遍历开始测试单个三角形。光线与第一个候选叶子簇的包围盒相交，于是若干叶子三角形成为候选。对每个候选，遍历硬件都判定该几何被标记为 alpha 测试，无法自动确认命中，于是调用任意命中着色器。

任意命中着色器运行。它收到交点的重心坐标，插值出 UV 坐标，发出纹理采样请求。纹理单元处理该请求——很可能是缓存未命中，因为这是第一帧，缓存还是冷的。采样返回。着色器把 alpha 值与材质的裁剪阈值比较。alpha 是 0.02——这是叶子之间的空隙。遍历继续。

下一个候选：又一个叶子三角形。任意命中着色器再次触发。UV 插值、纹理采样（又一次未命中）、比较。alpha 是 0.87——实心叶片。命中被确认。光线被阻挡。阴影查询返回「在阴影中」。

但仅这一条光线就调用了两次任意命中着色器，而森林场景中的大多数阴影光线会遇到更多次。一条以浅角度穿过树冠的光线，在找到实心命中或离开树木之前，可能会测试八个、十二个甚至更多叶子三角形。每次测试：一次着色器调用、一次纹理采样、一次判定。

乘以每像素 16 条阴影光线，再乘以数百万像素。任意命中着色器是整个帧中调用最频繁的着色器。

=== 有 OMM 的旅程

同一条阴影光线被射出。BVH 遍历过程完全相同——微图不改变 BVH 结构，也不改变包围盒层级。光线到达叶子几何区域，开始测试候选三角形。

第一个候选叶子三角形同样是 alpha 测试网格，但这次它附着了一张微图。遍历硬件像之前一样计算交点的重心坐标。然后——仍然在固定功能硬件中，没有任何着色器参与——它查找包含该交点的微三角形。该微三角形被分类为透明。硬件立即丢弃命中。没有着色器触发，没有纹理采样。遍历以极短的时间继续。

第二个候选：硬件检查微三角形。不透明。命中立即被确认。没有着色器触发，没有纹理采样。光线被阻挡。阴影查询返回「在阴影中」。

这条光线的任意命中着色器调用总数：零。一切由硬件解决。

如果另一条光线恰好落在叶缘区域——某个未知微三角形内——任意命中着色器确实会触发。但这是例外，而非常态。对一张细分良好的叶子纹理，这也许只发生在二十分之一的光线-叶子相交中，而不是二十分之十九。

== 硬件如何读取微图

微图数据在 GPU 内存中以紧密排列的 2 比特值数组存放，遍历硬件只要给定基址指针、步长和细分级别，就能直接寻址这种格式。当 BLAS 带着附着的微图构建时，加速结构会在几何旁边存下对这份数据的引用。

遍历期间，当硬件识别出候选三角形相交时，它执行一次微三角形查找，本质上是纯粹的索引计算：根据命中点的重心坐标和细分级别，算出该点落在哪个微三角形内，然后从数组中读取 2 比特状态。这是简单的整数运算——没有通用着色器，也不从单独管理的资源中取纹理。它属于固定功能遍历单元，与测试包围盒、计算相交距离的是同一套电路。

这就是硬件提供**硬件加速的不透明度求值**的含义。微图不是供着色器读取的计算缓冲区，而是嵌入加速结构的元数据，由遍历硬件自己读取。

在 `VK_KHR_opacity_micromap` 下，微图不是以单独的对象类型表示，而是以类型为 `VK_ACCELERATION_STRUCTURE_TYPE_OPACITY_MICROMAP_KHR` 的标准 `VkAccelerationStructureKHR` 创建。这种与标准加速结构对象的统一，是 KHR 扩展中刻意的设计选择：微图因此遵循与场景中所有其他加速结构相同的内存模型、屏障规则和生命周期管理，而不必引入一套平行的对象层级。

== OpacityMicromapKHR 执行模式

在 `VK_KHR_opacity_micromap` 中，光线查询的硬件微图快速路径**不是**自动生效的。阴影着色器必须显式声明由 `SPV_KHR_opacity_micromap` 定义的 `OpacityMicromapKHR` SPIR-V 执行模式，以告知遍历硬件它应当查询微图数据。在 GLSL 中，这个声明形如：

[source,glsl]
----
layout(constant_id = N) gl_EnableOpacityMicromapExt;
----

其中 `N` 是特化常量 ID。这个声明是 `SPV_KHR_opacity_micromap` SPIR-V 扩展的要求：如果光线查询着色器所遍历的加速结构包含不透明度微图，却没有以 `true` 声明 `OpacityMicromapKHR`，SPIR-V 规范规定这是**未定义行为**——而不是优雅地回退到任意命中路径。不要指望省略声明后会出现某种特定结果。这个声明让硬件的意图毫无歧义，也让驱动器和编译器能正确推断遍历行为。

== 对 warp 效率的连锁影响

回想上一章讲过的发散问题：当 warp 中的不同线程走不同代码路径时，warp 会被串行化。alpha 测试几何长期是发散的温床，因为任意命中着色器对不同光线会以不同结果触发。

有了 OMM，这种发散大幅减少。大多数光线-叶子相交根本到不了着色器。那些原本会在「命中的是实心还是透明」上分叉的线程，如今在着色器语境里根本不会走到这个判断——硬件在着色器甚至不知道存在候选相交之前，就在统一的固定功能路径中默默做出了判定。光线穿过透明微三角形的线程，与光线什么都没命中的线程保持同步，因为两条路径都是零开销的硬件操作。

未知微三角形仍会触发任意命中着色器，那里仍可能出现发散。但触发这条路径的调用比例小到足以让 warp 效率显著提升。在典型的植被密集场景中，从完全不用 OMM 换成分类良好的 OMM，可以把任意命中着色器调用减少 80% 到 95%。warp 效率的提升幅度与之相当可观。

== 软阴影的乘数效应

OMM 的性能收益随每像素阴影光线数成比例放大。对硬阴影——每像素一条光线——节省是真实的，但有限。对每像素 16 个采样的软阴影，节省会放大 16 倍。这是该技术最重要的实际意义之一。

软阴影是光线追踪渲染中最具视觉吸引力的特性之一，同时也是最昂贵的特性之一，因为开销直接随采样数增长。任何能降低阴影查询单条光线开销的手段，都会对软阴影性能产生倍增的影响。因此，OMM 恰恰在最影响视觉质量的渲染模式中——植被下方的高采样软阴影——效果最为显著。

还有一个更微妙的缓存收益。当相邻像素的 16 条阴影光线都测试同一批叶子三角形时（它们往往会这样，因为相邻像素看到的是相邻几何），这些三角形的微图数据在最初几条光线之后已经驻留在 GPU 的 L1 和 L2 缓存中。后续光线的微图查找在内存意义上几乎免费。相比之下，alpha 纹理每次都需要重新取，而且考虑到不同光线的 UV 坐标可能各不相同，它更不容易保持驻留。

== 阴影光线的完整生命周期

image::images/omm_shadow_ray_lifecycle.svg[流程图：展示启用 OMM 时阴影光线的生命周期——发出光线、BVH 遍历、发现候选命中、微图查找、分支到不透明、透明或未知；不透明与透明由硬件解决，未知回退到任意命中着色器, 600, 520]

在启用 OMM 的场景中，阴影光线的完整生命周期可以概括为一棵判定树。光线进入 BVH 遍历。对于每个候选三角形相交，硬件检查是否附着了微图。如果没有微图（非 alpha 测试几何），就走标准的不透明几何路径：立即确认命中。如果有微图，就查找微三角形状态。不透明：确认，不调用着色器。透明：丢弃，不调用着色器。未知：调用任意命中着色器，让着色器做最终判定。

对于不透明和透明两个分支，这棵判定树完全位于固定功能硬件中。只有未知分支进入可编程执行。结果是，GPU 的着色器执行单元从绝大多数 alpha 测试工作中解放出来，可以专注于真正需要着色器的情况。在 `VK_KHR_opacity_micromap` 中，要走上这条优化路径，还要求着色器已声明 `OpacityMicromapKHR` 执行模式。当加速结构包含不透明度微图却省略该声明时，按 SPIR-V 规范属于未定义行为——硬件与着色器必须达成一致，结果才正确。
