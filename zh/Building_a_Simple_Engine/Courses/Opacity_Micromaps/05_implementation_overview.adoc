= 在简易引擎中构建不透明度微图

== 概念架构

理解硬件是一回事，弄清这种理解如何转化为代码是另一回事。本章从概念层面走一遍引擎的不透明度微图实现。完整源码就在本课程旁边的 `Courses/` 文件夹中，我们会一路指引你查看具体文件。这里的目标是理解实现的形状：什么在什么时候发生、每个步骤为何必要、各部件如何连接。

实现围绕单个类 `OpacityMicromapBuilder` 组织，它定义在 `opacity_micromap_builder.h` 中，实现在 `opacity_micromap_builder.cpp` 中。这个类负责微图的整个生命周期：检查硬件支持、依据网格和纹理数据构建微图、管理其 GPU 内存，并把它们提供给 BLAS 构建过程。

== 阶段零：检查支持

在任何微图工作开始之前，引擎必须确认当前 GPU 和驱动器支持 `VK_KHR_opacity_micromap`。这个扩展相对较新，并非普遍可用。`OpacityMicromapBuilder` 在设备初始化期间检查该扩展并设置一个内部标志。如果扩展缺失，之后每次调用构建器都是空操作——引擎照常进行普通的 alpha 测试，与引入微图之前完全一样。

这种优雅的降级不是可选项，而是任何要发布的应用的硬性要求。无论 OMM 是否启用，内容看上去都必须正确。由于 OMM 不改变视觉结果（任意命中着色器仍是未知微三角形的回退，且着色器行为不变），禁用 OMM 后渲染在视觉上完全相同，只是回到更高的逐帧开销。回退路径不需要着色器里任何特殊的代码分支。

该扩展还要求启用 `VK_KHR_acceleration_structure`（任何光线追踪渲染本来就必须启用它），以及用于构建命令的 `VK_KHR_synchronization2`。这些依赖与主扩展一起检查。设备创建时使用的特性结构是 `VkPhysicalDeviceOpacityMicromapFeaturesKHR`，它暴露核心微图功能与可选的有损压缩特性的可用性；构建器查询这两项，并记录哪些能力处于启用状态。

== 阶段一：分析

当网格被提交给引擎加载时，`OpacityMicromapBuilder` 会检查网格的材质列表。对每个子网格，它检视材质属性并追问：这是 alpha 测试材质吗？具体来说，它是否带有 alpha 掩码纹理，并且被标记为使用 alpha 裁剪而非完全的透明混合？

如果答案是肯定的，该子网格就是微图生成的候选。构建器记录哪些子网格需要微图，并为每个子网格确定合适的细分级别。细分级别的选择目前基于一个简单启发式：构建器检查纹理尺寸，以及网格三角形数量与表面积之比。尺寸较小、细节精细的纹理受益于更高细分，而 alpha 图案简单的大三角形可以使用较低级别。引擎在选择细分级别时还会遵守设备报告的 `maxOpacityLossy4StateSubdivisionLevel` 和 `maxMicromapTriangles` 上限，确保所选参数仍在硬件能表示的范围内。`Courses/` 文件夹中的配置文件记录了这个启发式，以及如何按材质覆盖它。

分析阶段很快，在 CPU 上作为常规网格加载的一部分完成。它的输出是一份逐子网格的描述符，供下一阶段使用。

== 阶段二：分类

分类是实质工作发生的地方。对每个 alpha 测试子网格，以及该子网格中的每个三角形，构建器遍历所选细分级别下的所有微三角形。对每个微三角形，它计算该微三角形质心在原三角形中的重心坐标。再根据这些坐标插值三角形的 UV 坐标，求出质心在纹理空间中的位置。然后在 CPU 侧的 alpha 纹理上按该 UV 位置采样。

这里的采样刻意保持简单：在质心处做一次双线性采样，可选地与若干邻近的抖动采样一起平均，以减少边界处的锯齿瑕疵。如果采样得到的 alpha 高于上阈值（通常为 0.9），微三角形被分类为不透明；低于下阈值（通常为 0.1）则为透明；介于两个阈值之间则为未知。

分类结果被打包进一个紧凑数组——每个微三角形 2 比特——它构成 GPU 微图构建的原始输入。对大型网格，这个分类步骤可能耗时明显，所以对要发布的内容，它通常作为离线预处理的一部分执行，而不是在应用启动时进行。引擎两种模式都支持：加载期在线分类（用于开发），以及从二进制文件加载预先分类好的微图数据（用于生产）。

值得停下来体会这里的不对称性。分类步骤只运行一次，收益却在应用渲染的每一帧累积。对要发布的游戏或可视化应用来说，收益比是巨大的。

== 阶段三：GPU 构建

分类数据在 CPU 上准备好后，会被上传到暂存缓冲区，再传输到 GPU 本地内存。随后构建器填写 `VkAccelerationStructureBuildGeometryInfoKHR` 结构，指定 `type = VK_ACCELERATION_STRUCTURE_TYPE_OPACITY_MICROMAP_KHR`，以及几何类型 `VK_GEOMETRY_TYPE_MICROMAP_KHR`、用途标志、逐三角形的格式描述符、输入数据缓冲区地址，以及用于构建操作的临时缓冲区。目标加速结构句柄通过先调用 `vkCreateAccelerationStructureKHR` 获得——KHR 扩展复用了标准的加速结构创建路径，而没有引入专用的微图创建命令。

接着，构建器把对 `vkCmdBuildAccelerationStructuresKHR` 的调用录制到命令缓冲区，由它在设备上执行微图的实际构建。不存在宿主端构建路径——所有微图构建都必须提交到队列。这让加速结构工作牢牢留在设备侧：硬件内部的数据布局可以由驱动器在设备上决定并应用，无需经由宿主内存来回传输。

得到的 `VkAccelerationStructureKHR` 句柄会与子网格已有的 BLAS 几何描述符存放在一起。在 `VK_KHR_opacity_micromap` 中，微图不是单独的对象类型：扩展刻意复用标准加速结构句柄来表示微图，只靠创建类型区分。这显著简化了生命周期管理——适用于 BVH 加速结构的创建、屏障和销毁模式同样适用于微图加速结构，程序员不必再学一套平行的对象管理规则。该句柄必须在引用它的 BLAS 构建之前创建，并且在 BLAS 存活期间不得销毁。

还有一个值得注意的细节：微图的 `vkCmdBuildAccelerationStructuresKHR` 调用和 BLAS 构建本身一样，被录制到命令缓冲区并提交到 GPU 队列。微图数据不是由 CPU 算好再当作普通缓冲区推给 GPU——构建步骤会自行进行内部压缩与布局转换，把数据打包成遍历硬件的原生格式。引擎用一次传输与计算队列提交，为新加载的网格构建全部微图，然后在继续 BLAS 构建之前发出信号量。

== 把微图连接到 BLAS

微图 `VkAccelerationStructureKHR` 对象本身什么也不做。只有在 BLAS 构建或更新之前把它附着到 BLAS 的几何描述中，它才生效。附着通过 `VkAccelerationStructureTrianglesOpacityMicromapKHR` 结构完成，该结构被加入相关子网格的 `VkAccelerationStructureGeometryTrianglesDataKHR` 的 `pNext` 链。其中的 `micromap` 字段持有上面创建的 `VkAccelerationStructureKHR` 句柄，而 `indexBuffer` 字段（标识每个三角形对应哪个微图条目）是一个普通的 `VkDeviceAddress`。这里只接受设备侧地址，与整条管线中仅设备端构建的模型一致。

这条链就是把人类可读的概念（「这个叶子网格有一张微图」）与硬件可见的结果（「这个 BLAS 在其内部表示中包含微图数据」）字面连接起来的纽带。一旦 BLAS 带着这条链构建完成，之后所有针对该 BLAS 的遍历查询都会自动查询微图——前提是发起查询的着色器已声明所需的执行模式，如上一章所述。

附着微图后必须重建 BLAS。如果网格是静态的——植被通常如此——这就是一次性开销。如果网格发生形变（对微图用例不常见，但有可能），则必须重建微图并相应地更新 BLAS。`OpacityMicromapBuilder` 会跟踪哪些 BLAS 附着了微图，并在其微图数据变化时把它们标记为需要重建。

== 阴影着色器只需一点点补充

最优雅的部分就在这里。在完成所有这些基础设施工作——分析、分类、GPU 构建、BLAS 附着——之后，阴影着色器只需要增加一行，而不需要逻辑重写。

在 `VK_KHR_opacity_micromap` 下，光线查询着色器必须声明 `OpacityMicromapKHR` SPIR-V 执行模式，遍历硬件才会应用微图优化。在 GLSL 中，这表现为通过 `GLSL_EXT_opacity_micromap_ray_query_mode` 扩展启用 `gl_EnableOpacityMicromapExt`——着色器文件顶部的一行。没有它——而加速结构又包含不透明度微图时——SPIR-V 规范规定这是**未定义行为**，而不是优雅地回退到任意命中路径。着色器的其余部分不受影响：对 `rayQueryInitializeEXT`、`rayQueryProceedEXT` 以及标准查询函数的调用保持完全一致。微图对着色器的逻辑依然是透明的——遍历硬件在着色器层介入之前就处理了不透明和透明的微三角形，未知微三角形仍像以前一样通过同一机制调用任意命中着色器。着色器永远不会知道某次相交是由微图解决的还是由任意命中路径解决的。这一行声明不是逻辑改动，而是一个必须显式选择加入的开关，KHR 规范之所以要求它，是为了确保着色器作者已经考虑过微图参与所带来的、微妙的遍历顺序影响。

学员应打开 `Courses/` 文件夹中的 `opacity_micromap_builder.cpp` 查看三个阶段的完整实现，并查看 `simple_engine.cpp` 中引擎的主初始化序列，了解 `OpacityMicromapBuilder::buildForScene()` 在何处被调用。集成刻意保持最小——构建器是一个自包含的工具，插入已有的场景加载管线，而无需重构它。

== 内存与对象生命周期

构建器创建的每个微图 `VkAccelerationStructureKHR` 都连同其背后的设备内存分配，一起存放在一个持有句柄的向量中。构建器提供 `releaseAll()` 方法，用于销毁所有微图加速结构并释放其设备内存。场景卸载或引擎关闭时会调用它。

顺序要求很严格：必须先销毁 BLAS，再销毁它们引用的微图加速结构。因为 `VK_KHR_opacity_micromap` 中的微图就是标准的 `VkAccelerationStructureKHR` 对象，所以没有单独的销毁命令要学——拆掉 BLAS 所用的同一个 `vkDestroyAccelerationStructureKHR` 调用，同样能拆掉微图。BLAS 始终持有对其微图的活引用；KHR 模型中没有「可丢弃」或「可选」的微图附着概念。引擎的拆卸序列遵守这个顺序，在调用 `releaseAll()` 释放微图之前先销毁所有 BLAS 加速结构。如果你修改引擎的关闭序列，请保持这个顺序。

对于包含许多不同网格类型的大型场景，微图内存可能累积可观。`OpacityMicromapBuilder` 提供了一个查询微图总内存占用的方法，可用于实现基于预算的策略：如果微图内存超过阈值，优先级较低的子网格（视野中投射阴影的三角形较少的那些）可以用更低的细分级别构建，甚至完全跳过。设备报告的 `maxMicromapTriangles` 属性也给出了单个微图加速结构能构建的上限，构建器在决定是否把大型网格拆分到多个微图对象时遵守这个限制。
