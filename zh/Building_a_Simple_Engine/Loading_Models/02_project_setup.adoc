== 理解资产管线

在探索了引擎架构和相机系统之后，理解渲染引擎如何管理 3D 资产就变得很重要。精心设计的资产管线对于高效处理模型、纹理和其他资源至关重要，在任何生产环境中都是如此。

=== 资产组织概念

设计资产组织系统时，可以考虑以下关键原则：

1. *分类* - 把相似的资产归为一组
2. *层级* - 用嵌套结构管理复杂度
3. *可发现性* - 让资产易于查找和引用
4. *可扩展性* - 为项目扩张而设计

下面是一个最终产品中资产组织方式的示例，它演示了全部四项原则：

[source]
----
assets/
  ├── models/                  // 3D model files (Categorization)
  │   ├── characters/          // Character models (Hierarchy)
  │   │   ├── player/          // Player character models (Hierarchy)
  │   │   └── npc/             // Non-player character models (Hierarchy)
  │   ├── environments/        // Environment models
  │   │   ├── indoor/          // Indoor environment models
  │   │   └── outdoor/         // Outdoor environment models
  │   └── props/               // Prop models
  ├── textures/                // Texture files (Categorization)
  │   ├── common/              // Shared textures (Discoverability)
  │   └── high_resolution/     // High-res textures for close-up views (Scalability)
  ├── shaders/                 // Shader files
  │   ├── core/                // Essential shaders (Discoverability)
  │   ├── effects/             // Special effect shaders
  │   └── mobile/              // Mobile-optimized shaders (Scalability)
  └── config/                  // Configuration files
      └── quality_presets/     // Different quality settings (Scalability)
----

这个示例演示了全部四项原则：

- *分类*：资产按类型分组（模型、纹理、着色器、配置）
- *层级*：资产以嵌套结构组织（例如 models > characters > player）
- *可发现性*：常用资产放在专门的文件夹里（例如通用纹理、核心着色器），因此很容易找到
- *可扩展性*：结构可以容纳不同的质量级别和平台专属资产（例如高分辨率纹理、移动端着色器、质量预设）

具体的组织方式应当根据项目需求定制，但底层原则在不同引擎之间是一致的。

=== 资产管线概念

专业的资产管线通常包含若干阶段，无论具体的引擎实现如何：

1. *创建* - 美术在 3D 建模软件中制作模型
2. *导出* - 模型导出为适合游戏引擎的交换格式
3. *验证* - 检查模型是否有问题（例如缩放错误、纹理缺失）
4. *优化* - 针对运行时性能优化模型
5. *转换* - 开发资产转换为可直接用于生产的格式
6. *集成* - 资产导入引擎
7. *运行时加载* - 引擎在执行期间高效地加载资产

设计资产管线时，请考虑这些重要因素：

==== 选择文件格式

不同的文件格式各有取舍：

1. *交换格式*（例如 glTF、FBX、Collada）
   - 优点：建模工具广泛支持，能保留大部分数据
   - 缺点：可能包含不必要的数据，未针对运行时优化

2. *运行时格式*（例如 glb、引擎专属的二进制格式）
   - 优点：针对加载速度和内存占用进行了优化
   - 缺点：可能无法在引擎之外编辑

==== 纹理压缩

纹理压缩对性能至关重要：

1. *开发格式*（例如 PNG、JPEG）
   - 优点：无损或质量很高，编辑工具广泛支持
   - 缺点：文件体积大，未针对 GPU 优化

2. *运行时格式*（例如 ktx、GPU 压缩格式）
   - 优点：文件体积更小，GPU 可直接使用
   - 缺点：可能有质量损失，还需要考虑平台差异

==== 资产打包

考虑资产如何封装：

1. *独立文件*
   - 优点：更容易更新单个资产，版本控制更简单
   - 缺点：文件操作更多，可能出现依赖缺失

2. *打包资产*
   - 优点：文件操作更少，依赖关系有保证
   - 缺点：原子更新的体积更大，版本控制更复杂

=== 美术与引擎的协作概念

要把美术资产成功集成到渲染引擎中，需要美术与程序员之间清晰的沟通和既定的工作流。以下是需要考虑的关键概念：

==== 技术规范

无论具体引擎是什么，你都需要定义：

1. *坐标系* - 不同应用使用不同的坐标系（例如 Y 轴向上 vs. Z 轴向上）
2. *缩放* - 建立一致的缩放（例如 1 单位 = 1 米，或 1 单位 = 1 英尺）
3. *原点位置* - 定义不同类型资产的原点应放在哪里
4. *细节层级* - 规定不同类型资产与使用场景的面数范围

==== 工作流文档

编写文档时，应涵盖：

1. *命名约定* - 一致的命名有助于组织和自动化
2. *材质标准* - 定义材质应如何组织（例如 PBR 参数）
3. *导出设置* - 记录所选交换格式的正确导出设置
4. *质量检查清单* - 提供提交前验证资产的标准

==== 技术美术桥梁

可以考虑设立一个技术美术角色，其职责是：

1. 创建工具，简化从美术到引擎的管线
2. 在资产进入引擎之前对其进行验证
3. 就技术要求向美术提供反馈
4. 在资产于引擎中显示不正确时帮助排查问题

=== 从开发到生产的概念

从美术友好的开发资产过渡到优化后的生产资产，涉及几个重要概念：

==== 开发资产与生产资产

理解每个阶段的不同需求：

1. *开发资产*
   - 优先考虑可编辑性和迭代速度
   - 使用内容创作工具广泛支持的格式
   - 体积可能更大，对运行时性能的优化较少
   - 侧重保留最高的质量和最完整的信息

2. *生产资产*
   - 优先考虑运行时性能和内存效率
   - 使用针对目标平台优化的格式
   - 应用合适的压缩和优化技术
   - 在质量与性能要求之间取得平衡

==== 资产验证

在管线的关键节点实施验证：

1. *提交前验证*
   - 检查是否符合技术规范
   - 确认所有必需的纹理和材质都已就位
   - 确保缩放、朝向和原点位置正确

2. *转换前验证*
   - 确认资产能被转换工具成功处理
   - 检查可能在转换过程中引发问题的隐患

3. *转换后验证*
   - 确认转换后的资产保持视觉保真度
   - 检查性能问题或内存消耗问题
   - 确保与目标平台兼容

==== 自动化的考量

随着项目增长，自动化变得越来越重要：

1. *批处理*
   - 开发脚本或工具，一次处理多个资产
   - 实现自动化验证检查

2. *持续集成*
   - 考虑把资产处理集成到 CI/CD 管线中
   - 在资产提交时自动验证并转换

3. *版本管理*
   - 跟踪资产及其处理后版本的变更
   - 实现依赖跟踪，只重建必要的部分

=== 实现考量

在任何渲染引擎中实现模型加载系统时，有几个关键考量应当指导你的做法：

==== 抽象层

为模型加载系统设计合适的抽象层：

1. *文件格式层*
   - 负责解析特定文件格式（例如 glTF、FBX）
   - 隔离格式专属代码，让支持多种格式变得更容易
   - 把文件格式的结构转换为引擎的内部结构

2. *资源管理层*
   - 管理内存和 GPU 资源
   - 处理缓存和引用计数
   - 无论底层文件格式如何，都提供一致的接口

3. *场景图层*
   - 以层级结构组织模型
   - 管理变换和父子关系
   - 便于剔除和场景遍历等操作

==== 性能考量

在灵活性与性能之间取得平衡：

1. *异步加载*
   - 考虑在后台线程中加载模型，避免阻塞主线程
   - 实现处理部分加载模型的机制

2. *内存管理*
   - 制定处理大型模型的策略
   - 为复杂场景考虑细节层级（LOD）系统
   - 为超大型环境实现流式加载

3. *批处理与实例化*
   - 把相似的模型归组以高效渲染
   - 对重复出现的元素使用实例化

==== 可扩展性

为未来的扩展而设计：

1. *材质系统*
   - 创建能表达多种着色模型的灵活材质系统
   - 同时支持简单材质和复杂材质

2. *动画系统*
   - 为不同的动画类型而设计（骨骼动画、形变目标等）
   - 考虑动画将如何与物理和玩法系统交互

3. *自定义数据*
   - 允许把引擎专属的元数据关联到模型上
   - 支持用于玩法或渲染目的的自定义属性

理解这些概念，为在任何渲染引擎中设计和实现模型加载系统打下了坚实基础。从一开始就仔细考虑抽象、性能和可扩展性，你就能构建出稳健的系统，随项目需求扩展并适应不断变化的要求。

== 我们的项目实现

既然已经探讨了资产管线的通用概念，接下来讨论我们的具体项目将如何落实这些概念。

=== 文件格式与目录结构

我们的引擎将使用以下文件格式和目录结构：

1. *模型格式*：我们使用内嵌 KTX2 纹理的 glTF 2.0 二进制格式（.glb）。该格式有几个优势：
   - 紧凑的二进制表示，存储和加载都更高效
   - 可以内嵌纹理，减少文件操作
   - 支持动画、蒙皮和 PBR 材质
   - 行业标准，工具支持广泛

2. *纹理格式*：纹理使用 Basis Universal 压缩的 KTX2，它提供：
   - 相比 PNG/JPEG 显著减小的体积
   - GPU 可直接上传的现成格式
   - 通过转码实现跨平台兼容
   - 支持 mipmap 和多种压缩格式

3. *目录结构*：
[source]
----
assets/
  ├── models/                  // 3D model files
  │   ├── characters/          // Character models
  │   │   └── viking.glb       // Example character model
  │   ├── environments/        // Environment models
  │   │   └── room.glb         // Example environment model
  │   └── props/               // Prop models
  │       └── furniture.glb    // Example prop model
  └── shaders/                 // Shader files
      └── pbr.slang            // PBR shader
----

=== 工具与库

我们将使用以下工具和库来实现资产管线：

1. *模型加载*：使用 tinygltf 库解析 glTF 文件。该库提供：
   - 对 glTF 2.0 规范的全面支持
   - 高效的二进制 glTF 文件解析
   - 可访问所有 glTF 组件（网格、材质、动画等）

2. *纹理加载*：使用 KTX-Software 库加载 KTX2 纹理，它提供：
   - 加载并转码 Basis Universal 压缩纹理的支持
   - 高效的 mipmap 处理
   - 与 Vulkan 纹理格式的集成

3. *资产转换*：把开发资产转换为生产资产时，我们使用：
   - KTX-Tools 做纹理转换（PNG/JPEG 到 KTX2）
   - glTF-Transform 做模型处理和优化
   - 自定义脚本自动化转换流程

=== 与引擎架构的集成

我们的模型加载系统将与前面章节的引擎架构集成：

1. *资源管理*：我们复用引擎架构一章的资源管理系统来：
   - 缓存已加载的模型和纹理
   - 实现引用计数以高效管理内存
   - 支持模型的异步加载

2. *组件系统*：我们创建以下组件：
   - ModelComponent：管理模型渲染和动画
   - MaterialComponent：处理材质属性和纹理
   - 这些组件将与相机与变换一章的 TransformComponent 协同工作

3. *渲染管线*：我们的模型加载系统将以如下方式与渲染管线集成：
   - 为几何体通道提供网格数据
   - 为光照通道支持 PBR 材质
   - 为重复模型启用实例化渲染

=== 美术工作流

面向美术的工作流如下：

1. *开发阶段*：
   - 美术在 Blender 或 Maya 等工具中创建模型
   - 导出为标准 glTF（.gltf），纹理为独立的 PNG/JPEG
   - 用 glTF 查看器测试，确保外观正确

2. *技术要求*：
   - 右手坐标系，Y 轴向上
   - 1 单位 = 1 米的缩放
   - 使用金属度-粗糙度工作流的 PBR 材质
   - 纹理尺寸为 2 的幂

3. *转换流程*：
   - 按技术要求验证模型
   - 把纹理转换为 Basis Universal 压缩的 KTX2
   - 把纹理嵌入 glb 文件
   - 优化模型（移除未使用的顶点、压缩网格等）

4. *集成*：
   - 把转换后的资产放到合适的目录
   - 在资源管理系统中注册资产
   - 用合适的组件创建实体

=== 运行时加载

在运行时，我们的引擎将：

1. *加载模型*：
   - 用 tinygltf 解析 glb 文件
   - 提取网格数据、材质和动画
   - 为顶点和索引创建 Vulkan 缓冲区

2. *处理材质*：
   - 加载内嵌的 KTX2 纹理
   - 创建 Vulkan 图像视图和采样器
   - 为 PBR 渲染设置描述符集

3. *处理动画*：
   - 从 glTF 解析动画数据
   - 实现骨骼动画系统
   - 支持动画混合与过渡

4. *渲染模型*：
   - 用场景图以层级方式组织模型
   - 应用变换组件中的变换
   - 用合适的材质和着色器渲染

通过实现这些具体的做法，我们的引擎将拥有一套稳健而高效的资产管线，与本章前面讨论的通用概念保持一致。
