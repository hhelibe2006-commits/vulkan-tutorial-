== 光线查询渲染

本引擎包含一个基于 Vulkan *光线查询*的光线追踪渲染模式。你不必搭建完整的光线追踪管线（raygen／miss／hit 着色器），光线查询让你直接在普通着色器中执行相交测试。

在本示例中，我们用*计算着色器*里的光线查询渲染整个帧：

* 构建 *BLAS*（逐网格）和 *TLAS*（场景实例）。
* 派发一个计算着色器，它：
** 从相机为每个像素生成一条主光线。
** 用 `TraceRayInline()` 在 TLAS 中查找相交。
** 用与光栅路径相同的 PBR 工具对命中点着色。
* 把结果写入存储图像，然后合成到交换链。

=== 为什么用光线查询？

光线查询很适合「混合」渲染器：

* 你可以从计算、片元或其他着色器阶段调用它们。
* 它们复用标准描述符系统。
* 它们把控制流留在你的着色器代码里：如何遍历、何时接受命中、如何着色，都由你决定。

=== 高层架构

从高层看，Ray Query 模式涉及三块内容：

* *加速结构*：由场景的顶点缓冲区和索引缓冲区构建。
* *描述符*：绑定 TLAS、输出存储图像，以及着色所需的场景数据。
* *着色器*：生成光线、执行查询、对命中点着色。

关键的一点是，光线查询着色器并不「拥有」场景。它读取与光栅化相同的场景资产（网格、材质、纹理），只是通过一套为计算路径单独设计的描述符集。

=== 加速结构构建（BLAS/TLAS）

场景准备好后，我们构建加速结构：

* 每个唯一网格创建一个 BLAS。
* 每个场景实例连同其变换加入 TLAS。
* 每个 TLAS 实例编码一个自定义实例索引，好让着色器能索引到对应的 `GeometryInfo` 表。

Ray Query 着色器用这个逐实例索引来查找：

* 顶点缓冲区与索引缓冲区的设备地址
* 材质索引
* 用于得到正确世界空间法线的逐实例法线变换

=== 描述符布局

Ray Query 模式使用专用的描述符集布局。具体的绑定编号很重要，因为它们必须与着色器匹配。

本引擎中的典型绑定为：

* 绑定 0：一个小的 Ray Query 专用 UBO（相机矩阵、曝光／gamma、开关）
* 绑定 1：TLAS
* 绑定 2：输出存储图像
* 绑定 3：光源缓冲区
* 绑定 4：`GeometryInfo` 缓冲区
* 绑定 5：材质缓冲区
* 绑定 6：用作纹理表的大型组合图像采样器数组

=== 流式加载安全的纹理访问

本引擎异步流式加载纹理。Ray Query 模式的一个关键设计选择是：着色器通过一个固定大小的数组（「纹理表」）来索引纹理。

在运行时：

* 材质在表中存储纹理*索引*（baseColor、normal、metallic-roughness、occlusion、emissive）。
* 渲染器用*当前*的纹理句柄刷新该表。
* 槽位 `0..4` 保留给共享的默认纹理（这样采样总有一个有效回退）。

这种做法让着色器中的着色保持简单：采样使用 `NonUniformResourceIndex()` 和 `SampleLevel(..., 0.0)`（显式 LOD 对计算很重要）。

=== 派发与呈现结果

Ray Query 计算着色器写入存储图像（通常是支持 HDR 的格式）。

派发之后：

* 一个屏障把 Ray Query 输出图像从 `GENERAL`（写）转换到 `SHADER_READ_ONLY_OPTIMAL`（读）。
* 一个全屏合成通道采样输出图像，并写入交换链。
* 最后一次转换让交换链为呈现做好准备。

这样引擎就能在光栅路径和光线查询路径上复用同一套后处理控制（曝光／gamma）。

=== 代码里该看哪里

* 着色器：
** `shaders/ray_query.slang`
* CPU 侧的 Ray Query 构建与描述符：
** `renderer_ray_query.cpp`
* 渲染循环集成与 UI：
** `renderer_rendering.cpp`
* 描述符索引特性（用于大型采样器数组）：
** `renderer_core.cpp`
