= 同步与流式加载

现代 Vulkan 提供了强大的工具，让我们在资产流式加载进来的同时保持 GPU 忙碌。本引擎使用后台上传器、专用传输队列和 Synchronization 2 来避免停顿与闪烁。下面我们逐一走过这些部件，看看它们如何配合。

== 思路

- 文件 I/O 和暂存（staging）发生在渲染线程之外。
- GPU 拷贝和布局转换在传输队列上运行，而不是图形队列。
- 时间线信号量让图形侧可以等待「最近一次完成的上传」，而无需逐个资源管理栅栏。
- 我们只在安全点更新描述符（就在等待当前飞行帧的栅栏之后），因此绝不会写入 GPU 仍在使用的描述符集。

这让帧循环保持简单、响应及时——即使大纹理正在流式加载。

== 后台上传器

我们把纹理任务入队（转码／IO → 暂存缓冲区 → 设备图像）。一个专用线程会：

1. 把待处理的拷贝批量收集到一个位于传输队列上的命令缓冲区。
2. 用 Synchronization 2 录制从 `TRANSFER_DST_OPTIMAL` 到 `SHADER_READ_ONLY_OPTIMAL` 的布局转换。
3. 提交一次，并发出一个单调递增的时间线值。
4. 通知渲染器哪些纹理现在「可以采样」。

渲染提交会包含对最新上传时间线值的等待，所以到我们绘制时纹理已经可用。

== 描述符更新的安全点

Vulkan 不允许我们修改正在使用的描述符集。引擎改为这样做：

* 每帧开始时，我们等待与该飞行帧关联的栅栏。
* 此时更新这一帧的描述符集就是安全的（它们没在使用）。
* 我们就在这一刻用已上传纹理的视图／采样器刷新图像绑定。

结果是不会有纹理「翻来覆去」或闪烁：一旦真实纹理替换了占位符，它就会稳定下来。

== 实践中的 Synchronization 2

上传路径使用 `vkCmdPipelineBarrier2`，作用域清晰且最小：

* 暂存 → 图像拷贝：把目标图像置为 `TRANSFER_DST_OPTIMAL`。
* 最后一次拷贝之后：转换到 `SHADER_READ_ONLY_OPTIMAL`（src 阶段 = `eTransfer`，dst 阶段 = `eFragmentShader`）。
* 只有当传输队列和图形队列属于不同族时才需要转移所有权（大多数桌面驱动共用族）。

在图形侧，我们把附件布局转换保持在任何动态渲染通道实例之外，并且同样使用 `vkCmdPipelineBarrier2` 以保证可读性。

== 一张纹理的典型旅程

1. 任务带着文件路径入队。
2. 后台线程：加载／转码到暂存缓冲区，分配设备图像，录制拷贝。
3. 提交到传输队列；发出时间线信号。
4. 渲染器开始下一帧；逐帧栅栏解除阻塞。
5. 这一帧的描述符更新为指向已上传的图像（安全点）。
6. 绘制：片元着色器采样新纹理，没有停顿。

== 提示与陷阱

* 把描述符更新放在安全点。避免更新正在使用的描述符集。
* 批量拷贝使用传输队列；让图形队列专注于绘制。
* 为清晰起见优先使用 Synchronization 2（阶段／访问配对是显式的，转换会一目了然）。
* 批量上传：提交越少，CPU 开销越低。

做到这些，流式加载对玩家就「无形」了——代码也能保持整洁。

== 后续工作想法

如果你想进一步推进流式加载：

* 按 mip 层级流式加载（先加载低 mip），然后在后台细化。
* 在开发构建标志后面加一个小的流式状态 HUD（已入队字节数、已上传字节数、就绪纹理数）。
* 增加逐资源优先级（相机距离、重要性标签），让最显眼的资产先到达。
* 增加纹理「热重载」，以在快速更替下验证描述符生命周期规则。
