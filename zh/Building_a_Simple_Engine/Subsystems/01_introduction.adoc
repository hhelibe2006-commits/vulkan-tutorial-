= 子系统：简介

== 引擎子系统简介

在前几章中，我们已经搭好了简易引擎的基础，实现了渲染管线、相机系统与模型加载等核心组件。现在，我们准备通过添加两个关键子系统来扩展引擎的能力：音频与物理。

这两个子系统对于在现代游戏与仿真中营造沉浸式、可交互的体验至关重要。它们看上去可能与我们一直关注的图形管线没有直接关系，但现代引擎可以借助 Vulkan 的计算能力来增强音频处理与物理模拟。

=== 本章内容

本章将带你实现两个让游戏与仿真鲜活起来的关键引擎子系统。我们先从音频子系统入手，从播放音效与音乐的基础讲起，再进阶到头部相关传输函数（HRTF）处理这类更复杂的技术，以实现令人信服的 3D 空间音频。这一过程展示了 Vulkan 计算着色器如何把基础的音频播放转变为随你的 3D 世界响应的沉浸式声场。

物理子系统走的是类似的路线，先讲碰撞检测与响应这些让物体交互显得可信的基本机制。在打好这些基础的过程中，我们会演示 Vulkan 的并行处理能力如何大幅加速物理计算，从而支持大量相互作用的物体参与模拟——这类场景会让传统的基于 CPU 的方案不堪重负。

本章全程延续前几章采用的现代 C++ 做法。

=== 为什么音频与物理要用 Vulkan？

用 Vulkan 来做音频处理与物理模拟，乍看之下可能不太常规，但它代表了一种充分利用现代硬件能力的、面向未来的引擎开发思路。

现代 GPU 通过数以千计的、为并行计算而设计的核心提供强大的并行处理能力。借助 Vulkan 的计算着色器，我们可以把这份算力用于远超图形渲染的任务。音频处理从并行操作中获益极大——想象一下同时处理几十个声源并施加实时空间效果，或者运行涉及数千个相互作用物体的复杂物理模拟。

Vulkan 的统一内存模型带来了传统分离式方案无法企及的效率机会。当图形、音频与物理处理共享内存空间时，我们就能消除那些否则会在 CPU 与 GPU 之间反复搬运信息的高昂数据传输。这种共享内存架构让复杂的交互成为可能——物理模拟可以直接影响粒子系统，音频处理可以响应视觉效果，所有系统能够无缝协同。

当项目面向多种设备时，跨平台一致性变得越来越有价值。通过 Vulkan 实现这些子系统，我们可以在 Windows、Linux、移动平台以及新兴设备上保持一致的行为。这种一致性减少了调试时间，并确保音频与物理行为无论部署在哪个目标上都可预测。

性能收益不止于原始算力。把密集计算卸载到 GPU，可以释放 CPU 资源用于游戏逻辑、脚本、AI 处理，以及其它需要顺序处理或复杂分支的任务。这种分工让每种处理器都能专注于自己最擅长的任务。

此外，这里还想提供一种视角：在你的应用中使用 Vulkan 并不只是为了图形。本教程的目标并不是给你一个达到生产质量的游戏引擎，而是为你提供必要的工具，让你能够应对任何 Vulkan 应用开发，并批判性地思考你的应用如何从 GPU 中获益。

=== 实践考量：不要把一切都卸载到 GPU

虽然 Vulkan 计算能带来可观的加速，但把所有子系统都卸载到 GPU 并不总是明智的——在移动端尤其如此：

* 移动端功耗与散热：许多手机和平板使用 big.LITTLE CPU 丛集以及受功耗/散热限制的移动 GPU。持续的重度 GPU 计算很快就会触发温度降频，导致帧率下降与延迟不稳。
* 调度与延迟：GPU 擅长吞吐量，但某些任务（紧凑的控制循环、以指针操作主的小规模更新）由于启动开销与调度延迟，可能更适合放在 CPU 上执行。
* 确定性与调试：对于影响玩法的关键物理，确定性和能在 CPU 上逐步调试都是有优势的。在移动端可以考虑把宽阶段检测甚至整个物理都留在 CPU 上，或者采用混合方案（例如 CPU 做宽阶段 + GPU 做窄阶段）。
* 内存带宽：在集成式架构上，GPU 与 CPU 共享内存带宽。激进地把一切都搬到 GPU 会与图形工作争抢带宽，损害帧时间与续航。

音频方面的专门建议：

* 在可行的情况下，优先使用平台音频 API 以及任何可用的专用音频硬件/DSP（用于混音、重采样、效果处理）。这条路径通常延迟更低、功耗表现更好，并且在各设备上行为更可预测。
* 现实中专用硬件对 HRTF 的支持并不普遍。许多消费级设备依赖操作系统或应用内的软件 HRTF。评估你的实际需求：纯软件的 HRTF 管线可能已经足够；除非你有大量声源或复杂效果，否则很少有必要把 GPU 算力严格留给空间音频。

实用建议：

* 先做性能分析：在迁移工作负载之前，先建立 CPU 与 GPU 的基线。
* 偏向混合设计：把明显可并行、计算量大的内核（例如批量约束求解、FFT/IR 卷积）卸载出去，同时把控制与协调留在 CPU 上。
* 为移动场景做规划：提供运行时开关，根据设备档位、温度状态与电源模式在 CPU/GPU 路径之间切换。
