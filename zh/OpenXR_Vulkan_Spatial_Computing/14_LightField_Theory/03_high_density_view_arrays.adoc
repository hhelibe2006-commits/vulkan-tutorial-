= 高密度视图阵列

管理一个 4D 光场，既要优化存储，也要优化访问，才能应对动辄达到 GB 规模的数据集。

== 生态系统视角

本章属于以下类别：**超越 OpenXR 标准**。

标准 OpenXR 运行时聚焦于固定分辨率的投影层。你用 Vulkan 的缓冲区设备地址（BDA）与稀疏驻留来管理全光数据所需的高密度视图阵列，从而实现超越标准 OpenXR 缓冲区模型的空间细节。

== GB 级难题

管理一个 4D 光场会带来严峻的内存挑战。一个只有 latexmath:[1024 \times 1024] 个入射点、latexmath:[32 \times 32] 个角度的不起眼光场，就包含约 10 亿条光线。按每条光线 16 字节（RGBA FP32）计算，那就是 **16 GB 的 VRAM**——超过许多消费级 GPU 的容量。

运行时与操作系统紧密协作，把这些庞大的缓冲区「固定」（Pin）在 VRAM 中，通常使用**稀疏驻留**（通过 `VK_KHR_sparse_binding`）只加载可见的瓦片。

== FP16 与量化：节省带宽

降低精度是优化的第一步。在 Slang 中用 `half4` 代替 `float4`，VRAM 占用立刻减半。光场中相邻的光线往往非常相似，因此可以实现高质量压缩，而不会带来明显的视觉损失。

== 缓冲区设备地址（BDA）：基于指针的访问

面对如此庞大的数据集，标准 Vulkan 描述符集的开销可能成为瓶颈。借助**缓冲区设备地址**，我们可以把一个指向数据的原始 64 位指针直接传进着色器。

[source,cpp]
----
// Using BDA to get a raw pointer using designated initializers
vk::BufferDeviceAddressInfo addressInfo{
    .buffer = *lightFieldBuffer
};
uint64_t gpuAddress = device.getBufferAddress(addressInfo);

// Passing the pointer to a Slang shader via Push Constants
struct PushConstants {
    uint64_t lightFieldPtr;
    uint2 stRes;
    uint2 uvRes;
};
commandBuffer.pushConstants<PushConstants>(*pipelineLayout, vk::ShaderStageFlagBits::eCompute, 0, pc);
----

== 进阶：神经压缩与 4D 缓存局部性

Vulkan 支持超越标准线性缓冲区模型的内存优化：

*   **神经光场压缩**：使用 Vulkan 的**视频解码**与**压缩**扩展，你可以实现自定义的、基于计算的解压器。这样就能在同样的 VRAM 占用下容纳多得多的空间细节。
*   **4D 分块与重排**：你可以用计算着色器实现自定义的重排（例如 Morton 序索引），在采样高密度光场阵列时保持 GPU 缓存高效。

== 缓存局部性：空间-方向分块

标准的 4D 数组布局对 GPU 缓存极不友好。为了解决这个问题，我们实现 **4D 分块**，重新组织数据，让小块的、在空间与方向上相邻的数据在内存中连续存放。

[source,slang]
----
// Tiled 4D indexing example in Slang
uint getTiledIndex(uint2 st, uint2 uv) {
    uint2 tileSize = uint2(8, 8);
    uint2 tileCoord = st / tileSize;
    uint2 localCoord = st % tileSize;

    // Reorganizing memory to keep spatial neighbors together
    return (tileCoord.x + tileCoord.y * stResTiles) * (tileSize.x * tileSize.y) +
           (localCoord.x + localCoord.y * tileSize.x);
}
----
