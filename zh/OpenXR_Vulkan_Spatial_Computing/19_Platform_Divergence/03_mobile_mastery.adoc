= 移动端精通：攻克散热墙

移动空间计算是一场极限效率的演练。在一体机头显上，我们必须在约 5–10 瓦的功耗预算内跑完整个引擎、追踪与显示。

== 生态视角

本章属于类别：**你的 OpenXR 运行时大概率在做的事**。

一体机移动运行时会在幕后处理繁重的架构工作，例如热节流、直接到显示的扫描输出，以及合成帧生成（SpaceWarp）。你使用 Vulkan 的分块渲染特性，让自己的引擎与这些运行时行为对齐，从而榨取最大性能。

== 概念：分块渲染（TBR）

大多数移动 GPU（例如来自 Qualcomm、Arm 或 Imagination 的产品）采用**分块渲染**架构。GPU 不是一次性渲染整个屏幕，而是把屏幕切成一块块细小的瓦片（例如 16x16 像素）。它在高速、低功耗的片上内存（**LDS** 或 **SRAM**）中完整处理每一块瓦片，然后才把最终结果写回主存。

在移动空间计算中，**丢弃就是胜利**。

[source,cpp]
----
// Configuring optimal mobile attachments using designated initializers
vk::RenderingAttachmentInfo depthAttachment{
    .imageView = *depthView,
    .imageLayout = vk::ImageLayout::eDepthStencilAttachmentOptimal,
    .loadOp = vk::AttachmentLoadOp::eClear,
    .storeOp = vk::AttachmentStoreOp::eDontCare, // CRITICAL: Discard depth after use
    .clearValue = vk::ClearValue{.depthStencil = {1.0f, 0}}
};
----

在 Vulkan 1.3 中，我们可以使用**动态渲染本地读取**扩展（`VK_KHR_dynamic_rendering_local_read`），在同一瓦片内读回颜色或深度值，而不必访问主显存。这对延迟着色至关重要，能让整个操作都留在片上。

== 应用空间扭曲（ASW）：合成帧

为了在移动端维持流畅的 90Hz 体验，我们经常使用**应用空间扭曲**。它让引擎以一半帧率渲染（例如 45 FPS），剩下每隔一帧由 XR 运行时合成生成。

*   **工作原理**：引擎向运行时提供**运动矢量**和一张深度图。
*   **结果**：GPU 只对一半的帧执行繁重的着色，从而留出余量给更复杂的场景和更高的保真度。

== 进阶：瓦片本地延迟着色与线程亲和性

Vulkan 让我们能超越标准循环，攻克移动端的「散热墙」：

*   **瓦片本地延迟着色**：借助 Vulkan 的**输入附件**，你可以在高速片上内存中完成复杂的光照与后处理，避开昂贵的「主存税」。
*   **实时线程亲和性**：你可以用 Vulkan 的**优先级队列**为引擎的命令提交显式申请「实时」优先级，确保空间渲染不会被后台系统更新拖慢——这是标准本身并不保证的协调程度。

== 高效的空间同步

移动头显使用**统一内存**，CPU 和 GPU 共享同一块物理 RAM。这虽然简化了零拷贝交接，但也意味着两者要争夺**内存带宽**。每一次纹理采样和缓冲区写入都必须有正当理由。
