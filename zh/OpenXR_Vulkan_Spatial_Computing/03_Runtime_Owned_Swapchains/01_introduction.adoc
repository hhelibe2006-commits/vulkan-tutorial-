= 运行时拥有的交换链与图像包装：简介

在标准 Vulkan 应用中，引擎完全掌控交换链。我们创建 `VkSwapchainKHR`，决定图像数量与格式，并拥有内存。而在空间计算中，这个模型被彻底颠倒过来。

为了达到舒适 XR 体验所需的近乎零延迟，**XR 运行时**（合成器）必须拥有最终的那组图像。这样运行时才能执行**异步重投影**——在像素被频闪打到显示器上的那一刻，对你的图像做后期扭曲，使其匹配用户当时的头部姿态——而无需把你的数据拷贝进它自己的内存空间。

在本章中，我们将探讨从引擎拥有资源到运行时拥有资源的架构转变：

1.  **外部图像协商**：如何向 OpenXR 请求交换链图像，并处理运行时提供的格式。
2.  **RAII 资源集成**：把运行时提供的原始 `VkImage` 句柄包装进引擎的 `vk::raii::Image` 与 `vk::raii::ImageView` 抽象中。
3.  **内存所有权生命周期**：掌握**等待-获取-释放**循环，它取代了标准的 `vkAcquireNextImageKHR` 循环。

== 「等待-获取-释放」节奏

最显著的变化在于我们如何访问渲染目标。在桌面应用中，我们向交换链要一个图像索引并渲染进去。在 OpenXR 中，我们必须遵循严格的三步协议：

*   **等待**：阻塞，直到运行时准备好交给我们一张交换链图像。
*   **获取**：正式取得某个特定图像索引的所有权。
*   **释放**：命令缓冲区提交完成后，把图像交还给合成器。

这个节奏确保我们永远不会渲染到正在被显示或被合成器扭曲的图像中，从而避免撕裂并保证尽可能高的视觉稳定性。

到本章结束时，你的引擎将能够把空间视图直接渲染进头显合成器的缓冲区，同时继续使用现有的 RAII 包装器，并尊重运行时的所有权。
