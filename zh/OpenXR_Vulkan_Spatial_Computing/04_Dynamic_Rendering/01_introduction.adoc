= 面向空间视图的动态渲染

在把 OpenXR 与 Vulkan 1.3 集成的旅程中，我们已经建立起一套稳健的握手流程，也学会了如何管理那些实际由 XR 运行时拥有的图像。然而，拿到图像只是战斗的一半。现在我们需要把立体视图渲染到这些图像里。在之前构建引擎的系列中，我们采用**动态渲染**（通过 `VK_KHR_dynamic_rendering`）作为主要渲染路径。现在我们就来看看，这个决定对空间计算而言为何如此关键。

== 为什么 XR 要利用动态渲染？

对空间计算来说，我们已经构建好的动态渲染系统带来三大优势，而传统的渲染通道管线很难做到：

1.  **降低提交延迟**：既然我们已经绕过了复杂的渲染通道和帧缓冲区对象，就能更快地把视图矩阵（下一章会进行预测）转换成命令缓冲区提交。
2.  **自适应视口**：XR 头显常常使用不对称投影和非平行视图。我们的动态渲染路径可以轻松为每只眼睛重新配置视口与剪刀矩形状态，而不必让它们去匹配某个预定义的静态结构。
3.  **多视图集成**：当我们转向 `VK_KHR_multiview` 进行单趟立体渲染时，现有的动态渲染逻辑可以无缝集成，允许我们直接在 `vk::RenderingInfo` 中指定 `viewMask`。

在本章中，我们会把引擎的渲染逻辑应用到空间显示的特殊需求上。我们先看如何把 XR 交换链图像直接绑定到渲染会话，然后再处理现代头显所需的复杂视口。
